- **Scope:** rows written by Sim Meyhouse `a229f22b-2aac-4e54-a8b2-033a8f93ac5e`

- **Measurement:** [`REPAIR-2026-09-05-measure.md`](./REPAIR-2026-09-05-measure.md)
- **The operation:** [`repair-2026-09-05.sql`](./repair-2026-09-05.sql) — a data
  operation, **not** a migration. It deletes nothing, asserts every count against
  the measurement, and rolls the whole transaction back on any disagreement.

## 1. What it does

| | rows | change |
|---|---|---|
| **Class A** | 48 | `provisional_for_restaurant_id := <the one venue that stocks it>`, `producer := NULL`, `country := NULL`. The trigger rekeys the row under `venue:<id>\|`. |
| **Class B** | 29 | `country := NULL` only. A real producer; the row stays shared. |
| **Cross-link** | 1 | Antalya gets its own provisional `House White Wine` row; its `restaurant_inventory` (1), `inventory_lots` (1) and `pour_events` (2) move onto it, and the inventory row's `wine_name` goes back to the venue's own words. Sim Bistro's `ac6a550f` row is left byte-identical. |
| **Deleted** | 0 | Nothing is deleted, so none of the eight `ON DELETE CASCADE` FKs can fire. |

Each `UPDATE` is self-limiting — it fires only while the fabricated value is
still there — so a real value entered later survives and a second run is a no-op.

### A defect the dry run caught before production saw it

The first run aborted:

```
ERROR: value too long for type character varying(20)
CONTEXT: insert into public.master_wine_library (wine_id, ...) values
         ('WINE_repair_20260905_antalya_house_white', 'House White Wine', ...)
```

`master_wine_library.wine_id` is `varchar(20)` and `UNIQUE`. The literal was
40 characters. **The whole transaction rolled back and the fixture was
unchanged** — which is the shape the real run needs to have. Fixed to
`WINE_rpr0905ahw` (15 chars; confirmed unused in production).

Two of these need saying plainly rather than being reported as green:

- **`check_beverage_kind_regression.py` is red, and 77 of its 78 rows predate
  this repair.** Every `menu_import` row has been `classification_status =
  'unclassified'` since 2026-09-03 because the bulk-add path never asks the
  classifier; the guard was already failing at 77. The repair adds the 78th — the
  provisional row for Antalya's house white — and leaves it unclassified on
  purpose, because nobody has said what that wine is. Filed as item 5 in the ADR
  0130 block of `v3.0-TECH-DEBT.md`, with the writer named as the actual fault.
  The guard is not wired into CI, so this does not gate a merge.
- **`canonical_corpus_run.py` regenerated two files that have nothing to do with
  this repair** (`datasets/canonical/corpus-run-2026-09-05.*`, procurement
  invoice invariants). Its output *improved* against what is on `main` — 9 named
  failures → 5, 6 untestable → 4 — which is another track's work landing, not
  this one's. Reverted rather than committed here.
