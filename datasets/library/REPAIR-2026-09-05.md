## 1. What it does

| | rows | change |
|---|---|---|
| **Class A** | 48 | `provisional_for_restaurant_id := <the one venue that stocks it>`, `producer := NULL`, `country := NULL`. The trigger rekeys the row under `venue:<id>\|`. |
| **Class B** | 29 | `country := NULL` only. A real producer; the row stays shared. |
| **Cross-link** | 1 | Antalya gets its own provisional `House White Wine` row; its `restaurant_inventory` (1), `inventory_lots` (1) and `pour_events` (2) move onto it, and the inventory row's `wine_name` goes back to the venue's own words. Sim Bistro's `ac6a550f` row is left byte-identical. |
| **Deleted** | 0 | Nothing is deleted, so none of the eight `ON DELETE CASCADE` FKs can fire. |

Each `UPDATE` is self-limiting — it fires only while the fabricated value is
still there — so a real value entered later survives and a second run is a no-op.

### A defect the dry run caught before production saw it

The first run aborted:

```
ERROR: value too long for type character varying(20)
CONTEXT: insert into public.master_wine_library (wine_id, ...) values
         ('WINE_repair_20260905_antalya_house_white', 'House White Wine', ...)
```

`master_wine_library.wine_id` is `varchar(20)` and `UNIQUE`. The literal was
40 characters. **The whole transaction rolled back and the fixture was
unchanged** — which is the shape the real run needs to have. Fixed to
`WINE_rpr0905ahw` (15 chars; confirmed unused in production).

### Behaviour, not just column values

| | result |

### Negative control — the guard must refuse a database it did not measure

A clone of the repaired database with **one** Class A row rewound to its
fabricated state (so `class_a = 1`, not 48 and not 0):

```
ERROR: ABORT: pre-state does not match the measurement. class_a 1/48,
       class_b 0/29, house-white inventory 0/1, lots 0/1, pours 0/2.
       Re-measure; do not force.
```

and the rewound row still carried `country = 'Unknown'` afterwards — the
transaction rolled back rather than half-applying.
