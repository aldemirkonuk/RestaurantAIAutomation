## 2. The route/page-graph script cannot see the ADR 0149 rollout mechanism — treat its "orphans" as false positives

`generate_system_atlas.py`'s route resolver only follows a route whose `element={<Component/>}` name matches a statically-lazy-imported component. Since the finish-goal work (ADR 0149), the 24 flag-gated pages are wired as:

```
<Route path="/orders" element={<PageGate page="orders" legacy={<Orders/>} next={<OrdersNext/>} />} />
```

(`apps/web/src/App.tsx:239-396`). The script's regex only ever captures `PageGate` as the "component," can't map it to a file, and therefore never scans `Orders.tsx`/`OrdersNext.tsx` for outgoing links. Result:

- **Route-file resolution: 20/61 (33%)** — the other 41 are legitimately-built pages the script simply can't trace, not unbuilt pages.
- **"39 orphan entry points"** in the regenerated `PAGE_MAP.md` — verified by hand that this list is almost entirely the app's own primary nav (`/orders`, `/providers`, `/receiving`, `/reports`, `/team`, `/wines`, `/communications`, `/notifications`, `/documents-reports`, `/logs`, `/connections`, `/receipts` …), reachable from `HouseHeader`'s sidebar, which the script never scans. **This is not 39 dead pages** — it's the script being blind to the PageGate pattern and to sidebar-nav components outside each route's own directory. Only a genuinely small number of these orphans are real edge cases worth checking by hand: `/authorize/:integrationId`, `/credits`, `/services`, `/calendar-classic`, `/distributors`, `/inventory-legacy` (deliberate legacy fallback — see memory `inventory-command-page`), and the four `/simpos/*` / `/studio/*` clusters (internal tooling, expected to be entry-only).
- **Page-graph edges: only 26**, concentrated in public/auth pages (login, register, onboarding, help, privacy…) — the in-app navigation graph for all 24 Mudavym-flagged pages is effectively unmeasured by this tooling.

**Finding for the founder's checklist:** the atlas generator itself needs an ADR-0149-aware update (resolve `legacy=`/`next=` JSX props on `PageGate` calls, not just a single lazy import) before its page-graph and orphan counts can be trusted again. Until then, "dead link" and "orphan" claims from this script should not be acted on directly.

## 3. Per-page: Mudavym design vs. legacy — measured from production, not assumed

`apps/web/src/lib/mudavym/useMudavymDesign.ts` lists 20 pages enrolled (`MUDAVYM_PAGES`), all 20 are registered in the gateway's `feature-flag-registry.ts` (each with a `readBy` pointing back at the hook — no dangling/unregistered flags found). Queried the live flag table (`restaurant_feature_flags`, SELECT only):

- **`restaurant_feature_flags` has exactly 1 row**, out of **14 restaurants** in production. 13 of 14 restaurants have no flags row at all and therefore see **100% legacy design on every page** (the registry's documented fail-safe: no row/flag ⇒ off). Whether that's intended (1 pilot house on Mudavym, 13 dormant/demo/other tenants) or an oversight is a founder call, not something the code states either way — flagging as OPEN, not asserting a defect.
- On that one row, measured flag state:

| Page | Flag column | Live? |
|---|---|---|
| dashboard, orders, receiving, receiving_door, providers, communications, team, inventory, receipts, documents_reports, document | `mudavym_design_*` | **ON** (11 pages) |
| reports, notifications, recommendations, calendar, settings, profile, cellar, connections, logs | `mudavym_design_*` | **OFF / legacy** (9 pages) |

This matches the in-flight lane-status dossier (`.../dff04c7e-.../lane-status-2026-09-18.md`, another session's scratchpad, read for cross-reference only): settings, cellar, recommendations, receiving-rebuild-v2, and others are still `ready=False` on feature branches, consistent with their flags being off in the one production row.

- `inventory`'s `PageGate` passes the **same component** (`InventoryCommandPage`) for both `legacy` and `next` (`App.tsx:312`) — the flag is registered but structurally inert for that route; either intentional (page already unified) or a leftover that should be pruned from `MUDAVYM_PAGES`/the registry. Worth a one-line founder confirmation, not a rebuild.
- Two flagged "pages" are not legacy/new pairs at all: `connections` is a new ADR-0114 route (off ⇒ redirects to `/profile`, no legacy twin) and `document` is ADR-0104 D12's canonical `/documents/:id` view (off ⇒ redirects to `/receipts`). Counting these as "legacy vs. Mudavym" pages would overstate the redesign gap; they're additions, not migrations.
- `/inventory-legacy` is a real, separately-routed legacy fallback (matches memory `inventory-command-page`), reachable but with no in-app link found by the script (see §2 caveat — unverified whether it's linked from within `InventoryCommandPage` itself, which the script can't scan).

## 4. Endpoints: existence checked; "real data vs. stub" only spot-checked

Ground rules disallow starting a server or making live calls beyond the one Supabase SELECT set. What was checked by reading source:

- `grep`'d every `*.controller.ts` and `*.service.ts` for `TODO`, `not implemented`, `NotImplementedException`: **1 controller** (`procurement/receiving.controller.ts`) and **3 services** (`one-tap-actions.service.ts`, `pos-hub/catalog-matcher.service.ts`, `weather/weather-prefetch.service.ts`) carry a `TODO`. This is a shallow lexical check, not a stub audit — a hollow 200 that silently returns `[]` or a hardcoded object without a `TODO` comment would not be caught by this grep. **Not checked**: whether any endpoint returns fixture/mock data outside these four files. That needs either live calls against a seeded environment or a deeper per-controller read, which the ground rules' scope (no server, heavy-command budget already spent on vitest) didn't leave room for in this pass.
- All 689 regenerated endpoints exist as real files with real bodies (the script only counts a match on an actual `@Get/@Post/...` decorator in a real controller file — it cannot fabricate a hit), so "endpoint exists" is solid; "endpoint returns real, non-hollow data" is **not** verified beyond the TODO grep above.
