### C-01 · `extras=` typo in `sentry_sdk.capture_message`

**File:** `services/agent-orchestrator/tests/e2e/conftest_prod.py` (Plan 25-02)
**Where:** `teardown_e2e_records` fixture, Step 3 "Report orphans to Sentry"

```python
# WRONG — sentry_sdk has no `extras` parameter
sentry_sdk.capture_message(
    "E2E teardown: orphaned records could not be deleted",
    level="warning",
    tags={"e2e-orphan": "true"},
    extras={"orphaned_records": failed_deletes},   # <-- BUG
)
```

**Problem:** The correct sentry_sdk API keyword is `extra=` (no trailing `s`). Depending on
sentry_sdk version, `extras=` either silently drops the data or raises `TypeError: unexpected
keyword argument 'extras'`. Either way, orphaned record details are never attached to the
Sentry event.

**Fix:**
```python
extra={"orphaned_records": failed_deletes},   # singular
```

### C-02 · `asyncio.get_event_loop().time()` inside coroutines — broken in Python 3.10+

**Files:**
- `wave_c_agent_triggers.py` — `check_agent_still_healthy()` (Plan 25-04)
- `wave_d_toast_pipeline.py` — `poll_supabase_for_webhook_record()` (Plan 25-04)
- `wave_e_gmail_pipeline.py` — `poll_notification_delivery()` (Plan 25-05)
- `wave_g_calendar.py` — `poll_for_reminder_scheduled()` (Plan 25-05)

All four polling loops use this pattern:
```python
deadline = asyncio.get_event_loop().time() + timeout_seconds
while asyncio.get_event_loop().time() < deadline:
    ...
    await asyncio.sleep(N)
```

**Problem:** In Python 3.10+ (which Railway uses), calling `asyncio.get_event_loop()` from
inside a running coroutine emits `DeprecationWarning: There is no current event loop`. In
Python 3.12+ it raises `RuntimeError` in some configurations. The Railway Python runtime is
3.11; the GitHub Actions CI uses `python-version: '3.11'`. At 3.11 it's a DeprecationWarning
that won't fail tests — but it _will_ fail with stricter asyncio modes and will definitely
break if either runtime is bumped to 3.12.

**Fix:** Replace `asyncio.get_event_loop()` with `asyncio.get_running_loop()` everywhere
inside coroutines. This is the correct API when you're already inside an async function.

```python
# Before
deadline = asyncio.get_event_loop().time() + timeout_seconds
while asyncio.get_event_loop().time() < deadline:

# After
loop = asyncio.get_running_loop()
deadline = loop.time() + timeout_seconds
while loop.time() < deadline:
```

Apply to all 4 polling functions across wave_c, wave_d, wave_e, wave_g.

Also applies to `check_agent_still_healthy` in `wave_c_agent_triggers.py`:
```python
# current
deadline = asyncio.get_event_loop().time() + 5.0
async with httpx.AsyncClient(base_url=base_url, headers=admin_headers) as client:
    while asyncio.get_event_loop().time() < deadline:
```

### H-01 · Wave C creates 9 separate RabbitMQ connections — CloudAMQP free tier will exhaust

**File:** `wave_c_agent_triggers.py` (Plan 25-04)

The `test_agent_survives_test_message` test is parametrized with all 9 agent names. Each
test invocation calls `publish_test_message()` which opens a **new** `aio_pika.connect_robust`
connection:

```python
async def publish_test_message(rabbitmq_url, exchange_name, routing_key, payload):
    connection = await aio_pika.connect_robust(rabbitmq_url, timeout=10)  # new conn per call
    async with connection:
        ...
```

When this wave runs in CI under `pytest -n 2` (parallel with Wave B), up to 9 connections
open near-simultaneously. CloudAMQP's free tier allows **5 concurrent connections** by
default. Tests will start failing with "Connection refused" or "max connections reached"
errors at the 6th agent — but `pytest.skip()` is only triggered if the env var is missing,
not on connection errors:

```python
except Exception as exc:
    pytest.skip(f"Could not publish to RabbitMQ for {agent_name}: {exc}...")
```

So tests 6–9 would be silently skipped, masking the real issue.

**Fix:** Reuse a single connection across all 9 parametrized tests by using a session-scoped
fixture for the connection, or by opening the connection once in the test class and publishing
all 9 messages in a single session.

```python
@pytest.fixture(scope="session")
async def rabbitmq_connection(rabbitmq_url):
    """Single shared RabbitMQ connection for all Wave C tests."""
    connection = await aio_pika.connect_robust(rabbitmq_url, timeout=10)
    yield connection
    await connection.close()
```

Then pass `rabbitmq_connection` to the test and publish via `channel = await connection.channel()`.

### H-02 · `E2E_TABLES` teardown list is incomplete — agent side-writes not covered

**File:** `conftest_prod.py` (Plan 25-02)

The tag-based sweep in `teardown_e2e_records` only deletes from:
```python
E2E_TABLES = [
    "inventory_stock",
    "notification_deliveries",
    "order_interactions",
    "calendar_events",
    "pos_webhook_logs",
    "master_wine_library_submissions",
]
```

**Problem:** Agents write to more tables than this list covers. Wave D's Toast webhook causes
POSIntegrationAgent to update `inventory_stock` AND potentially write to `inventory_transactions`
or `audit_logs`. NotificationAgent (Wave E) may write to both `notification_deliveries` AND
`notification_events` or `notification_queue`. If those side-write tables aren't in `E2E_TABLES`,
orphan rows accumulate silently in production with `restaurant_id = 'e2e-test-restaurant'`.

The teardown step catches exceptions and reports to Sentry — but only for tables it
**knows about**. Unknown tables never get swept.

**Fix:** Before Phase 25 execution, audit each agent's `services/agent-orchestrator/agents/*.py`
to enumerate all tables each agent writes to. Add every table that could receive `e2e-test-restaurant`
data to `E2E_TABLES`. At minimum, verify `inventory_transactions`, `order_events`, and
`notification_queue` are covered or explicitly confirmed absent.

### M-02 · Wave BC combined XML — B vs C failures indistinguishable in cascading report

**File:** `cascading_report.py` (Plan 25-07)

Waves B and C run together with `pytest -n 2 wave_b_agent_health.py wave_c_agent_triggers.py`
producing a **single** `wave_bc.xml`. The cascading report handles this with:
```python
bc = wave_results.get("BC", {})
if bc.get("status") == "failed":
    # Cannot determine which of B vs C failed from combined XML — mark both
    wave_results["B"] = {"status": "failed", "from_bc": True, **bc}
    wave_results["C"] = {"status": "failed", "from_bc": True, **bc}
```

**Problem:** If only Wave B fails (e.g., 1 unhealthy agent) while Wave C passes, the cascading
report marks **both** B and C as failed. This triggers the "Waves A+B+C failed" suggested fix
(restart everything) instead of the more targeted "Wave B: check agent health" fix. The root
cause analysis loses precision exactly when precision matters most.

**Fix:** Run Wave B and Wave C as separate steps with separate JUnit XML files, then
run them in parallel in a matrix job or via `pytest-xdist` per-file. This preserves
individual wave attribution:
```yaml
- name: Wave B — Agent Health
  run: pytest tests/e2e/wave_b_agent_health.py --junitxml=test-results/wave_b.xml || true

- name: Wave C — RabbitMQ Triggers
  run: pytest tests/e2e/wave_c_agent_triggers.py --junitxml=test-results/wave_c.xml || true
```
Both steps can still run concurrently in CI using a matrix job or background process.

### M-03 · Wave F JUnit XML copy silently ignores missing file — Playwright failures masked

**File:** `.github/workflows/e2e-prod.yml` (Plan 25-07)

```yaml
- name: Copy Playwright JUnit XML to root test-results
  run: cp apps/web/test-results/wave_f.xml test-results/wave_f.xml 2>/dev/null || true
```

If Playwright fails to start at all (e.g., E2E_BASE_URL missing, `playwright install` failed),
`apps/web/test-results/wave_f.xml` won't exist. The `|| true` silently swallows the error.
The cascading report then marks Wave F as `"missing"` status — but "missing" looks the same
as "skipped by choice." The deploy gate step only checks for `failures="..."` in XML, so a
completely missing Wave F never triggers a deploy gate alert.

**Fix:** Use a separate `if: always()` check after the Playwright step:
```yaml
- name: Validate Wave F output
  if: always()
  run: |
    if [ ! -f "apps/web/test-results/wave_f.xml" ]; then
      echo "::warning::Wave F JUnit XML missing — Playwright may have crashed entirely"
      # Create a synthetic failure XML so cascading_report counts it as failed
      cat > test-results/wave_f.xml << 'EOF'
      <?xml version="1.0"?><testsuite name="wave_f" tests="1" failures="1">
      <testcase name="wave_f_setup"><failure>Wave F XML missing — Playwright crashed</failure></testcase>
      </testsuite>
      EOF
    fi
```

### M-04 · Wave G's 30s skip behavior may mask real CalendarAgent regression

**File:** `wave_g_calendar.py` (Plan 25-05)

```python
if not scheduled:
    pytest.skip(
        f"CalendarAgent did not schedule T-7 reminder for '{E2E_CAL_EVENT_ID}' "
        "within 30s. This may be a timing issue (scan interval > 30s). ..."
    )
```

**Problem:** A `pytest.skip` is used when `poll_for_reminder_scheduled` returns `False`.
In the cascading report and GitHub Actions summary, skipped tests show as neutral (⚠️), not
failures. If CalendarAgent stops working entirely (crashes, DB schema change), Wave G will
permanently skip rather than fail — meaning the nightly deploy gate never fires for a broken
calendar pipeline. The skip rationale is valid for a slow scan interval, but it hides
genuine failures.

**Fix:** Convert the skip to an `xfail` with a reason, or add a minimum-viable assertion
before the skip. At minimum, assert that the `calendar_events` row was **written successfully**
(test the Supabase write, not the agent processing), then skip only the scheduling assertion:

```python
# Verify the upsert itself succeeded (this MUST pass — not a timing issue)
result = prod_supabase.table(CALENDAR_EVENTS_TABLE).select("id").eq("id", E2E_CAL_EVENT_ID).execute()
assert result.data, f"Calendar event '{E2E_CAL_EVENT_ID}' not found in Supabase — upsert failed"

# Then skip only the CalendarAgent processing assertion if it times out
if not scheduled:
    pytest.skip("CalendarAgent scan interval > 30s — scheduling assertion skipped")
```

This ensures a broken Supabase connection or table schema issue always fails, while
a slow CalendarAgent scan still skips cleanly.

### L-01 · YAML inline Python in e2e-prod.yml Sentry step lacks `sentry_sdk.flush()`

**File:** `.github/workflows/e2e-prod.yml` (Plan 25-07)

The deploy-gate Sentry alert step initializes sentry_sdk inline:
```yaml
python - <<'EOF'
import os, sentry_sdk
dsn = os.environ.get("SENTRY_DSN")
if dsn:
    sentry_sdk.init(dsn=dsn, traces_sample_rate=0.0)
    sentry_sdk.capture_message(...)
    print("Sentry deploy-gate alert fired")
EOF
```

**Problem:** Short-lived Python processes need `sentry_sdk.flush()` after `capture_message`
to ensure the event is actually sent before the process exits. Without it, the event may be
queued but dropped at process exit.

**Fix:** Add `sentry_sdk.flush(2)` after `capture_message`:
```python
sentry_sdk.capture_message(...)
sentry_sdk.flush(2)   # wait up to 2s for the event to be transmitted
```

### L-02 · `asyncio_mode` compatibility — wave tests need `pytest-asyncio >= 0.23` assertion

**File:** `requirements.test.txt` (Plan 25-01)

The wave test files use session-scoped async fixtures (`prod_jwt`, `teardown_e2e_records`)
and async test methods inside classes. These require `pytest-asyncio >= 0.21` with
`asyncio_mode = auto`. The existing `services/agent-orchestrator/pytest.ini` has this set,
but `requirements.test.txt` only pins `pytest-xdist>=3.5.0` without pinning `pytest-asyncio`.

If CI resolves to `pytest-asyncio < 0.21`, session-scoped async fixtures will silently fail
(they'll be treated as sync and return coroutine objects instead of resolved values).

**Fix:** Add an explicit version pin to `requirements.test.txt`:
```
pytest-asyncio>=0.23.0
```
This matches the version already in `requirements.prod.txt` (assuming it's there) and
guarantees `asyncio_mode = auto` + session-scoped async fixture support.
