# Phase 26: Multi-Tenant Onboarding & Restaurant Hierarchy — CONTEXT

Created: 2026-05-06
Status: complete (UI polished 2026-05-09)

---

## Problem Being Solved

Current registration is broken for new users because:
1. The Register form requires an existing `restaurantId` — no path exists to CREATE a new restaurant
2. New restaurant owners have no self-service onboarding — they must get an ID "from admin"
3. No multi-location support — an owner with 5 restaurants can only manage one at a time
4. No branch/location concept — no way to group locations under one organization

---

## Decisions

### D-01: Two-Path Registration
Registration splits at the first screen:
- **Path A — Join Existing Restaurant**: user enters an invite code (not a UUID — human-friendly 8-char alphanumeric). Invite codes are generated by restaurant owners/admins.
- **Path B — Create New Restaurant**: user fills restaurant name, address, cuisine type → system creates restaurant row → user is assigned `owner` role automatically.
No "enter restaurant ID directly" field — it was the source of the failure.

### D-02: Password Security
Supabase handles bcrypt hashing server-side. Frontend sends plain text over HTTPS. No client-side hashing needed — this is correct and standard.

### D-03: Restaurant Hierarchy / Branch Support
New DB concept: `organizations` table (the brand/group) with one-to-many `restaurants` (locations/branches).
- Owner creates an organization (e.g., "Le Bernardin Group")
- Each location is a `restaurant` row linked to the organization
- Owner can switch active branch from a top nav selector
- All agents and data are scoped to `restaurant_id` — organization is for grouping only

### D-04: Invite Code Flow
- Owner generates an invite code from Settings → Team → Invite
- Code is 8 chars, alphanumeric, expires in 7 days
- Joining user's role defaults to `manager` (owner can change after)
- Codes are single-use (consumed on first registration)

### D-05: Email Verification
Supabase's built-in email verification is enabled. Users who register via Path B must verify before accessing the dashboard. Path A (invite code) skips verification since the owner vouched for them.

### D-06: Multi-Branch Context Switcher
After login, users with access to multiple branches see a branch picker in the top nav.
`AuthContext.availableRestaurants` already exists — it just needs to be populated from the `organization_members` table instead of hardcoded to one restaurant.

### D-07: Frontend-Only vs Full-Stack
This phase touches:
- Frontend: Register.tsx (two-path UI), Settings page (invite generation, branch management)
- Backend (NestJS API gateway): new auth endpoints for invite creation/consumption, organization creation
- Database (Supabase): new `organizations` and `organization_invites` tables, update `users` table

---

## User Stories

1. **New restaurant owner** visits /register → selects "Create New Restaurant" → fills name/address → gets dashboard access immediately
2. **Staff member** receives invite link from owner → visits /register → selects "Join Existing" → enters invite code → gets dashboard access
3. **Multi-location owner** (5 restaurants) → creates organization → adds 4 branches from Settings → Locations → switches between branches from top nav
4. **Admin** can see all locations under one organization from a unified dashboard
