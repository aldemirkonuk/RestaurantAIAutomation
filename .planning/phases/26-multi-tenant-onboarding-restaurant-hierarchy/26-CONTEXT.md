# Phase 26: Multi-Tenant Onboarding & Restaurant Hierarchy — Context

**Gathered:** 2026-05-06
**Status:** Ready for planning
**Source:** User decisions (discuss-phase)

<domain>
## Phase Boundary

Fix broken registration and introduce multi-tenant restaurant hierarchy. After this phase:
- New owners can self-register and create their restaurant without an admin
- Staff can join via human-friendly invite codes (not UUIDs)
- Owners with multiple locations can switch branches from the top nav
- All agents and data stay scoped to `restaurant_id` — organization is a grouping layer only

This is a full-stack phase: DB migrations (Supabase) + API endpoints (NestJS) + frontend (React).

</domain>

<decisions>
## Implementation Decisions

### D-01: Two-Path Registration
Registration splits at the first screen:
- **Path A — Join Existing Restaurant**: user enters an invite code (not a UUID — human-friendly 8-char alphanumeric). Invite codes are generated by restaurant owners/admins.
- **Path B — Create New Restaurant**: user fills restaurant name, address, cuisine type → system creates restaurant row + organization row → user is assigned `owner` role automatically.

No "enter restaurant ID directly" field — it was the root cause of the broken registration.

**UX mandate**: The split screen must make both paths equally obvious at a glance. No small radio buttons — use large card-style path selectors with iconography and one-line explanations.

### D-02: Password Security
Supabase handles bcrypt hashing server-side. Frontend sends plain text over HTTPS (TLS). No client-side hashing. This is correct and standard.

### D-03: Restaurant Hierarchy / Branch Support
New DB concept: `organizations` table (the brand/group) → one-to-many `restaurants` (locations/branches).
- Owner creates an organization (e.g., "Le Bernardin Group") — auto-created when they create their first restaurant
- Each location is a `restaurant` row linked to the `organization_id`
- Owner can switch active branch from a top nav selector
- All agents, inventory, and data scoped to `restaurant_id` — organization is for grouping only
- Future: cross-restaurant reporting (out of scope for Phase 26)

### D-04: Invite Code Flow
- Owner generates invite code from Settings → Team → Invite Members
- Code: 8-char alphanumeric (uppercase, no ambiguous chars like 0/O, 1/I), expires 7 days
- Sharing: show the code AND a copy-able invite URL (`/register?invite=XXXXXXXX`) — link is easier to share than a code
- Joining user's role defaults to `manager` (owner can change in Settings → Team after join)
- Codes are single-use (marked `used_at` on first consumption)
- **UX mandate**: Show invitee a preview card ("You've been invited to join The Oak Room by Jane Smith") before they confirm — reduces surprise and drop-off

### D-05: Email Verification
Supabase built-in email verification enabled for Path B (new restaurant creation). Must verify before accessing dashboard.
- Path A (invite code): skips verification — owner vouched for them, immediate access
- **UX mandate**: Verification pending state must NOT leave the user stranded. Show a clear "Check your email" holding page with a resend button (rate-limited to 1/min)

### D-06: Multi-Branch Context Switcher
After login, users with ≥2 branches see a branch picker in the top nav.
- `AuthContext.availableRestaurants` exists but is currently hardcoded to a single restaurant — wire it from `organization_members` table
- **UX mandate**: Branch switcher must show restaurant name + city (not just ID). Last selected branch persists in `localStorage`. Switching branch reloads data without full page refresh.

### D-07: Full-Stack Scope
Files touched this phase:
- **Frontend**: `Register.tsx` (two-path wizard), `Settings.tsx` (invite generation + branch management), `AuthContext.tsx` (multi-restaurant from org membership), top nav branch switcher component
- **Backend (NestJS api-gateway)**: new endpoints — `POST /auth/register/restaurant` (create org + restaurant + user), `POST /auth/invite` (generate code), `POST /auth/join` (consume invite), `GET /auth/invite/:code` (preview invite before joining), `GET /organizations/branches` (list branches for switcher)
- **Database (Supabase)**: `organizations`, `organization_members`, `organization_invites` tables + RLS policies

### D-08: UX Elevation — Key Principles
The current register form is a dead end. Every new user hits it and gets confused. This phase must feel **delightful and frictionless**:
1. **Progressive disclosure**: only show the minimum fields needed at each step — wizard pattern, not one big form
2. **Inline validation**: validate invite codes in real-time (debounced 400ms) — show "✓ Valid — The Oak Room" or "✗ Code expired" before form submit
3. **Smart defaults**: auto-detect timezone from `Intl.DateTimeFormat().resolvedOptions()` for the restaurant record
4. **Copy-able invite link**: owners should never have to read out an 8-char code. One click copies the full URL.
5. **Error recovery**: expired invite → clear CTA to contact the owner. Invalid code → suggest "check for typos — codes are uppercase".
6. **Branch switcher loading state**: never show stale data during branch switch — use optimistic UI with a subtle spinner

### D-09: RLS Security
Every new table gets Row Level Security:
- `organizations`: owner can read/update their own org
- `organization_members`: members can read their own memberships; owner can read all members of their org
- `organization_invites`: only org owner/admins can create; anyone can read (to validate a code); consumed codes immutable
- Existing `restaurants` table: scoped by `organization_id` for multi-branch queries

### Claude's Discretion
- Choice of invite code generation algorithm (crypto-random, server-side)
- Exact animation/transition details for wizard steps (use existing framer-motion patterns from Login.tsx)
- Whether to add an Onboarding checklist after restaurant creation (like "Add your first wine", "Invite a team member") — strongly recommended as empty state UX but implementation details deferred to executor

</decisions>

<specifics>
## Specific Ideas

### Registration wizard step structure (Path B — Create New Restaurant)
Step 1: Your account (name, email, password, confirm password)
Step 2: Your restaurant (name, address line, city, cuisine type dropdown, phone)
Step 3: Email verification holding page (with resend button)
→ Auto-redirect to dashboard on verification

### Registration wizard step structure (Path A — Join Existing)
Step 1: Enter invite code OR paste invite URL (auto-extract code from URL param)
Step 2: Preview card "You've been invited to join [Restaurant Name] by [Inviter Name]" + your account fields (name, email, password, confirm)
Step 3: Immediate dashboard redirect (no email verification for invite path)

### Invite code UX in Settings
- Settings → Team section: member list + "Invite Member" button
- Invite dialog: shows generated code + copy button for full URL (`/register?invite=XXXXXXXX`)
- Pending invites list: shows invited email (optional), code, expires_at, status

### Branch switcher in top nav
- Only visible when `availableRestaurants.length > 1`
- Dropdown shows restaurant name + city for each branch
- Active branch highlighted with a checkmark
- "Manage Locations" link at bottom → Settings → Locations tab

### Inline invite code validation API
`GET /auth/invite/:code` → returns `{ valid: true, organization: "Le Bernardin", restaurant: "The Oak Room", inviter: "Jane Smith" }` or `{ valid: false, reason: "expired" | "used" | "not_found" }`

</specifics>
