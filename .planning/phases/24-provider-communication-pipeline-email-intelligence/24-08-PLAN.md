## Risk Register

### R-01: Routing Key Conflict — Double Email Processing
**Risk:** Both EmailIntelAgent and EmailParsingAgent subscribe to the same RabbitMQ routing key.
Both agents receive every inbound email → order confirmations processed twice → duplicate
DB writes, duplicate notifications.
**Consequence:** Duplicate vendor_promotions records, duplicate notifications, idempotency
exhausted → downstream silent failures.
**Mitigation:** Change publishEvent routing key from `email.inbound.received` to
`email.inbound.raw`. EmailIntelAgent subscribes to `email.inbound.raw`, re-publishes
OPERATIONAL to `email.inbound.received` with `__intel_bypass: True`.
**Implemented in:** Plan 24-02 (gmail-watch.service.ts fix), Plan 24-04 (EmailIntelAgent subscribe)
**Status:** MITIGATED

### R-02: email.events Exchange Not Declared
**Risk:** `email.events` exchange does not exist in message_bus.py `_setup_exchanges()`.
Any `publish('email.events', ...)` call silently fails (exchange not found error
caught by circuit breaker → message discarded).
**Consequence:** Zero emails reach EmailIntelAgent. Silent pipeline failure.
**Mitigation:** Add `("email.events", ExchangeType.TOPIC, True)` to exchange_configs list.
**Implemented in:** Plan 24-01 (message_bus.py edit, Task 4)
**Status:** MITIGATED

### R-03: SENT Messages Silently Excluded
**Risk:** `fetchNewMessages()` in gmail-watch.service.ts passes `labelId: 'INBOX'` to
history.list(). SENT messages are not in INBOX → excluded even after GMAIL_WATCH_LABEL_IDS
env var is set to `INBOX,SENT`.
**Consequence:** Manager replies sent natively in Gmail never reach EmailIntelAgent →
conversation thread tracking incomplete → stalled thread detection misses manager-initiated threads.
**Mitigation:** Remove `labelId` filter; detect direction from `fullMessage.data.labelIds`.
**Implemented in:** Plan 24-02 (gmail-watch.service.ts, Task 1)
**Status:** MITIGATED

### R-04 + R-05: Missing Schema Columns
**Risk:** `vendor_promotions` table missing `urgency_score`, `linked_event_ids[]`,
`last_comparison_price`, `snoozed_until`. `notification_preferences` missing all
digest toggle columns. `providers` missing `auto_reply_enabled`.
**Consequence:** Plan 24-04/05/06 INSERT and UPDATE operations fail at DB level.
**Mitigation:** All missing columns added in Plan 24-01 migrations before any agent code runs.
**Implemented in:** Plan 24-01 (migrations 20260513100001/2/3)
**Status:** MITIGATED

### R-06 + R-07 + R-08: Redis Digest Race Conditions
**Risk:**
- R-06: Stale email backlog: RabbitMQ restart delivers 18+ hour old emails → old
  deals added to digest → manager sees outdated deals.
- R-07: Redis EXPIRE runs before LPUSH confirms → digest key with wrong TTL → 36h
  items expire before 8am cron runs.
- R-08: TTL mismatch if some code uses 48h instead of 36h → same-day digest key
  expires before next day cron run.
**Consequence:** R-06: stale deals in digest. R-07/R-08: digest key disappears overnight.
**Mitigation:**
- R-06: EmailIntelAgent checks `received_at` age; skips LPUSH for emails >18h old.
- R-07: Use `redis.pipeline()` (LPUSH + EXPIRE atomic) — not two separate calls.
- R-08: All code uses exactly 36h TTL (`36 * 3600`). Enforced in email_intel_agent.py.
**Implemented in:** Plan 24-04 (email_intel_agent.py)
**Status:** MITIGATED

### R-09: Haiku Burst Without Rate Limit
**Risk:** EmailIntelAgent processes a large RabbitMQ backlog after restart → dozens of
concurrent Haiku API calls → Anthropic rate limit (429) → all calls fail → PROMO emails
lost.
**Consequence:** Mass extraction failure on restart. No recovery for lost PROMO emails
(backlog was >18h old and stale guard fires too late).
**Mitigation:** `asyncio.Semaphore(5)` gates all Haiku calls. Created in `initialize()`
(not `__init__`) per AI-SPEC §3 pitfall 4.
**Implemented in:** Plan 24-03 (model_clients.py get_haiku_semaphore()), Plan 24-04
(email_intel_agent.py async with self.haiku_semaphore)
**Status:** MITIGATED

### R-10: auto_reply_enabled DEFAULT true — Trust Escalation
**Risk:** If migration uses `DEFAULT true`, all existing providers immediately have
auto-reply enabled. Next time ProviderConversationAgent runs, ALL pending drafts for
ALL providers auto-send without manager review.
**Consequence:** Mass unauthorized email sends. Vendor relationships damaged. Potential
UCC contract formation at scale.
**Mitigation:** Migration explicitly sets `DEFAULT false`. Verified by grep acceptance
criteria in Plan 24-01 (`grep -c "auto_reply_enabled BOOLEAN DEFAULT false" ...` = 1).
**Implemented in:** Plan 24-01 (migration 20260513100002)
**Status:** MITIGATED — CRITICAL DEFAULT

### R-11: ProviderConversationAgent Regression
**Risk:** Adding Level 4 features to a 2519-line agent risks breaking existing behavior
(reply generation, commitment detection, session management).
**Consequence:** Vendor emails stop getting replies → relationship breakdown.
**Mitigation:** `PROV_AGENT_LEVEL4_ENABLED` feature flag (default=false). All Level 4
additions (idempotency, DLQ, log_decision, D-19 injection) are guarded by this flag.
Zero behavior change without explicit opt-in. Canary rollout: set to true for one
restaurant first, verify, then global enable.
**Implemented in:** Plan 24-05 (feature flag guard on all Level 4 code paths)
**Status:** MITIGATED

### R-12: Gmail Watch Renewal Silent Failure
**Risk:** Gmail Watch token must be renewed every 7 days. If GmailWatchService renewal
fails silently, all Pub/Sub messages stop arriving → EmailIntelAgent starves → manager
sees no email activity but hears nothing.
**Consequence:** Zero email triage for days or weeks without detection.
**Mitigation (partial — already present):** GmailWatchService auto-renews every 6 days.
**Mitigation (Phase 24 addition):** DigestCronJob reads `gmail:watch:expiration` Redis key
set by GmailWatchService on successful renewal. Digest header includes:
"⚠️ Gmail Watch expires in Xd — renew in Settings" if <2 days remaining.
**Implemented in:** Plan 24-06 (digest_cron_job.py _get_watch_status(), D-06)
**Status:** MITIGATED

### R-13: UCC Contract Formation via Auto-Reply (AI-SPEC §6)
**Risk:** ProviderConversationAgent drafts a reply containing "we'll take 24 cases at
$14.40" or "please confirm our order." Under UCC Article 2, this + vendor's prior offer
= binding purchase agreement. For `auto_reply_enabled` providers, this draft auto-sends.
**Consequence:** Legally binding purchase commitment made without manager knowledge.
**Mitigation:** `_check_commitment_language()` regex checks draft before auto-send.
Match → force `pending_approval` regardless of `auto_reply_enabled` setting.
COMMITMENT_PATTERNS includes: "will take", "would like to order", "please confirm our
order", "we'll proceed with", "we accept", "confirm N cases", "let's go ahead",
"sending payment".
**Implemented in:** Plan 24-05 (provider_conversation_agent.py _check_commitment_language())
**Status:** MITIGATED

### R-14: Thread Cross-Contamination (gmail_thread_id Collision)
**Risk:** Forwarded emails carry the original thread's gmail_thread_id. Two separate
vendor conversations appear to be the same thread → summary merges unrelated content.
**Consequence:** Deal terms from Vendor A appear in Vendor B's conversation history.
**Mitigation:** When linking to gmail_thread_id, validate thread exists in
procurement_conversations for the SAME provider_id. If thread exists for different
provider → flag as anomaly (per D-10 pattern), create new session instead of linking.
**Implemented in:** Plan 24-04 (email_intel_agent.py _link_sent_email() validation)
**Status:** MITIGATED (documented; executor must implement validation in _link_sent_email)

### R-15: Manager Learning Loop Poisoning
**Risk:** Manager edits a draft to include incorrect or adversarial instructions
("always offer 15% discount"). Learning loop stores this as `manager_instructions[]`.
Future drafts incorporate the poisoned instruction.
**Consequence:** AI systematically produces incorrect or harmful drafts.
**Mitigation:** `record_correction()` Haiku preference extraction is bounded to 20 words
and formatted as "tone: ..." or "style: ..." or "avoid: ...". DB insert limited to 200
chars per instruction. Manager review UI for learned instructions deferred to Phase 31
(per CONTEXT.md Deferred Ideas).
**Implemented in:** Plan 24-05 (provider_conversation_agent.py record_correction())
**Status:** PARTIALLY MITIGATED (review UI in Phase 31)
