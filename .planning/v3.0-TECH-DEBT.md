# v3.0 — Phase 44: v2.0 Carry-Forward & Debt Consolidation

Everything v2.0 left behind, as **one phase with 14 subphases**. Ordered by what
it costs to leave alone, not by which document it came from.

**Phase 23 (Gmail OAuth2) is dropped.** Outbound email keeps its working SMTP
app-password fallback. Note that 44.1's email-pipeline fix **survives that
decision** — the provider-agnostic Postmark webhook is already code-complete and
publishes `email.inbound.received`, so registering the consumers makes *that* path
work. Only the Gmail OAuth2 credential gate died.

## Three findings that appear in no prior planning document

Found by direct verification during this compile, not by reading docs:

1. **44.1a — `one-tap-actions` has no auth guard** and trusts a URL parameter.
2. **44.1b — wine-library duplicate-add silently loses stock** and announces the
   loss as a success to other pages.
3. **44.2a — five agents are registered and empty**, so the orchestrator reports
   them live.

All three are the same failure mode: **code that exists, is reachable, and does
nothing.** That is strictly worse than absent code, because absence is visible.
The v2.0 audit named this once (unregistered email agents) and it recurred five
more times.

## Track A — Live defects (do these first)

### 44.1 Auth and data-integrity defects

**44.1a — Close the `one-tap-actions` auth hole.** *(new)*
`apps/api-gateway/src/one-tap-actions/one-tap-actions.controller.ts:39` is
`@Controller("one-tap-actions")` with **no `@UseGuards`**; every route takes
`restaurantId` from the URL path, and `userId` is hardcoded `"system"` (TODOs at
:121, :174). The global TenantGuard deliberately returns `true` for
unauthenticated requests, so this is internet-reachable and writes for any tenant
named in the URL — identical to the ux-optimizer hole closed in v2.0.
→ Class-level `JwtAuthGuard`, identity from `@CurrentUser()`, test for 401.

**44.1b — Fix silent stock loss on duplicate-add.** *(new)*
`apps/web/src/data/inventoryData.ts` holds an in-memory `inventoryStore`; its four
mutators push, `console.log`, return (TODOs: "Call Supabase API to persist").
`AddToInventoryFromLibraryModal.tsx:302` calls `updateInventoryQuantity` on the
duplicate-add path **then dispatches `dispatchInventoryUpdate`** — other pages sync
to a number the database never received; a refresh loses it.
→ Route through `apply_stock_movement`, then delete the module (see 44.5).

**44.1c — Revive inbound email consumption.**
`EmailIntelAgent` and `EmailParsingAgent` are fully implemented and **absent from
`services/agent-orchestrator/core/orchestrator.py:141 _register_agent_classes()`**
(verified against the live registry). Also `EmailIntelAgent` subscribes to
`email.inbound.raw`, which has **zero publishers**; the real webhook emits
`email.inbound.received`.
→ Register both, fix the key, add one integration test that publishes the real key
and asserts a consumer ran.

**44.1d — `notifications` writes. ✅ RESOLVED, and the documented symptom was the
wrong one.**

The register said the bug was `status:'unread'` versus `is_read:False`. Reading the
live schema settled that instantly — `status` exists (varchar, default `'unread'`),
`is_read` **does not exist at all** — but the `is_read` call site had already been
corrected before this pass, so that mismatch was stale.

**The real defect was bigger and neither agent's fault was the field name.** The
table carries two generations of columns, and three of the originals are still NOT
NULL with no default: `recipient_id`, `notification_type`, `channels`. **Both**
agents omitted **all three**. Proven against the live database:

```
INSERT INTO notifications (restaurant_id, type, title, message, status, metadata) …
ERROR: 23502: null value in column "recipient_id" violates not-null constraint
```

So every agent notification was rejected, inside a `try/except` whose message read
"Notification insert failed (non-critical)". It was not non-critical — it was
total. Provider-communication notices and PROVINT-04 unknown-sender alerts reached
nobody, and the only trace was one log line. **A caught exception around a write
that always fails is indistinguishable from a feature nobody triggers** — the same
shape as 44.1a's swallowed 404 and 44.1b's phantom stock event.

Fixed by adding `core/notifications.py`, mirroring the api-gateway's
`persistForRestaurant` (which had already solved this, with a comment naming the
legacy columns): resolve the restaurant's members, fan out one row per member, fill
the legacy columns, truncate `title` to its column width, and return an insert
count so "reached nobody" is distinguishable from "written". Both agents now route
through it.

Verified end to end: the fixed shape inserts against the live table, and the probe
row was removed. 9 new tests in `tests/test_agent_notifications.py` assert every
NOT NULL column is populated, so a future omission fails in CI rather than in
production silence.

### 44.2 Hollow features that report success

**44.2a — Five empty agents. ✅ RESOLVED, and my original claim here was wrong.**

The five are real stubs — `ghost_inventory_agent` (37 lines), `auto_pilot_agent`
(36), `negotiation_playbook_agent` (36), `shrinkage_detective_agent` (35),
`compliance_agent` (35) — each logging the event and returning.

**But I claimed they were live and consuming events, and they were not.** All five
are `AgentTier.OPTIONAL`, and `is_enabled()` requires
`AGENT_<NAME>_ENABLED`, defaulting to False. `_create_lazy_proxies()` skips them,
so they never instantiate and never subscribe. Health checks did not pass for them
and logs did not show events received. The only true part was that
`registered_count` counted them, so "Registered 20 agent classes" overstated what
was running.

**The real defect was the opposite of hollow-and-running: the gate was
unreachable.** `_build_feature_flags()` populated only three `FEATURE_*` keys and
never any `AGENT_<NAME>_ENABLED` key — so the switch the OPTIONAL tier documented
was one nothing read. `AGENT_GHOST_INVENTORY_AGENT_ENABLED=true` in the
environment did precisely nothing, silently.

Fixed: the flag builder now sweeps `os.environ` for `AGENT_*_ENABLED` (parsing the
string, since a truthiness check reads `"false"` as enabled); the five declare
`IS_STUB = True` and the orchestrator **refuses to start a stub even when its flag
is on** — now that the gate works, an operator could otherwise switch one on and
get an agent that subscribes to real events and discards them, which does look
healthy from every dashboard; and boot logging reports enabled-vs-gated rather
than a single count.

`auto_pilot_agent` is deliberately left unimplemented: its TODOs are "evaluate
`auto_pilot_rules`" and "create procurement orders", and autonomy stays
human-gated until the benchmark numbers are met. An empty auto-pilot that refuses
to boot is the correct state, not a gap.

Covered by 20 tests in `tests/test_agent_registry_gating.py`, including one that
fails if a future agent is OPTIONAL *and* implemented — the moment to revisit
whether the marker or the tier is wrong.

**44.2b — Settle the `ReportingAgent` contradiction.**
Phase 21 criterion #2 claims `stock.events → NotificationAgent + ReportingAgent`;
`ReportingAgent` only subscribes to `reporting.events`. The real golden path is
`POSIntegrationAgent → BufferManager → InventoryEngine`, not the ROADMAP's
simplified chain.
→ Subscribe it, or correct the criterion and topology. Prefer correcting the doc
if scheduled reports are the intent — but pick one.

### 44.3 Schema truth

**44.3a — Capture 13 ghost tables** (live in DB, in no migration):
`_migrations`, `conversation_embeddings`, `enrichment_queue`,

calendar event are split across `approveOrder()` and `approveDraft()` with no

"atomically" wording.

**44.3c — Two informational schema gaps.** `pos_webhook_logs` missing
`restaurant_id` (complicates synthetic-tenant teardown); `scheduled_reminders`
exists but CalendarAgent never writes it.

**44.3d — Adopt the rule: read the live schema, not migrations.** v2.0 produced
three wrong assumptions from migration files: `procurement_order_items` in no

`procurement_order_items.total_bottles` is `GENERATED ALWAYS` and rejects explicit
inserts — mentioned nowhere. `npm run db:drift` checks state.

## CI — `Lint TypeScript` is red for **two** errors, not one; turbo hides the second — added 2026-08-24

`ci.yml`'s `lint-typescript` runs `pnpm run lint` → `turbo run lint` without
`--continue`. When `@wineops/web#lint` fails, turbo stops scheduling and kills the
in-flight tasks, so CI's log ends at `Tasks: 3 successful, 5 total` and only ever
showed the web error. `@wineops/api-gateway#lint` had already started (`cache miss,
executing`) and was cut off mid-run — its own error never reached the log.

1. **`apps/web/src/lib/devAuthBypass.ts:43` — fixed** on `fix/web-lint-unused-disable`.
   `Unused eslint-disable directive`. `no-console` is `'off'` repo-wide
   (`.eslintrc.cjs:33`, no `allow` list, no apps/web override), so the directive was
   dead; only apps/web's lint script passes `--report-unused-disable-directives`
   (`apps/web/package.json:12`), which is why only this one was reported. The other
   four `no-console` directives in the repo (`apps/api-gateway/src/openapi.ts` ×2,
   `apps/mobile/src/guidance/analytics.ts`, `apps/mobile/src/lib/mmkv.ts`) are equally
   dead but unreported. Deleting was right — turning `no-console` on for apps/web
   would hit 243 call sites and is a policy decision, not a lint fix.

2. **`apps/api-gateway/src/wines/wine-submissions.service.ts:78` — fixed** on the
   same branch. `no-misleading-character-class` (error, from `eslint:recommended`):
   *Unexpected combined character in character class*, on the `DIACRITICS` regex.
   Verified pre-existing on pristine `main` source, not an artefact of that script's
   `--fix`. Cause: adjacent combining-mark **ranges** — `ͯ` (end of range 1) sits next
   to `᪰` (start of range 2) in pattern order and the pair segments as one grapheme.
   Probed on ESLint 8.57.1: each range alone is clean, any two adjacent ones error;
   `\u`-escaping alone does **not** silence it (the `allowEscape` option is ESLint
   9.7+), and neither does the `u` flag. Rewritten as `\u`-escaped, `|`-alternated
   single-range classes in the original order — which also ends the "unreadable
   source" problem the rule is actually about. Equivalence proven, not assumed: the
   old and new patterns were compared over every code point U+0000–U+FFFF (both are
   non-`u` regexes, so that is the whole domain) — 364 code points matched, 0
   disagreements — and `wine-submissions.service.spec.ts`, which asserts parity with
   `public.wine_normalize_text`, is green (27 passed; the 11-test integration spec
   beside it skips without DB credentials).

**After both:** `pnpm run lint` is 0 errors across all 5 packages (198 warnings —
131 web + 67 api-gateway — all pre-existing and untouched).
