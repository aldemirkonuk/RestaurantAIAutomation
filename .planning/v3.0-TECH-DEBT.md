> **Corrected 2026-08-25 (ADR 0018).** This is the **defect register**, not the plan
> of record. Phase 44 is not the current milestone and not the next action — the
> current milestone is **P2 — Web complete + deploy**. See `.planning/STATE.md`.
> Compiled 2026-07-28; entries below are dated as of that compile unless annotated.

Everything v2.0 left behind, as **one phase with 14 subphases**. Ordered by what
it costs to leave alone, not by which document it came from.

**Phase 23 (Gmail OAuth2) is dropped.** Outbound email keeps its working SMTP
app-password fallback. Note that 44.1's email-pipeline fix **survives that

## Three findings that appear in no prior planning document

Found by direct verification during this compile, not by reading docs:

1. **44.1a — `one-tap-actions` has no auth guard** and trusts a URL parameter.
2. **44.1b — wine-library duplicate-add silently loses stock** and announces the
   loss as a success to other pages.
3. **44.2a — five agents are registered and empty**, so the orchestrator reports
   them live.

All three are the same failure mode: **code that exists, is reachable, and does
nothing.** That is strictly worse than absent code, because absence is visible.
The v2.0 audit named this once (unregistered email agents) and it recurred five
more times.

**44.1d — `notifications` writes. ✅ RESOLVED, and the documented symptom was the
wrong one.**

The register said the bug was `status:'unread'` versus `is_read:False`. Reading the
live schema settled that instantly — `status` exists (varchar, default `'unread'`),
`is_read` **does not exist at all** — but the `is_read` call site had already been
corrected before this pass, so that mismatch was stale.

**The real defect was bigger and neither agent's fault was the field name.** The
table carries two generations of columns, and three of the originals are still NOT
NULL with no default: `recipient_id`, `notification_type`, `channels`. **Both**
agents omitted **all three**. Proven against the live database:

```
INSERT INTO notifications (restaurant_id, type, title, message, status, metadata) …
ERROR: 23502: null value in column "recipient_id" violates not-null constraint
```

So every agent notification was rejected, inside a `try/except` whose message read
"Notification insert failed (non-critical)". It was not non-critical — it was
total. Provider-communication notices and PROVINT-04 unknown-sender alerts reached
nobody, and the only trace was one log line. **A caught exception around a write
that always fails is indistinguishable from a feature nobody triggers** — the same
shape as 44.1a's swallowed 404 and 44.1b's phantom stock event.

Fixed by adding `core/notifications.py`, mirroring the api-gateway's
`persistForRestaurant` (which had already solved this, with a comment naming the
legacy columns): resolve the restaurant's members, fan out one row per member, fill
the legacy columns, truncate `title` to its column width, and return an insert
count so "reached nobody" is distinguishable from "written". Both agents now route
through it.

Verified end to end: the fixed shape inserts against the live table, and the probe
row was removed. 9 new tests in `tests/test_agent_notifications.py` assert every
NOT NULL column is populated, so a future omission fails in CI rather than in
production silence.

**44.1e — Saved sommelier conversations never load. Same shape as OD-45, different
cause.** *(new — found by the OD-72 RLS census, 2026-08-25)*

`apps/web/src/pages/SommelierAI.tsx:91` renders saved conversations from
`useSommelierQueries.ts:26`, which queries `sommelier_conversations` on the browser's
anon-key Supabase client. The table is **not** one of OD-45's 142 naked-RLS tables —
it has two policies — and it returns `[]` anyway. Its policy is
`USING (user_id = auth.uid())`, and **this product does not use Supabase Auth**:
`AuthContext.tsx` holds a gateway-issued JWT in `localStorage` and never hands the
Supabase client a session, so `auth.uid()` is permanently NULL and the policy can
never match. Verified against production: `GET /rest/v1/sommelier_conversations`
with the real anon key returns `200 []`.

The failure is then swallowed twice — RLS denial is not an error, and
`useSommelierQueries.ts:31-34` catches any error, logs
`"sommelier_conversations table may not exist yet"` and returns `[]`. The write path
fails loudly instead: `upsertConversation` violates the `WITH CHECK`, so "save"
throws while "load" lies.

→ Route through the gateway, as ADR 0012 did for reports. This is the second and
last live anon-key read in the product; closing it empties `lib/supabase.ts` of
callers. **52 of 73 policies in the database reference `auth.*`** and are equally
unsatisfiable from this browser — see [OD-72](decisions/OD-72-rls-census.md) §3.
Founder call is [OD-72](decisions/OPEN-DECISIONS.md).

**44.1f — Adding a location locked the owner out of it. ✅ FIXED 2026-09-03.**
*(measured on a local gateway on `main` `47f971de`, real call)*

An owner added a location through the product's own door —
`POST /organizations/locations`
(`apps/api-gateway/src/organizations/organizations.controller.ts:119` →
`organizations.service.ts` `createLocation`). The `restaurants` row was written
(slug `sim-meyhouse-9ef3dde7`, org set) and **no `user_restaurant_access` row was**,
so the very next call on that restaurant —
`GET /restaurants/:id/operating-hours`, which goes through
`MembersService.assertMembership` (`restaurants/members.service.ts:25`) —
answered `403 "Access denied to this restaurant"`. `assertMembership` reads a URA
row and falls back only to `users.restaurant_id`, which still names the creator's
ORIGINAL restaurant; there is no org-level path. `registerRestaurant`
(`auth/auth.service.ts:759`) has always written that row for the founding owner —
the SECOND door into `restaurants` did not, so the two creation paths produced
differently-usable restaurants.

→ Fixed: `createLocation` now inserts `user_restaurant_access {role: "owner",
is_active: true}` for the creator after the restaurant insert, and on an insert
failure deletes the just-created restaurant and throws — the same rollback
discipline `registerRestaurant`'s catch block has, because a restaurant nobody can
reach is worse than no restaurant (it still occupies its slug and lists in the org).
Spec: `organizations/create-location-grants-access.spec.ts` (both assertions fail on
the pre-fix tree).

**Second finding, NOT fixed — the two authorisation paths disagree.**
`AuthService.switchRestaurant` (`auth/auth.service.ts:446`) *does* gate, but on a
weaker rule: URA row **or**, failing that, an org-level fallback — the target
restaurant merely has to sit in one of the caller's organisations (:475-511). That
fallback is why `POST /auth/switch-restaurant` happily minted a session for the
locked-out location while `assertMembership` refused every request made with it.
So the platform has two membership answers for the same pair: **org-level for
minting a session, row-level for using it.** The fix above removes the symptom for
newly-created locations, not the disagreement. Deliberately left open: the fallback
also carries legacy users who have no URA row at all, so deleting it is a data
question (backfill URA rows for existing org members) and not a one-line check —
worth a decision record rather than a drive-by edit.

**44.2z — Retired Gemini model ids across the orchestrator. ⚠️ PARTIALLY FIXED

Two sites are fixed. `EmailIntelAgent` was failing all 3 retries and dead-lettering

quiet kind: retired model *and* a missing `genai.configure()`, both swallowed by a

**27 further references remain across 11 live non-test files** — see OD-57 for the

fabricates 3 dated rows.

Two real spend-ledger defects were found while pricing the replacement, and both
are fixed: `_RATES_PER_M` priced `gemini-2.5-flash` **8.3x under** its real output
rate, and all 18 Gemini call sites dropped `thoughts_token_count`, which Google
bills at the output rate (measured 598 billed vs 113 logged). Spend figures will
rise sharply as a result — that is the correction landing, not a regression. A
third change, longest-match rate lookup, is a **guard** rather than a repair: the
old table's lite/flash collision cost ~25% under-pricing on an id no live site
passed, but without the guard the corrected rates would have over-charged lite
output 6.25x.

An adversarial review of this work caught a regression before commit: the
unpriced-model guard originally keyed on rate-table membership, which nulled
Serper's flat configured per-query fee across 5 live sites and labelled known
spend `unpriced_model`. Now gated on provider, with regression tests.

A follow-up check of the Anthropic rows found the **same bug a third time**:
`claude-haiku` was priced at Claude Haiku **3.5**'s retired `(0.80, 4.00)` while
the repo calls `claude-haiku-4-5-20251001` at `1.00 / 5.00` — under-recording 20%
across 11 call sites, the orchestrator's highest-volume model. Corrected;
`claude-sonnet` verified correct. Three independent instances of "a superseded
model's price inherited by its successor" is a process gap, not three accidents.

**All three closed 2026-08-25** by [ADR 0016](decisions/0016-ledgers-must-express-unknown.md).
OD-61: `api_spend.cost_usd` made nullable (migration written, **not applied**) and

**44.2a — Five empty agents. ✅ RESOLVED, and my original claim here was wrong.**

The five are real stubs — `ghost_inventory_agent` (37 lines), `auto_pilot_agent`
(36), `negotiation_playbook_agent` (36), `shrinkage_detective_agent` (35),
`compliance_agent` (35) — each logging the event and returning.

**But I claimed they were live and consuming events, and they were not.** All five
are `AgentTier.OPTIONAL`, and `is_enabled()` requires
`AGENT_<NAME>_ENABLED`, defaulting to False. `_create_lazy_proxies()` skips them,
so they never instantiate and never subscribe. Health checks did not pass for them
and logs did not show events received. The only true part was that
`registered_count` counted them, so "Registered 20 agent classes" overstated what
was running.

**The real defect was the opposite of hollow-and-running: the gate was
unreachable.** `_build_feature_flags()` populated only three `FEATURE_*` keys and
never any `AGENT_<NAME>_ENABLED` key — so the switch the OPTIONAL tier documented
was one nothing read. `AGENT_GHOST_INVENTORY_AGENT_ENABLED=true` in the
environment did precisely nothing, silently.

Fixed: the flag builder now sweeps `os.environ` for `AGENT_*_ENABLED` (parsing the
string, since a truthiness check reads `"false"` as enabled); the five declare
`IS_STUB = True` and the orchestrator **refuses to start a stub even when its flag
is on** — now that the gate works, an operator could otherwise switch one on and
get an agent that subscribes to real events and discards them, which does look
healthy from every dashboard; and boot logging reports enabled-vs-gated rather
than a single count.

`auto_pilot_agent` is deliberately left unimplemented: its TODOs are "evaluate
`auto_pilot_rules`" and "create procurement orders", and autonomy stays
human-gated until the benchmark numbers are met. An empty auto-pilot that refuses
to boot is the correct state, not a gap.

Covered by 20 tests in `tests/test_agent_registry_gating.py`, including one that
fails if a future agent is OPTIONAL *and* implemented — the moment to revisit
whether the marker or the tier is wrong.

**44.2c — `deploy.yml`'s "The deployed build IS the merged build" reported a
correct Railway skip as a failure. ✅ RESOLVED 2026-09-03 (ADR 0097
Correction; found alongside
[ADR 0090](decisions/0090-pr-audit-gate-autonomous-merge.md)'s merge).**
The inverse of this section's usual shape: not a hollow success, a hollow
*failure*. `@wineops/api-gateway`'s Railway service only rebuilds when a push
touches its own `watchPatterns` (`apps/api-gateway/**`, `pnpm-lock.yaml`,
`pnpm-workspace.yaml`, `package.json` — confirmed via `railway deployment list
--json` → `.meta.serviceManifest.build.watchPatterns`). `check_deployed_sha.py`
was called with `--expect` set to the raw merged sha regardless, so any
docs/CI/tooling-only merge — where Railway correctly returns
`skippedReason: "No changes to watched files"` and keeps serving its last real
build — reported MISMATCH for a deploy that behaved exactly as designed.
Confirmed live on two consecutive merges: PR #284 (docs only) and PR #261
(CI/tooling/`.claude`/`.planning` only) both skipped correctly and both then
failed this check.
→ Fixed: `scripts/resolve_watched_commit.py` (new, `--self-test` covers it
against a real git repo) resolves the last commit at-or-before the merge that
actually touches the watched paths; `deploy.yml`'s Stage 2 now expects THAT
commit, not the raw merge sha. Verified against the real PR #261 case before
landing: resolves to `2e9d0723` (the actual last api-gateway change), not
`ce519d42` (the merge that tripped this the second time).

**Not resolved on the first pass — caught by PR #291's own real audit before
merge, same day.** Two BLOCKs: (1) the resolver's first version used plain
`git log <sha> -- <paths>`, which applies git's default history
simplification and can silently skip a real merge commit for a side-branch
commit that was never `main`'s pushed head — reproduced against 4 real merge
commits in this repo's own history; fixed with `--first-parent`, now covered
by a self-test case that builds a real `git merge --no-ff` commit rather than
only a linear history. (2) `CLAIMS.jsonl:154` and
[ADR 0097](decisions/0097-the-gateway-says-which-build-it-is.md)'s Decision
section both stated the pre-fix invariant ("compares against the merged
sha") as still true after this PR changed it — the claim's own `verify`
command kept passing because it only grepped for the substring `head_sha`
anywhere in the job, which simply moved to a new step. Both corrected (ADR
0097 gets a `## Correction` section, matching this repo's established
convention rather than silently editing the original text); the live-vs.
hand-mirrored watch-path fork the resolver's own docstring names is filed as
[OD-122](decisions/OPEN-DECISIONS.md), not defaulted.

## Security — Google sign-in self-provisioned a manager of a real tenant — CLOSED 2026-09-01

Found while preparing to put the app on a public branded domain
(`mudavym.com`), which would have advertised it. **Verified against
production, not reasoned:**

- `POST /api/v1/auth/oauth/google` carries no guard — probed live, it answers
  the service's own `"Failed to verify Google token"` (401), not a guard
  rejection, so it is reachable by anyone.
- `verifyGoogleToken` checks only the token audience and `email_verified`.
  There is no domain restriction or allowlist.
- `findOrCreateOAuthUser` then INSERTed any unknown address as
  `role: "manager"` with `restaurant_id = DEFAULT_RESTAURANT_ID`.
- `DEFAULT_RESTAURANT_ID` **is set** in Railway production, and resolved to
  a live tenant holding real inventory — not a demo row.

Net effect: anyone on the internet holding any Google account could mint
themselves a manager of a real restaurant. **No account had come in that way**
— the only `oauth_provider = 'google'` row belonged to a different tenant and
predated it — so this was a latent hole, not an incident.

**Fixed** (`fix/oauth-no-self-provision`): the create branch is removed
outright rather than re-gated on the env var — an unset variable was the only
thing standing between the public internet and a manager role, and a stray
value in a future environment must not be able to reopen it. OAuth sign-in now
only ever resolves an existing account; registration is where a restaurant is
created or an invite redeemed. The same change normalises the email before
lookup (`users.email` is UNIQUE and case-sensitive, so a mixed-case stored
address against Google's lower-cased claim used to miss the row and fall
through into the create branch — the same defect wearing a different hat).
Five tests added to `identity-first-signin.spec.ts`; four were observed
FAILING against the reverted implementation before being kept.

**Open, and it is a product decision, not a repair:** whether Google
self-signup should exist at all in some gated form (invite-only, domain
allowlist, or provisioning into a sandbox tenant at a low-privilege role).
Today the answer is simply "no self-signup". Also open and separate:
`findOrCreateOAuthUser` signs an existing account in on an email match
**without writing a `user_oauth_accounts` row**, so `resolveSignInMethods`
keeps reporting that identity as password-only while Google demonstrably
works for it — an ADR 0024 truthfulness gap pointed the other way.

## Convention — `toLocaleDateString` on wire timestamps needs explicit `timeZone: "UTC"` — added 2026-08-31

`studio-invite.controller.ts:98` formatted `data.expires_at` (a UTC ISO wire
timestamp) with `toLocaleDateString("en-US", {month, day, year})` and no
`timeZone`, so a UTC-midnight expiry rendered as the **prior day** on any
server west of UTC — and `studio-invite.controller.spec.ts` only caught it
because CI runs in UTC (`TZ=America/New_York npx jest
src/common/orchestrator/studio-invite.controller.spec.ts` failed before the
fix, passes after). **CLOSED 2026-08-31** (`fix/studio-invite-expiry-tz`):
added `timeZone: "UTC"` to the options object; full gateway jest suite green
(109/110 suites, 1 pre-existing skip, 1363/1374 tests).

~~**Open, unowned — same bug class found in a second file.**~~ **CLOSED
2026-08-31** (`fix/email-template-date-tz`, #175 — merged hours after the
entry above, which is why the paragraph shipped reading "open"). The open
question it named — whether every call site feeds a UTC wire timestamp or an
already-local `Date` — was answered by tracing them, and the answer was
**both**, which is why the fix is not a blanket `timeZone: "UTC"`:

- `scheduled-tasks.service.ts` passes DB-column ISO strings
  (`scheduledDate`/`expectedDate`/`dueDate`/`eventDate`) — genuine wire
  timestamps that need the UTC pin.
- The same service's inventory-audit reminder builds its date with
  `new Date(); .setDate(+2)` — local-time calendar arithmetic for "the
  upcoming Wednesday" in the server's own clock. Forcing UTC there would
  re-derive a different calendar day on any host whose process TZ is not
  already UTC: the opposite bug, introduced by too broad a fix.

So `formatDate`/`formatShortDate` now branch on input type — a `string` is a
wire timestamp and is pinned to UTC, a `Date` object is left in local time —
with `template-config.spec.ts` pinning both halves, including a test that
fails if someone later "simplifies" it to an unconditional UTC option.

**The convention this section names still stands** for new code:
`toLocaleDateString` on a wire timestamp needs an explicit
`timeZone: "UTC"`, and a spec that only runs in UTC CI cannot catch its
absence — pin the suite's TZ (as `apps/web` now does in
`src/__tests__/setup.ts`) or the assertion is vacuous.

## Analytics — `deadStockCapital` measured stock depth, not movement — CLOSED 2026-09-01

`AnalyticsService.getFinancialSummary` defined dead stock as
`qty > max(thresholdMin * 3, 12)` with **no consumption join at all**, while
`recommendations.service.ts` rendered the total to managers as capital "locked in slow

## Analytics — the forecast "backtest" was an in-sample fit — CLOSED 2026-09-02

Closes **defect 3** above. Fixed on `fix/holt-winters-lookahead-leak`; recorded in
[[0064-a-fitted-value-is-a-prediction-not-a-memory]].

`fitted[i]` on every smoother in `engine/forecasting.ts` is now the one-step-ahead
prediction of `series[i]` from `series[0..i-1]` — pushed **before** the state update
rather than after it. Measured as ∂fitted[k]/∂series[k] on a 56-point weekly series
at k=40, pre-fix vs post-fix: `holtWintersAdditive` **0.525 → 0** (the closed form was
α+βα+γ(1−α)), `holtLinear` **0.04 → 0** (α·β), `simpleExponentialSmoothing` 0 → 0.

**Two corrections to the entry above, both verified.** Defect 3 was right that
`holtLinear:74-79` leaked and the brief that reopened it was wrong to call that sibling
correct — it read pre-update *level* but **post-update trend**. And the second consumer
it named, `insight-generator.service.ts:488`, was never leaked: it trains on
`values.slice(0, -7)` and scores `hw.forecast` against the held-out week, a genuine
holdout. Its *comment* said "fitted"; the arithmetic did not. Only
`analytics.service.ts` consumed `fitted`, and `fitted` never leaves the API response.

Every model now returns its own `warmup` (SES 1, Holt 2, Holt-Winters 2·period), and
the accuracy block scores `fitted.slice(warmup)` — because seeding reads the first two
seasons, so those fitted values stay in-sample however the recursion is written
(verified post-fix: ∂fitted[3]/∂series[3] ≠ 0 while k ∈ {14,21,33,55} are all 0). The
spec pins each warmup at its exact boundary — `warmup − 1` must still leak — so a value
that is merely large enough does not pass.

`accuracy` gained `basis` and `scoredPoints`. **Read that as a qualifier, not as an
honesty feature in itself** — an independent adversarial pass showed it cut the other
way on the no-data path, where a stated evidence count of 106 made an empty claim read
as a well-grounded one. Two defects that pass found and closed on the same branch:

- **MASE spanned two different windows.** The numerator moved to `[warmup, n)` while
  the denominator stayed on the full series, so the benchmark priced days the numerator
  refused to score. `mase` now takes a `from` bound. The error runs **both** ways:
  measured over 400 simulated series of each shape, an opening-blitz head flatters MASE
  by a mean 4.5% (worst 13.9%, 22/400 beats-naive verdict flips) and a leading-zero
  "POS went live on day 20" head punishes it by a mean 6.6% (143/400 flips). Both
  shapes are ones `toDailySeries` produces directly.
- **The no-data series certified itself.** Zero-fill means a restaurant with no
  consumption yields 120 zeros, not a short series, so Holt-Winters never returns null
  and MAE/RMSE both answer **0** — a perfect forecast over a series holding no
  observation (`mape` and `mase` already refused, both dividing by zero). All four now
  return null with `basis: "no_observations_in_scored_window"`, `scoredPoints: 0`, per
  ADR 0051's rule that an unknown is an em dash and never a zero. The zeros are
  pre-existing; what the ADR 0064 fields added was the false confidence around them.

**The numbers this invalidates.** On a simulated 120-day series of the shape
`toDailySeries` produces, the reported figures move MAE 1.606 → 3.550, RMSE 2.106 →
4.546, MAPE 6.95% → 15.31%, MASE 0.402 → 0.889, scored points 120 → 106. The forecast
still beats seasonal-naive, by 11% rather than 2.5×. No forecast accuracy figure was
ever rendered to a user (`fitted` has zero hits outside `apps/api-gateway`), so nothing
shipped needs correcting — but any such number quoted in a doc or a session predating
2026-09-02 is wrong by roughly 2×.

Regression guards: `apps/api-gateway/src/analytics/engine/forecasting.spec.ts` (7 new
cases) and `apps/api-gateway/src/analytics/forecast-accuracy-honesty.spec.ts` (4 new
cases, service-level through a mocked client). **7 of the 11 are verified failing**
against the pristine tree with the specs in place — measured, not projected: the source
files were reverted and the suite re-run, 3 against `origin/main` and 4 against the
pre-adversary commit. The rest are must-pass-both-ways guards that the fixes are not a
blanket mute — that an honest `fitted` is still a *useful* fit, that `from` clamps
rather than reading off the front of the array, and that a restaurant which *does* have
consumption still gets scored. The leak assertion compares all three models as a single
object, so the pre-fix failure reads `holtLinear: false, holtWinters: false, ses: true`
— naming every model that broke instead of short-circuiting on the first.

## Four defects surfaced by the motion-canvas codebase sweep — added 2026-08-27

Found while five agents read the web app to ground sketch 087's motion set in real
behaviour. Design work, but the findings are engineering ones. All four were
**re-verified by hand in the repository** rather than taken on an agent's report — one
agent's count was wrong (it said 15 `data-ux-key` markers; there are 11), which is the
reason for checking each claim independently.

### 1. Every `stock:updated` rewrites the row someone is reading

`apps/web/src/lib/websocket.tsx:489-491` invalidates three whole query trees on every

```ts
queryClient.invalidateQueries({ queryKey: queryKeys.inventory.all })
queryClient.invalidateQueries({ queryKey: queryKeys.dashboard.all })
queryClient.invalidateQueries({ queryKey: queryKeys.wines.all })
```

One bottle moving anywhere in the restaurant refetches and re-renders inventory, the

reading. The blast radius is the whole page, and the event carries enough information
to patch a single row instead.

### 2. A dropped door receipt is indistinguishable from a delivered one

`lib/doorOutbox.ts:113-118` gives up after 8 attempts or a permanent 4xx. **The drop
itself is correct and deliberate** — the comment argues it well ("a queue that never
drains stops being watched, and then a real failure hides behind the stuck one") — and
the function reports the outcome, returning `{ sent, failed }` at `:129`.

The defect is that nothing reads it. `watchDoorOutbox:137-139` calls
`flushDoorOutbox().then(() => onChange?.())`, discarding the result, and
`pages/receiving/DoorReceipt.tsx:70-71` only re-reads `pendingDoorCount`. So when a
porter's receipt is discarded after 8 failures, the pending badge **decrements exactly
as it does on success**. The person at the door cannot tell a delivered receipt from a
lost one.

`lib/spotCountOutbox.ts:110-115` has the identical shape, so a lost spot count behaves
the same way.

**The fix is small** — surface `failed` where `pendingDoorCount` is already rendered.
Sketch 087's `inv-09` shows the shape: the receipt lands in a needs-attention rail as a
pinned task, deliberately not a modal, because this fires mid-service.

### 3. A docstring asserts a wiring that does not exist

`hooks/useUxOverrides.ts:12` reads *"Mounted once in DashboardLayout."* The hook has
**zero importers** (grep across `apps/web/src`), and 11 `data-ux-key` markers sit in
the tree waiting for a reporter that never runs. The dead code is a known deferral;
the false comment is not, and it is the more expensive half — it tells the next reader
the gap is already closed.

Fix is one line: say what is true.

### 4. `Notifications.tsx:231` discards `foldedById`

`lib/notificationStack.ts`'s `collapseStackedNotifications` returns a `foldedById` map
describing what each fold swallowed. The page throws it away, so the "N earlier
duplicates grouped" string the library already computes is rendered only by the header
bell — the inbox itself silently hides the count.

`POST /api/v1/auth/dev-bypass-login` mints a real session for

**Fixed** by making the *session* claim what it is, not by editing the row.

token is inert against a production server — the shape the OAuth self-provision
hole (above, 2026-09-01) taught: an unset env var must never be the only thing
between a caller and a privilege. A normal token omits the key entirely; the
database column is untouched and still answers everywhere else.

session as verified to `/auth/me` was necessary and not sufficient: it got the

built, and in `refreshAccessToken`, which otherwise rebuilt the payload from the
row and dropped the marker — the override lapsed after 15 minutes, which is the
worst shape of the bug: it looks like the fix never worked rather than like it
expired. Both gates are re-checked per request / per refresh, never inherited.

Collapsing the env gate into it too would make "not a dev session" and "a dev

## CodeQL — two highs the extraction door made real — FIXED 2026-09-04

Both alerts fired on `refs/pull/301/merge`, both in
`apps/api-gateway/src/procurement/documents/document-extractor.service.ts`, and
neither is new code. PR #301's `POST /procurement/documents/:id/extraction`
(entry above) put a **client's request body** on a path that until then only ever
carried our own model's reply, which is what turned two dormant shapes into
reachable ones. Triaged by ADR 0100's rule — *decide by reachability and by what
failure would mean, not by the severity badge* — and both fixed, because
reachability is exactly what changed.

**#1327 `js/polynomial-redos` [high] — `stripJsonFence`, was `:116`, now `:130`.**
The regex was `/^```json\s*|\s*```$/g`. Its second alternative has no anchor at
its start, so on a run of whitespace the engine restarts `\s*` at every offset
and backtracks the whole run — quadratic. **Measured on the unmodified code**
(node v22, this machine): 200 kB of spaces took **21_833 ms**;
`" ".repeat(50_000) + "x"` took **1_702 ms**. That is a multi-second stall of the
gateway's single event loop, bought with one POST. Replaced with
`startsWith`/`endsWith`/`slice`/`trim` — **no regex at all** — which is
character-for-character equivalent (the two `\s*` runs both fall inside the
existing final `.trim()`, so the regex was only ever deciding *whether* each
fence was present). The same 200 kB body now returns in **< 2 ms**; the spec
file's wall time fell from **44.98 s to 0.56 s**.

**#1328 `js/remote-property-injection` [high] — `spreadPrinted`, was `:469`, now
`:555`.** The `printed` map (PR #298) was copied with
`for (const [k, raw] of Object.entries(v)) out[k] = raw`, so **the key came from
the body**. Now the loop walks a closed allow-list — `PRINTED_KEYS` at `:489`,
the twenty money/quantity fields `SYSTEM_PROMPT` names for a line and for the
document totals — and the destination is `Object.create(null)`. Unknown keys are
dropped **and counted** in `warnings`, because a silently lost transcript field
would be indistinguishable from one the paper never printed.

**Honest scope of #1328.** `Object.prototype` was *not* reachable through it:
`out["__proto__"] = "…"` invokes the inherited setter, which ignores a string, so
no prototype was ever polluted — the "leaves `Object.prototype` untouched" test
passes against the unmodified code too, and is a regression guard, not a repro.
What *was* live is the rest of it: any key a caller chose — `constructor`,
`prototype`, or arbitrary text — landed verbatim in the `as_printed` jsonb the
canonical document and every provenance hover read back. That is a real
injection into stored, re-rendered data, and it is what the allow-list closes.

**Also swept:** `\[.*\]\s*=` across the file finds exactly **one** computed
property write, the one above. `num()`'s `/[$,\s]/g` at `:471` is a character
class with no quantifier over it and is linear. No other model-JSON key reaches
an assignment anywhere in the file.

**Not verified:** the `codeql` CLI is not installed on this machine
(`which codeql` → not found), so neither query was re-run locally against the
patched tree. The claim that the alerts close rests on removing the flagged
constructs entirely — there is no regex left in `stripJsonFence` and no
input-derived key left in `spreadPrinted` — not on a green local scan.

## CI — Two parallel PRs took one migration version — guarded — added 2026-09-05

Measured 2026-09-05: PR #309 (`feat/canonical-document-slice-3-corrections`) and PR #310
(`fix/simpos-real-pos`) each added a migration named
`supabase/migrations/20260905120000_*.sql` —
`20260905120000_document_correction_reason_and_kind.sql` and
`20260905120000_simpos_behaves_like_a_pos.sql`. Both PRs were green.

Nothing in CI could see it. Every check in this repository runs against one branch, and each
branch's migration set is internally consistent. Supabase's migration history keys on the
**version** (the leading 14-digit timestamp), not the filename or the contents, so whichever
merged second would fail on auto-apply or — the worse case — be recorded as already applied and
silently skipped, leaving `main`'s schema missing SQL that the history says ran. Same shape as the
ADR-number race behind [`decisions/0085`](decisions/0085-a-fixture-tests-the-guard-not-the-checkout.md):
the version is claimed at commit time and checked (if at all) by a human minutes earlier, so a
correct sweep still loses the race.

**Guarded** by `scripts/check_migration_versions_unique.py`, CI job
`A migration version names one migration` in `.github/workflows/ci.yml`, next to
`An ADR number names one decision`. It compares the versions this branch introduces against
`origin/main` **plus every other open PR** — the half no single-branch check can see — enumerated
through `gh pr list` and the pull-request *files* API. It exits 2, never 0, when it cannot
enumerate (no `gh`, no token, an API error, an unfetched ref), because zero open PRs and no
collision are indistinguishable otherwise. A collision names both files.

Two things this does **not** cover, stated rather than implied: a version taken by a branch with no
open PR is invisible to it (that branch cannot merge without a PR, so the collision is caught when
the PR opens, not before); and it says nothing about whether two migrations with *different*
versions conflict semantically.

**Note on the reproduction:** by the time the guard was written, both PRs had already been renamed
by hand (#309 → `20260905231500`, #310 → `20260905174500`), so the live tree no longer collides.
The guard's `--self-test` rebuilds the exact 2026-09-05 pair in a scratch repo with a stubbed `gh`
and asserts it fires.

## Dev tooling — a conflict-marker guard that only read the planning corpus — FIXED 2026-09-05

`scripts/check_no_conflict_markers.py` was added 2026-09-01 after
`.planning/decisions/0032-vault-cleanup-cut-line.md` sat on `main` for days with
12 unresolved conflict blocks inside its Tombstone index. Its CI step
(`.github/workflows/ci.yml`, job `decision-claims`) was named *"No planning
document carries an unresolved conflict marker"* — but the script's own name, and
the way everyone read the step, promised the repository.

It scanned `.planning/` and nothing else. **Measured twice on 2026-09-05:** a
builder pushed `apps/web/src/pages/inventory/useInventoryPage.ts` carrying two
unresolved hunks and the guard printed

```
== Conflict markers: 1369 files scanned, none corrupt
PASS -- every planning document still parses as a document.
```

and exited 0. Reproduced deterministically with a staged probe file
(`apps/web/src/pages/inventory/__probe_conflict.ts`, three marker lines) against
the unmodified script: same PASS, same exit 0.

This is the absence-reported-as-health fault in its purest form.
Every number in that output was *true* — 1369 files really were scanned and
really were clean. The verdict it implied was false, because the denominator was
the wrong corpus and nothing in the output said so. A conflict marker in
TypeScript is exactly as much a broken file as one in Markdown, and it reaches
production faster.

**Fixed** by giving the guard two sections that both always run and report
separately, so neither can hide the other:

1. **Repository** — every tracked text file, enumerated with `git ls-files`
   (not a filesystem walk: the thing that must not carry a marker is the thing
   that gets committed). Binaries are dropped by extension *and* a NUL sniff of
   the first 8KB, so an extensionless binary cannot slip through on its name;
   lockfiles, `node_modules`, `dist`/`build`/`.next`/coverage are skipped and
   **counted as skipped in the output**, because the whole defect above was an
   unstated exclusion. 4267 files scan clean on `main` today.
2. **Planning corpus** — the original `.planning/` document-parse check, kept
   verbatim and reported under its own heading.

One true positive surfaced and was excluded deliberately:
`.planning/.obsidian/plugins/obsidian-git/main.js:371` is a vendored, minified
third-party bundle whose source embeds a fenced ` ```diff ` block showing the
user what a merge conflict looks like. Those marker lines are *documentation
inside a dependency*, not a broken file here. It is skipped via
`VENDORED_PREFIXES`, an exact path prefix rather than a `plugins/` directory
rule — "we ship someone else's bundle at this path" is a much narrower claim
than "skip any directory called plugins", and the narrow claim is the one that
stays true. A self-test invariant proves the skip does not leak to a same-named

## Canonical document — slice 3 stop 1 (corrections): three findings — added 2026-09-05

Found while building the correction door of ADR 0104 D5
(PR: `feat/canonical-document-slice-3-corrections`). All three were MEASURED, not reasoned.

1. **🔴 Two spec harnesses resolve every `Promise.all` read against the LAST table named — FIXED
   in the new spec, OPEN in the two that already existed.** The supabase mock in
   `apps/api-gateway/src/procurement/canonical/canonical-document.service.spec.ts:163` and
   `.../price-base-round-trip.spec.ts:256` keeps ONE shared `currentTable` and reads it *when the
   chain resolves*, not when `from()` is called. supabase-js chains are built eagerly and awaited
   later, so the moment a service issues two reads under `Promise.all` — as `readCorrections` now
   does — both chains come back with the answer canned for whichever table was named second. The
   first symptom was a correction-log fixture silently arriving as the revision fixture, which made
   four new assertions pass against an implementation that was not doing what they claimed. The new
   `document-correction.service.spec.ts` captures the table per chain
   (`makeChain(table)`); the two older files still share `currentTable` and are one `Promise.all`
   away from the same silent agreement. **This is the absence-as-health fault inside the test
   harness: the mock answered a question it had not been asked, and the suite went green.**

2. **`kasa` and `koli` ARE readable units — the first draft of the "refuse an unconvertible unit"
   test asserted the opposite.** `normalizeUom`
   (`apps/api-gateway/src/procurement/documents/document-types.ts:156`) folds the Turkish words for
   a shipping case to `case`, and `şişe`/`adet` likewise. A test written from the assumption that a
   Turkish word is unreadable would have passed for the wrong reason and would have started failing
   the day someone *removed* that folding. Measured, not assumed; the test now uses a word the
   normaliser genuinely cannot read.

3. **The next revision number was computed in two places, and they disagreed by one.** The
   correction door needs the number BEFORE the row exists (the corrected field's envelope carries
   its own `revision`), while `persistRevision` computed its own from `max(revision)`. On a document
   with no revision rows the envelope claimed 2 and the row was written as 1. Fixed by giving
   `CanonicalDocumentService` one public `nextRevision()` that both callers use, and by having the
   first correction write the pre-correction document down as revision 1 before taking revision 2 —
   so the log opens with what the machine read rather than with somebody's correction of it.

**Deviation from the brief, stated (CLAUDE.md §0.5).** The brief asked for `verified_by` /
`verified_at` to be "preserved from the prior revision" on a correction. They are preserved when the
correction RESTATES the same value and CLEARED when it changes it — carrying a tick onto a different
number would print *"Verified by Ayşe"* beside a figure Ayşe never saw, which is a fabricated human
assertion. The old tick is not lost: it is inside the append-only correction row's `before`. ADR 0104
D5 itself says only "a `verified_by` tick per field" and does not decide this; if the founder wants
literal preservation it is a one-line change in
`document-correction.service.ts` and a test that already names both directions.

**Also stated:** `buildFromDocumentId` reads the latest revision NUMBER and replays the
`document_corrections` log, rather than serving the stored `document_revisions.layer1` blob whole.
The blob is still written on every correction (it is the append-only record and slice 4's input),
but serving it would freeze a document against a later re-extraction — the rows would change and the
page would keep showing the layer 1 captured at correction time. Replaying the log keeps a new
extraction visible and the human's corrections applied on top.

## Two type-checks agreeing about a file neither of them reads — added 2026-09-05

Found when `Lint TypeScript` went red on a branch that had passed every local check
(slice 3, PRs #309 and #315):

```
documents.controller.spec.ts(41,18): error TS2554: Expected 5 arguments, but got 4.
canonical-route.spec.ts(110,18):    error TS2554: Expected 6 arguments, but got 5.
```

Two specs construct `DocumentsController` **directly** — deliberately, so the class-level
`JwtAuthGuard`'s own dependency chain is not dragged into a test about route behaviour — and
the controller gained constructor dependencies. The specs were stubbing too few.

**Why nothing local caught it, which is the finding rather than the fix.**

- `apps/api-gateway/tsconfig.json` **excludes `*.spec.ts`**, so `tsc --noEmit -p tsconfig.json`
  — the command this repo's sessions reach for — is clean while a spec is one argument short.
  Only `tsc --noEmit -p tsconfig.spec.json` reads them, and CI's `Lint TypeScript` is the only
  place that runs.
- **Jest does not typecheck.** It transpiles each file with swc; `new C(a, b, c, d)` against a
  five-argument constructor runs fine, because the missing dependency is `undefined` and the
  routes under test never touch it. The suite was green.

So a green `tsc` and a green `jest` were two checks **agreeing about a file neither of them was
reading** — the same shape as this repository's standing fault, one level up: not a system
reporting absence as health, but two systems whose union looks like coverage and whose
intersection is empty.

**The habit, until something mechanises it:** after touching a controller or service
constructor, run `npx tsc --noEmit -p apps/api-gateway/tsconfig.spec.json`, not just
`-p tsconfig.json`. Each stub in those two specs now carries the name of the dependency it
stands in for, so the next argument is a one-line edit rather than a puzzle. A guard that
simply ran the spec typecheck in the same pre-push sweep as the others would close it; that is
not built here, and saying so is the point.
