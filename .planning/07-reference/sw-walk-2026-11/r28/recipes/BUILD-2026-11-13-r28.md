### #1385: a serve is costed from invoices only (gap 3)

- **Migration `20270920100000`** adds the side view `inventory_lot_invoice_cost` (security_invoker; service_role only). Per good it gives:
  - `stock_qty`: live, non-sample units;
  - `invoice_qty`: invoice-provenanced units with a cost above 0;
  - `invoice_wac`: their average cost, 6 places;
  - `settled_qty`: invoiced units whose cost is final.
- **`resolveUnitCost`** reads the view when `invoice_cost_read` is set. Only `RecipesService.readPricing` sets it.

### Gap 1 design (stock draw on sale), not built

**Invariant:** for every POS sale line mapped to a dish or drink with a current recipe:

- the draw on each stocked line's good equals `qty_base × qty sold ÷ yield_serves`, in the good's base unit;
- each draw is booked once, keyed by (pos line id, recipe line id, recipe version id);
- a void or refund books the exact reverse, keyed the same way;
- draws stay inside the line's `restaurant_id`.

**Cases that break it:**
- unit mismatch (piece against weight, the gap 7 bridges);
- a recipe edited between the sale and the void (draw from the version stamped at sale, never the current one);
- a POS line with no link (book nothing, and count it as "not drawn");
- more than 1,000 lines in one sync (page the reads).

**Approach:** extend the existing POS draw path rather than a new writer. #949 stamps glass-pour draws and gives a void its cost back. Rejected: a nightly batch over the day's sales, which leaves variance stale all day and duplicates the void logic.

**Not verified this session:** the #949 code path, and whether a POS item already carries a menu or cocktail link. Read both first.
