## Ranked gaps

### G1 (high, money). Choosing a long menu runs past the page's 30 s limit, and the page then says "Nothing has changed" when the switch did happen

**Where.**
- The switch commits first, at 1340:`apps/api-gateway/src/menus/menus.service.ts:1748` (`make_menu_current`).
- Every priced line is then carried one RPC at a time (`setHouseMenuPrice`, `:2531`). The code's own note puts that at about 0.33 s per call against the pooler.
- `apps/web/src/services/api/client.ts:67` sets `timeout: 30000`.

**What the person sees.**
- With about 90 or more priced lines, the request is cut off.
- `MenuPlan.tsx:462` then prints "It was not made current: timeout of 30000ms exceeded. Nothing has changed." That is false: the menu is already current.

**Why it cannot be finished.**
- If the carry dies part-way (a deploy, a crash), choosing the menu again answers `already_current` with zero lines carried (`:1777`).
- Half the prices stay old, and no screen can finish the carry.

**Evidence.** The 0.33 s per call comes from the code comment, not from a measurement (no production pooler was used). The ordering and the false sentence are read directly from the code.

**Open PR?** None. #1101/#1102 batch the reads and the write-back, but the price write stays one call per line (r2 report, "set_house_menu_price stays one call per line").

### G2 (high, goal: inventory and recipes). A menu drink that matches none of the house's goods is filed as a bottle of wine, cocktails included

**Where.**
- `addToInventory` inserts new goods with no `kind` or `uom`, at 1340:`menus.service.ts:2329-2335`.
- The insert trigger fills them in: `supabase/migrations/20260903171000_the_house_item_is_the_ledgers_key.sql:431` sets `NEW.kind := coalesce(NEW.kind, 'wine')` and uom `'bottle'`. No later migration redefines it.

**What happens.**
- A beer, spirit, soft drink or cocktail line becomes a `kind='wine'`, `uom='bottle'` good, both when a menu is made current and when a line is added to the current menu.
- A cocktail line becomes a stocked "bottle" and is never linked to its recipe. The goal asks for a drink/cocktail recipe ↔ goods link, and this works against it.

**Open PR?** None. #1299 to #1301 only avoid the twin when the house *already* carries the good (r23).

### G3 (high, the founder's own house). The dish test knows only English section names, so a Turkish menu's dishes are taken for drinks

**Where.**
- 1340:`apps/api-gateway/src/menus/menu-line-view.ts:49` (`KITCHEN_HINTS`) and `:109` (`HINT_WORDS`).
- The web copy of the same list: `apps/web/src/lib/firstProof.ts:26`.

**Probe.** The hint regex was run against Turkish section names:
- Each of these returned false: `ana yemekler`, `tatlılar`, `çorbalar`, `mezeler`, `soğuk mezeler`, `ızgaralar`, `kebaplar`, `salatalar`, `başlangıçlar`, `ara sıcaklar`, `pideler`.
- Only the singular `meze` returned true. The plural suffix allows only `s|es`, so it never matches `-ler/-lar`.

**What happens.** A CSV or typed dish under a Turkish section:
- is sent to the shared wine library as a provisional wine;
- once current, is carried as a `kind='wine'` good (G2);
- has its dish price written as that good's house bottle price.

**Open PR?** None. The only KITCHEN_HINTS edits are in #1069, #1098 and #1218, and they are English.

### G4 (high, goal: menu upload). The photo/PDF reader reads drinks only, so a scanned food menu loses its dishes, and a food-only photo is told it is unclear

**Where.**
- The prompt, 1340:`apps/api-gateway/src/menus/parsers/scan-parser.service.ts:81-82`: "You are analyzing a restaurant beverage menu image. Extract EVERY drink listed…".
- The closed category list (`wine-extract-item.interface.ts:20-36`) has no food member.

**What the person sees.**
- On a full menu, the read keeps the drinks and silently drops every dish.
- On a food-only photo, the read finds nothing, and the house is told "No line could be read from this file… Try a clearer photo or the PDF itself" (`menus.service.ts:344`). The real cause is that dishes are not read at all.
- Onboarding says the same thing ahead of time, "We'll extract your wines using AI" (`MenuCsvUpload.tsx:303`).
- So a typed or CSV menu can carry dishes (#1213/#1261), but a photo cannot.

**Open PR?** None. No open diff touches the scan prompt for food.

### G5 (high, speed; introduced by open PR #1299, not on main). Matching menu lines to house goods compares every line with every good, and blocks the gateway while it does

**Where.**
- 1340:`apps/api-gateway/src/menus/house-good-match.ts:257` (pre-filter) and `:187`/`:174` (`matchLine` → `formFits` → `nameParts(good)` per pair).
- Every good's name is folded again for every line, twice over (step 2, then `matchLine`). It is pure CPU, run on the Node event loop.

**Probe.** Measured on this Mac with the transpiled module and synthetic names:
- 100 lines × 300 goods: 608 ms.
- **485 lines × 1,000 goods: 7,279 ms.**
- **485 lines × 3,000 goods: 20,190 ms.**

**What happens.**
- A CSV import runs inside the 30 s request, so it gets close to the limit.
- Every other request on the gateway stalls for the duration. The same happens when a background scan finishes.

**Fix.** Fold each good once into a key → goods map (O(lines + goods)).

**Open PR?** None. It should be fixed on #1299 before that PR merges.

### G6 (high, Turkish dedupe). The dotless "ı" is deleted instead of folded, so "Yeni Rakı" never matches the house's "Yeni RAKI"

**Where.**
- 1340:`apps/api-gateway/src/wines/wine-signature.ts:139-143`: NFD, then strip diacritics, then `[^a-z0-9]` → space. "ı" has no decomposition, so it is dropped.
- `house-good-match.ts` matches with this function.

**Probe.**
- `Rakı`→`rak`, `RAKI`→`raki`, `Kalecik Karası`→`kalecik karas`, `KALECIK KARASI`→`kalecik karasi`.
- `matchLine({name:'Yeni Rakı'}, [good 'Yeni RAKI'])` → `none`.
- `matchLine({name:'Kalecik Karası'}, [good 'Kalecik Karasi'])` → `none`.

**What happens.** The D1 dedupe misses, and a twin good is made: the very fault #1299 to #1301 were built to stop.

**Fix and open PR?**
- #1100's `foldMenuName` (plan 2d) and #761 fold ı→i, but the matcher does not.
- Fold ı→i in `house-good-match.ts` itself. Changing the shared signature function would change stored hashes.

### G7 (medium-high, money/locale). The /menu "Add to menu" price boxes are number boxes read with `Number()`

**Where.**
- 1340:`apps/web/src/pages/menu/next/MenuNext.tsx:216,229` (`type="number"`) and `:172-173` (`Number(byGlass)`, `Number(bottle)`).
- `AddMenuItemDto` is only `@IsNumber()`, with no `Min(0)` (`dto/add-menu-item.dto.ts`).

**What happens.** In a lira house:
- "45,50" makes the box empty in Chrome, so the line is added unpriced and flagged. In other browsers it becomes NaN and gets a 400.
- "1.250" is taken as 1.25.

The Change price boxes on the same page are text read by the gateway's `parseMenuPrice` (#1252), so two boxes on one page read a price two ways. #1253 hides the add-form boxes from staff but keeps `type="number"` for owners and managers (1253:`MenuNext.tsx:224,237`).

**Open PR?** None.
