# r41 onboarding: fresh-eyes adversarial audit, "smoothly fast loading" (2026-11-14)

Opus, read-only. No stack, no browser. Production `vite build` run twice in a scratch worktree (`wt/r41-onb-perf`, removed after): once at origin/main `c459b0a12`, once at the tip of the open perf stack #1239 → #1245 → #1246 → #1287 (`perf/the-sign-in-client-loads-when-asked`, `a00b4b02a`). A config wrapper added a Rollup `generateBundle` hook that dumps every chunk's static imports and each module's rendered length. Route weight is the static-import closure of the entry plus the route's lazy chunk, summed as `gzip -9` of the built files (`measure.py` in this folder). PR file lists came from `git diff --name-only origin/<base>...origin/<head>` for all 977 open PRs (gh's `--json files` drops past 400).

The r28 and r36 audits and the r30-r40 BUILD "Left" lists are not repeated here. The app-shell-speed lane (r18-r22, QUEUE.md:802-850) owns the general entry-chunk work; this audit measures what that lane leaves on the onboarding road.

## Already fixed by an open PR (verified this round, not counted above)

- **Entry weight 827 → 274 KB on every onboarding page:** #1239 → #1245 → #1246 → #1287. This is the build above. Register, the inventory desk and the charts are out of the entry; Supabase and Sentry load later.
- **The scan read cut off at 30 s.** The web client's timeout is 30 s (`client.ts:67`), while a photo read may take up to 180 s (`scan-parser.service.ts`, `timeoutMs: 180_000`; one measured menu took 73 s). On main a medium-sized menu photo at /get-started fails as "We could not read that photo just now. Try again in a moment", and the server keeps the read, so the retry makes a second draft and a second AI spend. Fixed by #1062 (gateway reads a scan in the background, `reading: true`, and the same bytes reopen the earlier read) and #1063 (`importMenu` polls `waitForRead`). GetStarted gets the fix through `importMenu` with no change of its own.
- **Make-current writes line by line.** On main `addToInventory` makes a select and an insert per line, and `backfillMenuItemColumn` an update per line: about 3N serial round trips for the activation press. The menu lane owns this: #1101/#1102 (batched write-back) and #1376/#1377 (one-call carry, and the web waits for a long menu).
- **Register's phone library (49 KB).** The register chain tip (#1315) no longer imports `PhoneNumberInput`.

## How the open PRs fit once merged

- **#802 and #1239 are the same change.** Both are titled as perf: Register and the inventory desk lazy, the barrel off the Tremor root, no `ui` manualChunk. #802 dates from 2026-11-07; #1239 and its three follow-ups came later and are measured. Merging one leaves the other with 4 conflicts (`git merge-tree`: App.tsx, components/ui/index.ts, ToastContext.tsx, vite.config.ts). The r32/r37 merge tables list both as "clean" against main, so nothing flags the pair. #802 should be closed as superseded. This audit does not close it.
- **The menu-standing helpers** (gap 7) and **the money reads** (gap 8): see above.
- `firstProof.writeProof` returns `boolean` on the /house chain (#1591) but is called as `void` on the GetStarted chain (#1592). When both land, GetStarted ignores a refused write (r28 gap 8's cause). Type-wise the merge still compiles.

## Not done / not verified

- **No browser.** No network waterfall, LCP or CLS was recorded. The shifts in gaps 1, 5 and 9 are read from render code, not measured.
- **Byte counts are bundle-level.** `gzip -9` of the built files. Brotli on Vercel would be about 15% smaller. Parse and execute time on a phone was not measured.
- **The perf-stack numbers come from #1287 alone.** It was not built merged with the onboarding chains. The register chain cannot merge with main without hand resolution (3 conflicts), so `/register`'s weight with #1315 + #1287 is an estimate: 366 minus the 49 KB phone library.
- **Gap 6:** table size unknown; no `EXPLAIN` was run (no local DB this round).
- **Gap 10:** not profiled, and the 13 open AuthContext PRs were not read for a memo.
- **Not traced:** WebSocket/Realtime start-up for a houseless owner on /get-started. The socket is guarded on token + user (`websocket.tsx:462`) but opens before a house exists.
