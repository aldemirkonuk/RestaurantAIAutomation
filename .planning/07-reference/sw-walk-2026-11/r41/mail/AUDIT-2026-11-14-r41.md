### What was tried against the top two

- **Is the 662 ms just a cold cache?** No. It was repeated warm (688 ms people, 609 ms summary), and both spill to temp on every run.
- **Is the house so large it is unrealistic?** 12k letters is about one year at 40 letters a day across 40 vendors. The 2k house already takes 181 ms per people read, so the curve is linear, not a cliff.
- **Is it the window sort over Message-ID?** No. Run alone, that sort takes 28-108 ms with or without bodies.
- **Would an index fix it?** No. The time goes into materialising the function's result, not into finding rows (a seq/bitmap scan of 12k rows is ~25 ms). The migration's own note (`:942-946`, "No new index") rightly declined a composite index for the one-vendor read.
- **Does the Mail tab's 30 s poll dominate?** It does not, once #1580 lands. The counter runs on every page and in every tab, including tabs nobody is looking at: TanStack stops `refetchInterval` in a hidden tab, but `useHouseCounter` is a hand-written poll, and whether it pauses when the tab is hidden was not checked.

## The session's call on gaps 1, 2, 4 and 5 (2026-11-07 /goal)

Fork: how Mail stops paying for the whole history on every read.

- **(a) Chosen, first.** Narrow `mail_letter_rows` to the columns its callers need. Return `subject` (computed in the row) and no `message_text`/`email_headers`. Search reads the bodies in its own direct query over `procurement_conversations`, not through the function. Measured: 662 → 381 ms, and temp falls by half. This is a safe, local change.
- **(d) Chosen, with (a).** The gateway keeps a 15 s per-(house, withhold) memo of `mail_inbox_summary` and the waiting-people page. The Mail header, the tab label and the shell counter share one computation per house instead of one per tab per poll. This cuts gap 2 by the number of open tabs.
- **(e) Chosen.** Lists stop polling blind. Only `/mail/summary` polls, and the people, threads and thread queries are invalidated when the summary's newest-letter time (`doors.*.lastStoredAt`) or `waitingPeople` moves. That removes gap 4's serial page refetch, and gap 5's re-run of a held search, on every quiet poll.
- **Rejected (b): drop `SET search_path = ''` so the function inlines.** It would give the best plan (69 ms count-only), but every SQL function in this repo pins an empty search_path for safety, and the Supabase linter flags a function without one.
- **Rejected for now (c): a trigger-maintained `mail_thread_state` table.** It would make the list and summary cost proportional to threads, not letters. But procurement_conversations has many writers (gateway, Python agents, retention), and the waiting rule depends on marks, the withhold-by-role rule, duplicates and automatic mail. A second copy of that rule would drift. Revisit if (a)+(d)+(e) still read above 300 ms at 12k.

Gap 3 (quoted history): the gateway splits each body into `text` and `quoted`. `quoted` is the trailing block that starts at an "On … wrote:" line or a run of `>` lines, and only when that block appears in the letter before it. The thread then shows the quoted part behind "Show the quoted letter". This is decided here. It is not briefed below, because the quote detector needs its own fixtures from real vendor mail (local stack only).
