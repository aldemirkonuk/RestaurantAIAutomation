## #845/#846 — what ran (probe `sale-cost-probe.mjs`, output `results-846.txt`; controls `results-845base-control.txt`)

1. **Sale spanning two lots (2 @ 10.00 older, 5 @ 12.00, sell 3): correct.** cost_total 32.00, unpriced_qty 0, draws 2 @ 10.00 and 1 @ 12.00, older lot kept at 0, status depleted. Replay writes no second draw (the PR's proof also checks).
2. **Sale larger than stock: refused**, `stock would go negative: 4 + -9` (P0001), zero draws added, lots unchanged. Selling exactly the remainder stamps 48.00 and depletes both lots.
3. **Glass pour: NOT stamped (FIXED? no).** `record_glass_pour` 3 x 150 ml from a 3 x 24.00 lot, then 3 more: lot goes 3 -> 2 sealed + 300 ml open -> 1 + 600 ml; **zero draws**; the ledger row is `sale -1` with `cost_total NULL, unpriced_qty NULL`. By the column's own comment (migration line 122) that exact shape means "written before a_sale_carries_its_cost: unknown". So a glass sale is indistinguishable from pre-migration history forever. The PR files this (tech-debt "A glass pour stamps no cost yet") and defers it to the `one_pour_size_for_the_house` PR. Cost-of-goods (lane 3.1) would read these as legacy, not as "glass pour".
4. **Void/refund: cost does not reverse, and the bottle comes back with no price (NEW, not filed in the PR's tech-debt).** pos-hub sends a void as `+qty`, type `return`, no `p_unit_cost` (`pos-hub.service.ts:1478-1485`). Probe: sell 3 (32.00), void 3 -> a **new** lot of 3 with `unit_cost NULL`, `cost_provenance estimated`, `provisional`, received now (so FIFO sells it last); the original lots are not refilled and no draw is reversed (draw count stays 2). Summing `cost_total` over sale rows still says 32.00 with the bottles back on the shelf. Re-selling those returned bottles stamps them unpriced (4 sold: 24.00 priced + 2 unpriced). The "same lot" the user asked about is never restored; the return is an unpriced new lot.
5. **Lot cost corrected after sales (re-verify): stamps go stale and nothing restates them.** Lot booked 6 @ 20.00 provisional at the door, sold 2 (stamp 40.00, draw 20.00 provisional), `finalise_delivery_cost` to 18.00: lot is 18.00/final, the draw and ledger row stay 20.00/provisional. A second correction to 16.00 leaves draws at 20.00 and 18.00. Worse, the common path: a bottle booked at the door **with no price**, sold 3 before verification (stamp `cost_total NULL, unpriced_qty 3`), then verified at 30.00: `finalise_delivery_cost` only touches lots with `qty > 0` (`20260906233000...sql`, loop filter), so the 3 sold bottles stay unpriced permanently (the 1 left became 30.00). The draw keeps `provisional` as the "a later restatement owes a difference" marker, but nothing writes that restatement; tech-debt names "lane 2.4 restates a delivery's depleted lots too" (`2026-11-07-cost-math-2-1-lots-kept.md:15`) — unbuilt. By design "stamped when it left", but a wine sold before its invoice is verified has no cost in the books.
6. **Zero-cost lot: handled, with one distinction lost.** A `sample` lot at 0.00 sells as `cost_total 0.00, unpriced_qty 0` (not NULL), correct (free). An `invoice` lot at 0.00 is stored and stamped identically as a real zero cost (pre-existing: no CHECK refuses it). NULL stays NULL (unknown, never 0): sale of an unpriced lot gives `cost_total NULL`, `unpriced_qty 1`; mixed lot gives priced part only (8.00) and unpriced 2 (also in the PR's proof).
7. **Concurrent sales on one lot: not executable here** (PGlite is one session). Static reading only: `apply_stock_movement` takes `FOR UPDATE` on the item row, so two sales on one item serialise; the unique index `uq_inventory_transactions_idem` stops a doubled key. Unverified concern: `record_glass_pour` locks the item's **lots** (`FOR UPDATE`) but not the item row, and the sale's FIFO loop reads lots unlocked, so a pour and a sale racing on one item may stamp a draw from a stale lot snapshot. Pre-existing locking shape, but draws now record its result. Needs a real Postgres with two sessions.
8. **Rounding: sums are exact; lot precision is the limit.** Ledger `cost_total` equals the sum of `qty x draw.unit_cost` on every row (0 mismatches over 5,000+ rows); `unpriced_qty` equals the NULL-cost draws (0 mismatches). But a lot's `unit_cost` is `numeric(10,2)` (baseline) and the draws copy it, so there are not 6 decimals anywhere: a 142.00 case booked at 11.8333 stores 11.83 and selling all 12 stamps 141.96 (0.04 short per case). The PR's own spec accepts "11.83, what a two-place lot cost keeps". Pre-existing, inherited.
9. **Tenant scope: holds.** A movement naming house 1 for house 2's item is refused 42501 before anything is written; draws carry the item's house (0 rows where draw house differs from lot or ledger house); no client role has a grant, RLS on, service_role has SELECT and INSERT only (PR proof, plus mine). Direct DELETE of a draw by a superuser is refused (55000). Deleting a ledger row cascades its draws away (allowed by the depth > 1 exception): the cost history goes with the ledger row, same as any cascade.
10. **Performance, 5,000-line import: fine.** 0.71 ms/sale vs 0.67 on the base (PGlite). Worst case, one sale draining 3,000 one-bottle lots: 9.9 s head vs 9.5 s base — the array appends are not the cost.

## #844 — what ran (probe `r12-844-probe.spec.ts`; outputs `results-844-wt72.txt` PR, `results-844-control816.txt` base)

- **A. Accepted proposal with a case price: works.** 240 on a `case`, pack 12, line posts **20.00**, provenance `manual`, basis "accepted proposal: price 240 per case of 12 = 20.0000 per bottle"; with a printed `case` base also 20.00. Base posted 240.
- **D1. Proposal keyed to the door-count line is still read per bottle (partial fix).** Door-count lines carry no money (uom bottle, pack 1 in my fixture). A per-case counter of 240 keyed to such a line posts **240 per bottle** (12x). The existing spec says the live drive found proposals keyed to the door count (`delivery-stock.service.spec.ts` "keyed to the DOOR COUNT"). I fabricated that line's uom/pack; whether real door-count rows carry `bottle`/`1` was not confirmed from code. The PR's fix converts in "its line's price base", which a money-less line does not have.
- **D2. A proposal restates in the line's base, not per bottle.** A per-bottle counter of 20 on a case line posts 1.67 (12x under). Documented on the DTO as the fork; no web or mobile caller sends the field, so API callers only.
- **C. Over-refusal.** `24 bottle @ 264, pack 12, total 6336` prices fine alone (264, invoice). With an accepted proposal of 250 on that same line the proposal is **refused** and the item held provisional, because the proposal path passes no `qty_bottles`/`line_total` to `perBottleLotCost` (`delivery-stock.service.ts:817-823`). Safe direction, but the total that decides the invoice line is ignored for the proposal, and the refusal also deletes the valid invoice price.
- **Refusal message — API yes, UI no.** `costNote` carries a per-item sentence (e.g. "the invoice prices this item, but not per bottle: the accepted proposal's price 250 is read in its invoice line's unit, and ... whether 250 is a bottle's price or a case's is not known. The lot stays provisional.", via `delivery.service.ts:984-1004`). The only web caller, `CanonicalDocumentPage.tsx:559` `deliveryWrite(() => deliveriesApi.verify(...))`, awaits and **discards the result**; no file under `apps/web/src` or `apps/mobile/src` renders `costNote` or `stillProvisional`. A manager sees nothing: the lot just stays provisional. This is the "visible to user" test, and it fails.
- **Wording.** For `uom each` the refusal reads "counts eachs that come 12 to a case" (pinned by the PR's own test). Cosmetic.
- **K. Self-consistent mislabel stays priced wrong.** A case row stored as `bottle`, qty 2, pack 12, total 528, price 264 passes the total check (264 x 2 = 528) and posts 264 per bottle. The total can only catch a disagreement; it cannot catch a row whose unit was misread consistently. Tolerance is max(0.05, 1%): totals 6280 and 6400 pass for 24 x 264, 6272 and 6000 refuse.
- Edge outcomes: a proposal of 0 or -5 is skipped and the invoice price stands (22.00); 0.04 per case rounds to 0.00 and is refused by name; a string `"240.50"` posts 20.04; two accepted proposals: the later one wins (21.00); unknown units (`btl`, `unit`, `carton`) are refused by name.
