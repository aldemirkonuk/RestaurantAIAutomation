# r24 door-count — build report (2026-11-13)

## The problem the house saw (r23 walk)

Counting an invoice at its own door booked nothing. The web sent no item ids, so the gateway answered 201 and made 0 lots. The delivery it made held only the count: neither the invoice nor its order. After a reload the invoice still said "Nobody has counted this yet". Separately, `/receiving/<order>/door` said "5 bottles" for a 5-liter order.

## Audit (root causes, file:line on the base branches)

1. **Web, `DoorFrame` submit.** It built lines from `layer1` only (description, unit, size) and sent no `inventoryId` and no link to the paper line. `bookAtTheDoor` skips a line with no item, so 0 lots were made.
2. **Web, `CanonicalDocumentPage` `onSubmitCount`.** It sent `createDelivery` with no order and no paper. `POST /procurement/documents/door-count` then made a delivery whose only document was the `door_count`. With no vendor-side paper on it, `agree` rule A could never pass, so VERIFIED (which prices lots from role=invoice lines) could not run.
3. **Gateway, canonical read.** `buildFromDocumentId` never filled `spine[i].received`, so the paper could not read back a count made on it. That is why it said "Nobody has counted this yet" after the reload.
4. **Web, `DoorModel`.** It treated every order line as bottles: `expectedBottles = qty`, so a 5 L order showed as 5 bottles.
5. **Double count (found while fixing 1–2).** The legacy order door books lots through `door-receipt:` / `order-delivered:` with `delivery_id` null. Once the paper's door books for the same order, the same goods would be on the shelf twice.

## Decisions (the session's calls, under the 2026-11-07 /goal; also in the PR bodies)

- **D1. The paper is the truth.** The client names the paper line by id (`sourceLineId`). The server copies item, unit, size and line number from that row.
  - Rejected: the client sends `inventoryId`. It can disagree with the paper, and VERIFIED prices by the line's own `inventory_id`.
  - Rejected: matching lines by description. Two lines can share a name.
  - Rejected: booking straight from the invoice with no count. That would erase the door-count side of rule A.
- **D2. The delivery carries the count, the paper (role invoice, or despatch_advice for a packing slip or delivery note/receipt), and the paper's one order.** If the paper already sits on one open delivery, that delivery is used. If it sits on more than one, the request is refused with 409 before anything is written.
- **D3. A paper with no order is countable (UNORDERED).** Rejected: refusing it, because buying at the market is real. A paper linked to several orders is refused unless `orderId` names one of its own orders.
- **D4. The order-door guard refuses rather than subtracts.** If the order's own door already booked an item, the paper's door does not book that item and says why in `notBooked`.
  - Rejected: subtracting. A partial subtraction hides which door is wrong.
- **D5. The door books by the line's own pairing only, never a pairing inherited from the order.** VERIFIED would never cost an inherited pairing, so those lots would stay uncosted. The web warns on an unpaired line instead.
- **D6. A measured order is redirected to its paper's door** and not converted at the box door.
  - Rejected: teaching the box door volume math. That would make a second door for the same goods.
