## Decisions (the session's call, under the 2026-11-07 /goal)

1. **Seen is stored per person, house, vendor and thread as a LETTER time, not the clock.**
   - The mark keeps least(time shown, thread's real newest letter). A letter arriving between the read and the mark therefore stays new, and a caller cannot mark past the letters that exist.
   - Rejected: a per-letter seen row. One row per letter per person grows without bound.
   - Rejected: a now() timestamp. A letter that lands mid-read would be hidden.
   - Rejected: localStorage. It does not follow the person across devices, and Claude/agents cannot read it.
2. **Unknown is null, never false.**
   - A failed seen-read gives `newToYou: null` per row, and no chip is drawn ("absence reported as health" rule).
   - A row whose last letter is the house's is `false`: nothing new from the vendor.
3. **Person row rule: the vendor's newest letter is newer than max(seen over its threads).**
   - Known limit: if the house wrote last on the newest thread, an older unseen thread does not light the person row. The thread row still shows it.
   - Rejected: per-thread aggregation in SQL for the people page. It costs another RPC over every thread; deferred until someone hits it.
4. **Dates use the house zone from `/mail/summary`, which is already read.**
   - Rejected: a new zone endpoint, which adds a request.
   - Rejected: the browser's zone, which is the bug itself.
5. **Tour: role-neutral wording naming both chips.**
   - Rejected: role-aware tour steps. `TourStep.description` is a plain string, and the change would reach TourEngine for one sentence.

## Browser checks for the walker (local stack only, never production)

Setup:
- Build a walk branch that has both chains: check out `fix/mail-shows-what-is-new-to-you-web` (#1630), then `git merge origin/fix/mail-knows-what-each-person-has-seen-gw` (#1615, which carries #1614's migration), `origin/fix/mail-dates-say-year-and-house-time` (#1643) and `origin/fix/mail-tour-says-who-a-vendor-waits-on` (#1644).
- Start it with `local-stack.sh up <wt>`, so migration `20271118100000_mail_remembers_what_each_person_has_seen` is applied.
- You need one vendor whose newest letter is inbound. If none exists, insert one into the LOCAL DB:
  ```sql
  insert into procurement_conversations (restaurant_id, provider_id, direction, channel, message_text, status, thread_key, received_at, created_at, email_headers)
  select restaurant_id, provider_id, 'inbound', 'email', 'Walk check: new prices attached', 'DELIVERED', 'walk:new-1', now(), now(), '{}'
  from procurement_conversations where provider_id is not null limit 1;
  ```
- For check D, also insert one letter dated last year:
  ```sql
  insert into procurement_conversations (restaurant_id, provider_id, direction, channel, message_text, status, thread_key, received_at, created_at, email_headers)
  select restaurant_id, provider_id, 'inbound', 'email', 'Walk check: last year', 'DELIVERED', 'walk:old-1', '2025-11-13 09:00+00', '2025-11-13 09:00+00', '{}'
  from procurement_conversations where provider_id is not null limit 1;
  ```

A. "New" appears and leaves (role: owner).
1. Open `/communications?tab=mail`.
2. Expect: the vendor row with the walk letter shows a small chip reading exactly `New` (testid `new-to-you`) beside the name.
3. Click the vendor. Expect: the thread row "Walk check: new prices attached" (or its subject) shows `New`; other threads with no vendor letter after your last visit do not.
4. Open that thread. Expect: in DevTools Network, one `POST /mail/thread/seen?key=walk%3Anew-1&with=vendor%3A<id>&through=...` with status 200. The response has `seenThrough` equal to the letter's received_at.
5. Go Back to the person, then to the list. Expect: no `New` chip on that thread or on that vendor row.
6. Reload the page. Expect: still no `New`, because the mark is stored server side.
7. Open the same thread again. Expect: no second seen POST for the same letter.

B. Per person (role: staff, then manager).
1. Sign in as a different user of the same house (staff).
2. Open `/communications?tab=mail`. Expect: the same vendor still shows `New`, because the owner's read is not this person's.

C. A newer letter lights it again (role: owner).
1. After A, insert another inbound letter in `walk:new-1` with `received_at = now()`.
2. Reload `/communications?tab=mail`. Expect: `New` is back on the vendor row and on the thread.

D. Dates (role: owner, house zone e.g. Europe/Istanbul; set the browser to another zone if possible).
1. On `/communications?tab=mail`, open the vendor that has "Walk check: last year".
   - Expect the thread row date reads `13 Nov 2025`, with the year.
   - A letter from today reads as a time only, e.g. `14:05`.
   - One from earlier this year reads `D Mon`, with no year.
2. Open the last-year thread. Expect the letter time reads `13 Nov 2025, 12:00` (09:00 UTC in Istanbul). It must not read in the browser's zone.
3. Mark a letter "needs no reply". Expect `Marked as needing no reply, <D Mon>.` using the house's day.

E. Tour wording (role: staff).
1. On `/communications?tab=mail`, start the page tour (the guidance "?" / tour button).
2. On step "Mail by person", expect the text: `"Waiting on you" (or "Waiting on the house", if you cannot answer vendors) keeps only the vendors waiting on a reply.`
3. The staff chip on the page reads `Waiting on the house`.
