## Additional findings from the expanded review

### Native approval has not adopted the server's required seal

**P1 functional compatibility defect, static proof.** Native Supply enqueues `POST /procurement/orders/:id/approve` at `app/(tabs)/supply/[id].tsx:44`. The outbox sends only method/body/idempotency key (`src/state/outbox.ts:178`), and its API wrapper has no arbitrary-header option (`src/api/client.ts:22-55`). No `seal-challenge`, `X-Seal` or `x-seal` call exists in current mobile app/src. Gateway `procurement.controller.ts:439-463` reads `X-Seal-Challenge`; `procurement.service.ts:3465-3473` unconditionally redeems it before updating. This approval flow therefore cannot succeed against the audited gateway as written, even for a permitted actor. None of the pure mobile tests proves this HTTP contract. A repair should preserve the intended contemporaneous approval challenge rather than turning off the gateway's gate.

### Native priced receipt cannot pass the current currency gate

**P1 functional compatibility defect, isolated validation.** The screen pre-fills `invoiceUnitPrice` from the order when present (`app/(tabs)/cellar/receive/[orderId].tsx:40-42,95-101`) and includes it in the outbox body without `invoiceCurrency` (`:148-165`). Gateway `procurement/dto/procurement.dto.ts:499` validates the pair; service `procurement.service.ts:4875-4898` repeats the refusal before any write. [Exact-source DTO reproduction](mudavym-2026-09-13-reproduce-native-receipt-currency.cjs) rejects the native-shaped priced body, accepts an explicit real currency, and accepts count-only. No actual HTTP or stock write ran. Currency must come from stated evidence/user choice; silently assuming the house currency would create another defect.

### Door-to-desk receipt reconciliation can multiply the prior stock twice

**P1 arithmetic defect, isolated reproduction plus service tracing.** Door receipt writes `quantity_received` in bottles (`gateway/procurement/receiving.service.ts:543`), while desk `verifyReceipt` passes the same field as `stockedQtyInCountedUom` (`procurement.service.ts:4959,5039-5056`). With no counted unit stated, case-order conversion multiplies that already-normalized quantity again. [Exact-source reproduction](mudavym-2026-09-13-reproduce-receipt-unit-delta.cjs): five cases × twelve, already-booked 60 bottles, accepted five cases → interpreted prior stock 720 bottles, `ledgerDelta=-660`, `requiresOverride=false`. This occurs with no invoice; a matched-invoice arithmetic variant does the same, though service acceptance of a priced variant separately requires valid currency. Service then attempts its stock-adjustment RPC for a nonzero delta (`procurement.service.ts:5080-5114,4610-4705`). Database acceptance and actual stock impact were not tested. The server's own unit comments acknowledge this unresolved representation; frontend warnings do not remove it.

### Native receiving names bottle counts but sends order-unit quantities

**P1 candidate requiring isolated unit fixtures.** The screen explicitly offers “Each barcode read accepts one bottle” and increments `acceptedRaw` without reading barcode content (`app/(tabs)/cellar/receive/[orderId].tsx:128-133,368-385`). Yet it omits `countedUom` and `invoiceUom`, with a comment saying omitted means the order's own unit (`:148-165`); it also labels `order.quantity` as bottles (`:258`). A case order therefore needs explicit conversion/declared units before bottle scans are meaningful. Existing pure invoice-match tests do not establish the screen-to-gateway unit contract. Test a two-case, twelve-bottles-per-case order with partial acceptance and rejection before calling this native flow ready.

### Dashboard month cache can show the previous house when mounted across a switch

**P2, isolated control-flow reproduction.** `useMonthLedger` caches by `year-month` alone (`web/pages/dashboard/next/useDashboardNextData.ts:161-171`); cache hit returns before checking/fetching restaurant. Normal remote flag transitions may unmount/remount the page and clear the hook; a browser override that keeps the redesign mounted avoids that accidental protection (`lib/mudavym/useMudavymDesign.ts:127-130`). The isolated [reproducer](mudavym-2026-09-13-reproduce-dashboard-month-cache.cjs) uses exact source and fake React hooks/API/window: load A=100, rerender B in same month, displayed value remains 100 and API requests contain only A. No real HTTP request or browser state was used. House must be part of cache identity, or cache reset must be an explicit invariant.

### Native honesty and parity are behind the current web redesign

Current native Insights hardcodes dollars and can conflate unavailable queries with absence; Team calls a failed week read an unconfigured team. Native Draft uses only cached feed content. Native settings persists service preferences, with push registration errors swallowed. These are concrete scope/quality limits, not proof that underlying API operations always fail.
