## Patterns that affect implementation order

1. **One operational loop, several product surfaces.** Procurement writes, door count, document adjudication, credits and analytics have different pages and owners. Verify the joined event rather than certifying each screen independently.
2. **The two web renders can disagree.** The old page may retain controls missing from the new one; the new page may enforce tenant caching/error states the old one lacks. Reconcile both renderings until the old route is retired.
3. **A proposal needs a record before judgment.** Preserve original extraction and model suggestions, append the human answer and actor, and retain rejected/superseded distinctions. Otherwise the purported learning data loses the machine half exactly when a label becomes useful.
4. **Absent, failed, zero and capped are different facts.** Repeated defects are successful-looking emptiness, false all-clear, unmarked limited windows and configured-provider mistaken for healthy-provider. The newer ADRs/guards address this class, but current swallowed-read baseline still carries 185 sites in the code audit.
5. **Reachability is part of a capability.** A standalone recurring page remains unrouted, while current Orders has actual recurrence controls. The surface and version must be named; an endpoint declaration alone is not a usable feature.
6. **The same noun is not the same stream.** Procurement spend is not revenue; a price quote is not a settled invoice price; an opened/requested credit is not recovered money; a simulator is not a real POS merchant; an action disposition is not execution.
7. **A recorded closure is not data repair.** Generic wine links, historical alert timestamps and seeded wages/prices can remain after code is corrected. Never overwrite those rows without a separately scoped evidence-backed repair.
