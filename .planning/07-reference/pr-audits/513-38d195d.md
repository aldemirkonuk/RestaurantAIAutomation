## Blocker: F1 is real, introduced by this diff, data-changing, and not disclosed
I checked this against the SHA directly, not only from the adversary's report.
- CalendarNext.tsx:358 `openEvent = (event) => setSheet({ mode: 'edit', event })` passes the drawn occurrence itself to the sheet.
- EventSheet.tsx:125 seeds `date` from `editing.date`, which for an occurrence is that occurrence's key (expand-series.ts: `date: key`, `endDate: keyOf(n + span)`).
- EventSheet.tsx submit (about :166-199) always puts `eventDate: date` (and `eventDateEnd` when not all-day) in the PATCH, sends it to `{ id: editing.seriesId }`, and has no `updateScope`.
- calendar.service.ts updateEvent at this SHA: `if (dto.eventDate !== undefined) updatePayload.start_date = dto.eventDate;`. The scoped branch needs `existing.parentEventId && dto.updateScope`. A series master has no parentEventId, and the web sends no scope, so the branch is skipped and the master's start_date is overwritten.
- Effect: opening a later date of a weekly series and fixing only its title moves the series' start date to that date. Every earlier date disappears from the book, and an after_count series restarts its count and runs past its intended end. Nothing records the old start date, so it can only be restored by someone who remembers it.
- Reachability on main: the list returned no recurrenceRule (on main, only create/getEvent attach it: calendar.service.ts:226,265). The legacy expander on main (lib/calendar/recurrence.ts:236-250) falls back to the stored row when it has no rule, so the sheet only ever held the master with its own date. The exposure is new with this PR, because this PR is what makes later dates drawable and openable.
- The warning at EventSheet.tsx:252 ("anything saved here changes the whole series") suggests the fields apply to every date. It does not tell the user the series will start again on the date they opened. The TECH-DEBT "Not done" list and the CLAIMS entry do not mention it, and no test opens and saves an occurrence (the only isOccurrence:true fixtures are MeetingNote.test.tsx:183 and the series test's expansion assertion).
- Why it blocks rather than being accepted as a follow-up: it is a silent, destructive write reached by the most common action on the feature this PR ships. It is undisclosed, so accepting it would mean acting on an undisclosed partial result (CLAUDE.md §0.5). Only the founder could accept that risk, and no agent message can. The fix is small: for `editing.isOccurrence`, leave out eventDate/eventDateEnd unless the user changed the date field (or send the master's stored date), plus one test that saves an occurrence's title and asserts the patch has no eventDate.
