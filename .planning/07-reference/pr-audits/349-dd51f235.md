## 1. Security & production blast-radius — BLOCK

### 1.1 Critical — Playwright traces leak the plaintext test password and session JWTs to a 30-day artifact on a PUBLIC repo

`apps/web/playwright.nightly.config.ts:49` sets `trace: 'retain-on-failure'`. A Playwright
trace is a full network capture (request/response headers and bodies), and this nightly
runs at a **127-of-130 historical failure rate** — a failed run producing a trace is the
common case, not the edge case.

**Independently reproduced by this session**, not only asserted:

- `gh repo view --json isPrivate,visibility` → `isPrivate: false`, `visibility: PUBLIC`.
- A failed run's own trace (from earlier work in this session) already contained
  JWT-shaped strings in `0-trace.network`, `1-trace.trace`, `test.trace`,
  `1-trace.network`.
- A deliberate sentinel test — `E2E_TEST_PASSWORD='PW_SENTINEL_ZQ7X_DO_NOT_MATCH'`,
  `npx playwright test --config=playwright.nightly.config.ts --grep precondition` —
  failed at login exactly as designed, and the sentinel string turned up verbatim inside
  `test.trace`, `0-trace.trace`, and
  `resources/d67c8bfc4a6e8ad24e72cac7b63584aceb0bb8e4.json`.

The workflow (`e2e-prod.yml`) uploads `test-results/` (and `apps/web/test-results/`) as a
30-day artifact. The first real nightly run against production — the moment the
founder's secrets land — would upload a trace containing his own credentials and live
session tokens to a public GitHub artifact.

**Fix:** `trace: 'off'`. This alone clears the blocking finding. (`screenshot:
'only-on-failure'` is fine — a screenshot does not carry headers or bodies.)

**Leaked local traces from this session's own sentinel run were deleted** —
`rm -rf apps/web/test-results/nightly-traces apps/web/test-results/nightly` — before this
report was written. Nothing was pushed; the exposure this finding blocks is what the
*first CI run* would do, not something already public.

### 1.2 High — `API_GATEWAY_URL`'s host is unguarded

`e2e-prod.yml` guards `E2E_BASE_URL` against `localhost`/`127.0.0.1` (`case "$E2E_BASE_URL"
in *localhost*|*127.0.0.1*) … exit 2 ;; esac`) but has no equivalent guard on
`API_GATEWAY_URL` — the URL that actually receives `E2E_TEST_EMAIL` /
`E2E_TEST_PASSWORD` on every login. A misconfigured `workflow_dispatch` (or a future
edit) pointing `API_GATEWAY_URL` at a local or third-party endpoint would leak
credentials to it with no guard catching the mistake before the request goes out.

**Fix:** the same `case` guard, applied to `API_GATEWAY_URL`.

### 1.3 Medium — `E2E_LEGACY_RESTAURANT_ID` is unconstrained

Once F3 is implemented (a second sim house for the legacy pass, per the founder's
relayed answer — see ADR 0135), whatever restaurant id is passed there gets walked and
screenshotted with real session cookies. Nothing in the current diff constrains it to a
`sim-` slug. If a future session (or a fat-fingered `workflow_dispatch` input) points it
at a real production house, the nightly would screenshot that house's actual data on
every run and upload the screenshots as an artifact.

**Fix:** resolve the id through `GET /api/v1/organizations/branches`
(`apps/web/src/contexts/AuthContext.tsx:365` reads this shape already) and assert its
slug matches `sim-%` before walking it; `cannot_check` otherwise. Apply the same
constraint to the primary sim-owner house for symmetry.

### 1.4 Low — `nightly_summary.py::_load_json` crashes rather than reporting `cannot_check`

A malformed or truncated JSON artifact (a JUnit XML the browser step died mid-write, a
truncated `wave_h_checks.jsonl`) raises inside `_load_json` and the whole summary step
fails — which the workflow then reports upstream as "Production E2E failed" rather than
the more honest "the summary itself could not read its own inputs." Not a security hole,
but it is exactly the [[absence-reported-as-health]] shape this whole ADR exists to
avoid, one level up: a crash in the *reporter* reads as a product failure.

**Fix:** wrap the read in `try/except`, record `cannot_check` with the exception text as
the reason, and continue merging the other sources.

### 1.5 Suggested hardening (not required to clear BLOCK)

A `page.route('**', route => { if (route.request().method() !== 'GET') { record
cannot_check/fail; route.abort() } else route.continue() })` interceptor would make the
suite's "read-only" claim something Playwright itself enforces, rather than only
something the manifest and the author's care promise. Worth doing once the P0 fixes
land; not blocking.

### What this angle could not check

- The actual behavior of a real production run — no such run has happened
  (`aldemirkonuk@mudavym.com` does not yet exist in `public.users`).
- Whether `RAILWAY_ORCHESTRATOR_URL`'s stored *value* already points at the corrected
  host (`servicesagent-orchestrator-production.up.railway.app`) — the secret's value is
  unreadable from a session; only its presence is confirmed (`gh secret list`).

## 2. Correctness & regression risk — APPROVE WITH NOTES

Full auditor report (verbatim, condensed only by removing what is repeated above):

> I considered BLOCK and did not land there. **What I checked:** the full diff (24
> files) read against the code it touches — `App.tsx`, `ErrorBoundary.tsx`,
> `useMudavymDesign.ts`, `rate-limit.guard.ts`, `pytest.ini`, `ci.yml`/`deploy.yml`. I
> traced `walk()` end-to-end for both modes, exercised `nightly_summary.py` on synthetic
> corpora, broke both pinned fixtures on purpose and confirmed red, listed the
> dev-server Playwright corpus, and collected Wave H with no gateway env. **What I could
> not check:** anything requiring a real production run.

**Finding 1 (the significant one) — `absent` is inferred from an absence of evidence,
states a cause it never verified, and discards the one contrary signal it had.**
`nightly.spec.ts:280-283`: when the override is on and no `.mudavym` root renders, the
walk records `absent` with the reason `"...no root rendered (legacy showed)"` —
"(legacy showed)" is asserted, not checked, and `continue` skips the uncaught-error
check at `:324-326`. Concrete failure scenario: an App-root `ErrorBoundary`
(`App.tsx:151`) with no route-change reset trips on any render throw and never
recovers; every one of the 19 pages then records `absent`, and `absent` is **not in the
verdict expression**:
```python
# nightly_summary.py:403-407
verdict = "cannot_check" if counts["cannot_check"] else ("fail" if counts["fail"] else "pass")
```
→ exit 0 → the Sentry deploy-gate alert stays silent. The whole redesign can be down and
the alert channel reports silence as health. **Why not BLOCK:** confined to a
non-blocking observability workflow, changes no runtime path, and the blind spot is
latent behind the orchestrator preflight (guarantees exit 2 tonight regardless). Cheapest
fix: a pinned `expected_gated` floor in `manifest.json` (11 of 19 routes use `PageGate`
on `main` today) with one `recordAndAssert` when fewer render a `.mudavym` root.

**Finding 2 — a 5xx from a list endpoint is recorded `absent`, not `fail`.**
`lib.ts:438-440` returns `route: null` on any non-2xx, collapsed into `absent` by a
comment that is only true of the *other* null path. Not hypothetical: the ADR's own
measured run found `/reports/schedules` answering `500`. Fix: distinguish `!res.ok()` →
`cannot_check`/`fail` from an empty list → `absent` at the call site.

**Finding 3 — the legacy walk has no landing check** (non-blocking; disproved as a false
green — every path that would produce it also fails the next-walk test, so the run is
already red; still worth adding `landed === routePath` to the legacy branch).

**Finding 4 — the one alias assertion in the manifest is wrong and unreachable.**
`manifest.json:62` expects `/cellar` → `redirect:/wines`; neither route exists on
`main`, and the assertion never runs because `cellar` always lands in `absentOnBuild`
first.

**Finding 5 — `denied` matches the bare substring `"403"`** (`manifest.json:9`), which
can silently disarm `/settings`' only `provenance_required` assertion.

**Finding 6 — `AuthBudget` measures roughly half the auth traffic** (only
`page.on('request')`, missing the `APIRequestContext` calls in `mintSession`). Failure
mode is a 429 → `cannot_check` → red, so it cannot produce a false green — it just means
the pacing `pass` row proves less than it claims.

**Finding 7 — coverage lost by retiring `prod-smoke.spec.ts`, enumerated:** login
redirect — covered, improved. `/admin/health` ≥7 agent cards — **nothing covers this
now**, a real gap. Dashboard <5s timing — **nothing covers this now**. Console-error
check — partial (uncaught `pageerror` only, and skipped on the Finding-1 `absent` path).
`/studio` write flow — nothing, **deliberately** (it wrote to production).

**Verified correct:** `testIgnore` change (15 tests, 4 files, nothing from `nightly/`);
both pinned fixtures are real drift assertions (proven by breaking each); `conftest_prod.py`
teardown is genuinely disarmed (the pre-PR line would have deleted all four production sim
houses on the first service-role-key run); Wave H skips safely under push CI and a skip
cannot read as a pass downstream; the empty-corpus guards are real; `absent-on-build.json`
cannot leak across CI runs; zero production runtime code in this diff.
