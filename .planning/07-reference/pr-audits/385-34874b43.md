## Round 1 — three independent Opus angles missed a critical logical inconsistency

Correctness, compliance and security each read the diff, ran the guards
(`check_adr_numbers_unique.py`, `check_decision_claims.sh`), and exercised the build
locally (`tsc`, vitest, `vercel build`). All three leaned APPROVE WITH NOTES: the
design was sound, the ADR was complete, and two genuine Vercel-platform bugs
(`middleware.ts` ESM import extensions; a `process` type reference failing Vercel's
isolated middleware type-check) had already been found and fixed by testing directly
against a live preview deployment — invisible to `tsc`/vitest/eslint alone.

**None of the three caught that `robots.txt` disallowed the sitemap it advertised.**
`CRAWL_PREFIXES` (`apps/web/src/lib/seo/routes.ts`) had no entry for `/sitemap*`, so
every robots group's own `Disallow: /` closed the exact file the `Sitemap:` directive
pointed at — the build's whole point (making the crawl surface discoverable) was, by
its own robots.txt, unfetchable by any compliant crawler. The mandatory adversarial
pass (step 7 of this skill) found it: `grep -i sitemap dist/crawl/robots-mudavym.txt`
showed the bare `Sitemap:` line with no covering `Allow:`. **Verdict: OVERTURNED.**

## Fix

Added three `CRAWL_PREFIXES` entries (`/sitemap.xml`, `/sitemap-pages.xml` open to
`everyone`; `/sitemap-vendors-` gated `answer`-only, matching `/v/`'s own split-by-
purpose rule) with the reasoning recorded inline (`routes.ts:120-134`) and in ADR
0158's "Known limits" section. Proved against the regression: temporarily removed the
three entries, watched the new capability-based test
(`seo.test.ts`, "every group may fetch the sitemap the file itself advertises") fail,
restored them. Added a permanent guard: `scripts/crawl_surface_census.py`'s
`check_robots_permits_sitemap()`, which parses the first `robots.txt` group and the
`Sitemap:` line and asserts an `Allow:` line covers it — this check's own first
version had a bug (stripping `$` before `startswith` made the anchored rule
`Allow: /$` match every path), caught by testing both the buggy and fixed robots.txt
as fixtures side by side before trusting it.

## Round 2 — post-fix adversarial re-audit

Re-ran the adversary against the fix with all three round-1 reports plus the new
diff. One remaining inaccuracy: the code comment and ADR both claimed the sitemap
index "names nothing a reader could not already fetch directly" — false, since the
index *does* list the vendor sitemap's URL, which a training crawler can see (from
the index) but not fetch (the vendor file itself is `answer`-only). Fixed as a
documentation-accuracy correction (no functional change): the comment and ADR now
state the narrower, true reason the index itself is open to everyone — `Sitemap:` is
a single directive with no per-group form, so it cannot itself be gated, and this
costs nothing today because the index carries no vendor slugs, only filenames.
**Verdict: HOLDS.** No further findings.
