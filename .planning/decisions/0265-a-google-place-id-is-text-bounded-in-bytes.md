## Context

The owner-quarter sim (2026-10-02, F-006, a BLOCKER) could not create a house on /get-started. The owner picked a street address from the Places autocomplete, and the insert failed with "value too long for type character varying(100)". The XHR capture measured that `googlePlaceId` at 128 characters. That is **one** measured id: it shows a street-address Place ID can be longer than 100 characters, not that every one is. Google documents no maximum length.

`restaurants.google_place_id` was created `varchar(100)` by `supabase/migrations/20260807001252_distributor_geo_foundation.sql:52` and never widened. Its only dependent is the partial unique index `idx_restaurants_google_place_id` (same file, :65-66), measured with `pg_depend` on a PGlite build of every migration. A btree entry over 2704 bytes is refused with 54000. As of this record the only writers are the two gateway sign-up inserts (`apps/api-gateway/src/auth/auth.service.ts:1703`, `:1846`), both fed by `coordinateColumns` (`:1517-1543`).

[2026-10-03: the line numbers above are as of 8c673db4b. Since F-006 PR 2 the two inserts are one, `AuthService.insertHouseRow`, called once from `createFirstHouse` and once from `registerRestaurant`, and still fed by `coordinateColumns`. [Superseded in part 2026-10-08, see the amendment below: `insertHouseRow` is now called by `createFirstHouse` only; `registerRestaurant` looks the place up and inserts inline, refusing a held place. Both are still fed by `coordinateColumns`.] Cite these by name; claim F006-NO-ROUTE-READS-THE-PLACE-ID keeps the column's writers and readers to this list.]

## Options considered

1. **Leave `varchar(100)`.** F-006 stays a BLOCKER for any owner whose pick has a longer id. Rejected.
2. **A wider `varchar` (255, 512).** Still a guess against an id Google gives no maximum, and the next longer id fails the same way, as 22001. Rejected.
3. **`text` with no bound.** The simplest change, and what the triage line literally says. An *incompressible* value of about 2.7 KB fails 54000 inside the index, a raw error that names no constraint. [CORRECTED 2026-10-03: this said "At about 2.7 KB a value fails 54000". The audit gate on PR #593 (run at fe5215837; its report is p4-scratch/audits/593-fe5215837/report.md:33, outside the repo) found that true only for values that do not compress; a value that compresses well is stored compressed in the index entry and passes.] No real Place ID is near that, but a client can send one. Rejected narrowly; this is the main alternative, and F1 puts it to the founder.
4. **`text` with a `char_length` bound.** A character bound does not hold a byte limit: 683 three-byte characters are 2049 bytes, and about 902 of them pass 2704. Rejected.
5. **`text`, with the unique index moved onto a hash** (`md5(google_place_id)`). Removes the size limit from the index altogether. It changes the index that the recorded shared-place ruling keys on (23505 on `idx_restaurants_google_place_id`), and it pulls the open one-house-per-place question into a migration that should not touch it. Rejected for now.
6. **`text` plus `CHECK (google_place_id IS NULL OR octet_length(google_place_id) <= 2048)` (chosen).** 2048 bytes is 16 times the one measured id. It sits below 2704 with room for the index tuple's header, so every value the CHECK admits fits the index. A value past it is refused as 23514 under a constraint name the gateway can put into plain words.

## Decision

`restaurants.google_place_id` becomes `text`, bounded by the named CHECK `restaurants_google_place_id_length` at 2048 bytes (`octet_length`, not `char_length`). What carried it: Google sets no maximum, so a width is a guess. The index sets a hard byte limit, so a bound in bytes keeps the refusal named instead of raw.

## Consequences

- **Easier.** Any id up to 2048 bytes is stored whole. A refusal past it is a named 23514, not a 22001 or a 54000.
- **Given up.** An id over 2048 bytes would be refused, although Google documents no maximum. Until the wording change maps it, the owner would see the raw message. **Revisit when** a 23514 on `restaurants_google_place_id_length` appears in production logs, or Google publishes a length. [2026-10-03: the founder accepted this window, verbatim: *"Merge now, PR 2 follows (Recommended)"*. PR 2 (branch fix/onboarding-shared-place-f006) maps every refusal to a fixed sentence; see Amendment.]
- **23505 reaches more owners. Sequence this before merging.** The database refuses duplicates exactly as before. But an id over 100 characters used to die at 22001 before the index saw it, so two houses picking the same such address (a food hall, a hotel with several outlets) could not collide. After this migration the second one gets 23505. As of this record both sign-up paths pass the raw database message to the browser: `auth.service.ts:1758-1762` ("House creation failed: …", read by `GetStarted.tsx:169`) and `:1959` ("Registration failed: …", read through `AuthContext.tsx:767-769` by `Register.tsx:1107`). The second path is the **public** register route. The founder's ruling for a shared place, 2026-10-02, verbatim: *"Open it, keep the pin (Recommended)"*. It is recorded as: open the house with latitude and longitude and no place id, and say nothing about another house. That is the separate wording change. So either land that change in the same merge window, or have the founder accept the window explicitly.

  [2026-10-03: the window was accepted explicitly (verbatim under **Given up**), and PR 2 lands the ruling; see Amendment. The lines cited here are as of 8c673db4b. Both catches now end in `refuseHouseOpening` (in `AuthService.createFirstHouse` and `AuthService.registerRestaurant`), and the web shows its own sentence, `houseNotOpened` in `apps/web/src/lib/houseOpeningWords.ts`, never the gateway's text.]
- **Lock.** The ALTER takes ACCESS EXCLUSIVE on `restaurants`, which nearly every request reads. With no `lock_timeout` (no migration after the baseline sets one), a long or idle-in-transaction session holding a lock on `restaurants` queues every later `restaurants` query behind the ALTER for up to the migration's 120 s `statement_timeout`. The migration then fails and has to be re-run. Before merging, check `pg_stat_activity` for such sessions. Adding a first `lock_timeout` is a repo precedent this record does not set.
- **Renumber at merge (ADR 0235).** The version is embedded in three places: the migration file name, the `supabase/tests` file name, and its line in `scripts/sql_outside_migrations.txt`. Rename all three together. Then re-run `check_migrations_single_home.py`, `check_migration_order.py` and `check_migration_versions_unique.py`.
- **Forward-only.** Reverting the PR must never delete the migration file. Production keeps the change, and the ledger guards go red on a missing file. A real rollback is a new migration.

## Amendment 2026-10-03 — a shared place opens the house (F-006, PR 2)

- **The ruling, verbatim.** The founder, 2026-10-02, on an owner picking a place another house already holds: *"Open it, keep the pin (Recommended)"*. Recorded as: on a 23505 against `idx_restaurants_google_place_id`, open the house with its latitude and longitude kept and no `google_place_id`, and say nothing about another house. The ruling asked for it to be written into the F-006 wording change's record; this is that record, so no new ADR is created.
- **What the code does.** [Superseded in part 2026-10-08, see the amendment below: OPEN-1 is answered, /register now refuses a held place and no longer goes through `insertHouseRow`, and /get-started looks the place up before its insert.] Both writers insert through `AuthService.insertHouseRow`. A 23505 that `isSharedPlace` recognises (`apps/api-gateway/src/auth/house-opening.ts`: code 23505 and the quoted index name) inserts the row once more without `google_place_id`, with its latitude and longitude kept. Any other 23505 (the slug, an email) is not this path. The house is answered exactly like any other — same status, same body — and only the server log says the place was held.
- **Refusals are fixed sentences.** Both catches log the raw code and message on the server and send one sentence: 23514 and 22001 → 400 ("Could not open the house: one of its details is too long to keep. …"), anything else → 500 ("Could not open the house. Something went wrong on our side; …"). Both DTOs check F1's 2048 bytes before any write (`@FitsInBytes`), and cap the restaurant name at 249 characters, the city, state or province, neighborhood and country at 100, the postal code at 20 and the phone at 50. [PENDING OPEN-5 — decided 2026-10-08, option (a): /register caps the cuisine at 100 and the registrant's name at 255; see below.] A NUL in any text field is still a 500. The window under **Given up** and **23505 reaches more owners** closes with this change.
- **Residual: timing.** [OPEN-1 answered 2026-10-08: /register now says a held place outright, so there is no timing to hide there; on /get-started both classes make the same two calls. See below.] As built, a held place costs one more database round trip in about 8 on the public register route, and one more on /get-started. A probe can fail after the insert and leave no rows; the rate limit is per process and keyed on a header the client controls (ADR 0229). So a script that averages many probes can tell whether a house holds a place. The draft's old grounds ("every probe opens a real house", "10 per 60 s per IP") are wrong and are not written.
- **Residual: a later reader, guarded.** As of this record no route returns `google_place_id`. In the gateway only `coordinateColumns`, `insertHouseRow`, the two sign-up writers, `house-opening.ts` and the two DTOs name it, and outside it `scripts/backfill_restaurant_coordinates.py`. A route that later returned it would let an owner see their pick was not kept, and so learn that another house holds the place. Claim F006-NO-ROUTE-READS-THE-PLACE-ID fails the build on such a reader in the gateway, on an all-column select of `restaurants`, or on an RLS policy on `restaurants`; any change to that needs this ruling revisited first.
- **Residual: a failed token mint on /register.** [Closed 2026-10-08, OPEN-4 option (c), see below.] `registerRestaurant` returns the token mint without `await`, so a failed mint skips the rollback: it leaves a working, unverified account and its house, and the API caller is told "Nothing was done".
- **Residual: a concurrent duplicate first house.** [Closed 2026-10-08, OPEN-6 option (b), see below.] A concurrent duplicate first-house request by one account can leave the account's `restaurant_id` NULL beside a live house. This existed before without a place id, and this change widens it to requests with one.
- **Open: is one house per place a rule at all?** Recorded as open on 2026-10-02 alongside the ruling, and still OPEN: whether `idx_restaurants_google_place_id` should stay unique. This amendment matches the index's name and does not guard or change it. Recorded here rather than as an OPEN-DECISIONS row, following ADR 0240 F3.

## Amendment 2026-10-08 — /register refuses a held place (OPEN-1), and four lane decisions

The F-006 PR 2 plan (`~/Projects/p4-scratch/f006/plan.md` §0) named five forks. One is the founder's; four were decided by the F-006 lane.

- **OPEN-1, the founder's ruling, verbatim.** Asked by coordinator f523debf on 2026-10-08, about a place on the public /register that is already a house: *"Refuse, say it exists (Recommended)"*.
  - It overrides the 2026-10-02 ruling ("Open it, keep the pin", say nothing about another house) **on the public register route only**. The signed-in /get-started route keeps the 2026-10-02 ruling.
  - **What the code does on /register.** `registerRestaurant` looks the place up (`.eq("google_place_id", …).maybeSingle()`) before it writes anything. If the place is a house, it throws `PlaceAlreadyAHouse`. `refuseHouseOpening` turns that into 409 *"A house is already open at this place, so this one was not registered. If it is yours, sign in instead."* The web maps /register's 409 to the same sentence (`houseOpeningWords.ts`), but no web user reaches it today: the /register house form's second step is never shown (`setPathBStep` is only ever called with 1, `Register.tsx:1258`), so the sentence is met only by API and mobile callers until that form is wired.
  - A place taken between the look-up and the insert (the 23505 on the place index) is refused the same way, after the rollback. A failed look-up writes nothing and answers the plain 500.
  - **What the code does on /get-started.** `insertHouseRow` (now called by `createFirstHouse` only) looks the place up first and inserts once: without the id if the place is held, with it if not. The 23505 re-insert stays as a backstop for a race. Both classes make the same two calls, so the timing residual above does not apply on this route.
  - **What this gives up.** Anyone can now learn from /register whether a house holds a Google place. That is the founder's pick. A place id is a public Google value, and the 409 names no house, owner or account. It also lets a /register that nobody has verified hold a place it does not own: the real owner's own /register is then refused and told to sign in. Their house still opens on /get-started, after an account-only sign-up by email or Google (`createFirstHouse` asks only for a verified address), without the place id, under the 2026-10-02 ruling. The hold is indefinite: nothing sweeps an unverified account (ADR 0149 answer 2 deletes no `users` row; the 7-day lapse in `unproven-address.ts` ends only the password) and no gateway code deletes a restaurant. No place-ownership check is built; that is accepted with this ruling, not solved.
  - Claims: F006-REGISTER-REFUSES-A-HELD-PLACE and F006-SHARED-PLACE-OPENS-THE-HOUSE (narrowed to /get-started).
