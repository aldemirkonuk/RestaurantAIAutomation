# 0142 — The security gate can fail, and it says so when it cannot check

- **Status:** Locked
- **Date:** 2026-09-12
- **Decider:** Aldemir (founder) — "Make it fail on high and critical", 2026-09-12
- **Keywords:** trivy, security, CI, required check, baseline, trivyignore, absence reported as health, exit code
- **Links:** [[0090-pre-merge-audit-gate]], [[absence-reported-as-health]], `.github/workflows/ci.yml` job `security`, `.trivyignore`

## Context

`security` ("Security Scan") is one of the five required status contexts on `main`.
Its only scanning step was:

```yaml
      - name: Run Trivy vulnerability scanner
        uses: aquasecurity/trivy-action@master
        with:
          scan-type: "fs"
          scan-ref: "."
          format: "sarif"
          output: "trivy-results.sarif"
```

It sets neither `exit-code` nor `severity`. That is correct for a step whose job
is to publish findings into the Security tab — and it meant the job **could not
fail**. A required check that cannot fail is not a gate; it is a green light
wired to nothing, and it is the repo's own cross-cutting fault
([[absence-reported-as-health]]) reaching CI.

Measured on a clean archive of `941d9cb4` on 2026-09-12:
`trivy fs --scanners vuln --severity HIGH,CRITICAL` returns **143 finding rows
across 107 distinct advisories**, 139 HIGH and 4 CRITICAL. The job was green over
all of them, on every run it has ever had.

A second thing was measured the same day and changed the shape of the fix:
**trivy exits 1 for a fatal error as readily as for a finding.** A
vulnerability-database download that timed out exited 1. So did an unknown flag.
An armed gate that cannot tell "a new critical advisory landed" from "the scanner
could not run" produces the same red for both — and the second kind teaches
people to ignore the first, which is how a gate dies.

## Options considered

1. **Set `exit-code: "1"` and `severity: "HIGH,CRITICAL"` on the existing SARIF
   step.** One line, no new steps. Rejected: it breaks the SARIF publication
   (the step stops before uploading when it finds something), it fails
   immediately over 143 inherited findings so the first act would be to disarm
   it, and it inherits the exit-1-means-two-things problem above.
2. **Arm it with a baseline copied from GitHub's Dependabot alert list.** This
   was the drafted plan, and it was wrong. A baseline has to be generated by the
   tool that enforces it: the Dependabot list (104 HIGH + 1 CRITICAL) does not
   describe what trivy reports (139 HIGH + 4 CRITICAL rows, different ids). Used
   as written it would have exempted the wrong advisories and gone red on the
   rest the first time it ran. Named here because the draft is on record.
3. **Arm it with a trivy-generated baseline, in a separate step, with the
   database download split out.** Chosen. Below.
4. **Do nothing and work the backlog first.** Costs: the 219 open advisories get
   worked, and the 220th still lands green, because nothing is watching the
   boundary. The backlog is a separate problem from the gate; solving it does not
   arm anything.

## Decision

Keep the SARIF step exactly as it is, and add three steps after it:

- **Install trivy, pinned** (`aquasecurity/setup-trivy@v0.3.1`, `version:
  v0.74.0`) rather than `@master`. The gate's verdict must not change under us on
  someone else's release schedule, and v0.74.0 is the version both halves of the
  proof were run with.
- **Fetch the vulnerability database as its own step.** This is the separation
  that makes a red mean something: a download failure now fails a step named
  "Fetch the vulnerability database" instead of masquerading as a finding.
- **Fail on a new high or critical advisory**, reading `.trivyignore` and
  running with `--skip-db-update` so it cannot silently re-enter the download
  path it was just separated from.

`.trivyignore` carries the 107 advisories that were already open when the gate
was armed, each with the package and version it was found on. **It may only
shrink.** Adding a line silences a NEW advisory, which is the one thing the gate
exists to refuse; a line may only be added with a founder decision and its own
record.

### The gate was proven able to fail, on the tree it will run on

A guard that is armed but still cannot fail is the same defect wearing a new hat,
so this was measured three times on a clean archive of `941d9cb4`, with the exact
command the workflow runs:

| `.trivyignore` | exit | what came back |
|---|---|---|
| empty file | **1** | 143 high-or-critical finding rows |
| the 107-entry baseline | **0** | no rows, no error |
| the baseline with `CVE-2025-7783` removed | **1** | that advisory, named, and nothing else |

The third row is the one that matters: it proves the gate fails **on the right
thing**, not merely that it can fail.

## Consequences

- A new HIGH or CRITICAL advisory in any lockfile now turns `Security Scan` red,
  and `Security Scan` is required, so it blocks the merge.
- A day when Aqua's database is unreachable fails a differently-named step. It
  still blocks the merge — a scanner that could not run must not report health —
  but nobody has to guess which kind of red it is.
- The 107 inherited advisories are **not** judged by this decision. They stay
  open and stay exempt until somebody pays them down. The most material line is
  `nodemailer` 8.0.1 in the production gateway, whose vulnerable path is
  genuinely used and whose only fix is a major bump ([[codeql-alerts-2026-09-06]]).
- Pinning trivy means the gate does not pick up new detections until somebody
  bumps the pin. That is the trade: a gate whose verdict moves on its own is a
  gate people stop believing. The signal to revisit is a pinned version more than
  two minor releases behind, or a `.trivyignore` that has not shrunk in a quarter.
- `.github/workflows/ci.yml` is a **gate-owned path** under [[0090-pre-merge-audit-gate]],
  so the PR carrying this cannot self-merge: it escalates to the founder by
  design, which is correct for a change to what CI is allowed to pass.
