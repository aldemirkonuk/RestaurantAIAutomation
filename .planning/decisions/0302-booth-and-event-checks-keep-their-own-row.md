## Context

The owner-quarter sim's analytics walk on Tuzlu Rüzgar (2026-10-03, read-only) found A-050 and filed it as fork AW24. The street-fair booth's two checks ($4,201.10 on Aug 22 and $3,508.42 on Aug 23, rung up under Kerem, no covers, tip 0) count as Kerem's table service. At 42 days his average check reads $248.16, 27.6% above the staff mean, against a booth-free $192.25, and his tip rate reads 9.82% against 12.87%. Over the true 90 days he tops revenue ($134,007 against Priya's $127,689; $126,298 without the booth). Today the 1,000-check sample hides it; lane cap (ADR 0292) reads the whole window and turns it on.

The root cause is that no check says how it was rung up. Every cite is at `e2cbe426a`:

- `CanonicalCheck` (`apps/api-gateway/src/pos-hub/pos-types.ts:24-45`) has no channel, and neither has `pos_checks` (`supabase/migrations/20260805000000_baseline_from_production.sql:4192-4209`; `source` is the provider key, not the channel).
- Clover folds its order type into the table slot: `tableRef: o.orderType?.label ?? null` (`pos-adapters.ts:155`). An order type is a name the house makes up ("Dine In", "To Go"), not a table.
- `/analytics/waiters` credits every check with a server name to that server (`apps/api-gateway/src/analytics/table-analytics.service.ts:418-444`), and the same check feeds the table-adjusted fit when it has a table.
- The insight loop accumulates the table and the server for every check (`apps/api-gateway/src/analytics/insights/insight-generator.service.ts:1111-1155`), the peer block ranks on it (`:1283-1322`), and the hot-table filters take every check (`:1350-1395`).
- The sim posts `TR-2026-08-22-BOOTH` and `TR-2026-08-23-BOOTH` as Kerem with `tableRef: 'BOOTH'`, and `TR-2026-09-17-EVENT` ($5,283.47, 60 covers) as Owen, who is not one of the five servers. None carries a channel (`p4-scratch/sim-run/rebuild/run/gen.py:188-194`).

## Decision

A check names its channel, and a booth or event check is its own row in staff and table figures while it still counts in takings. The method, proposed for review:

1. **The column.** `pos_checks.channel` is `text`, null, bounded by the CHECK `pos_checks_channel_known` to `'table'` and `'booth_event'`. Null means no channel the hub knows was named, and reads as table service. The CHECK is added validated, in one step. The Supabase CLI runs the file as one transaction, so the `ADD COLUMN`'s ACCESS EXCLUSIVE lock is held until commit, and the CHECK's one pass over `pos_checks` runs under it, blocking reads and writes for that pass. Adding it `NOT VALID` and validating it in the same file would scan under the same held lock, so it is not done (measured on local Postgres 17, 2026-10-04, in one rolled-back transaction: `pg_locks` showed AccessExclusiveLock beside ShareUpdateExclusiveLock after `VALIDATE`). Every value is the new column's null, so the pass cannot fail; its length against production's row count is not measured (no production reads from this lane). [Corrected 2026-10-04 after the round-1 review: this item first said the `NOT VALID` / `VALIDATE` pair kept the lock catalogue-only and ran the scan under a lock that blocks nothing. That is false inside one transaction. The body of commit 27bae89a2 says the same, and history is not rewritten.] No backfill and no index (readers fold it in memory). No feed is known to have sent a channel: the canonical adapter never read one, and the sim's generator sends none (`gen.py:188-194`). That is not checked against production, where a channel a feed did send would sit unread in `pos_checks.raw`; `select source, count(*) from public.pos_checks where raw ? 'channel' group by source` (read-only) would show it. [Narrowed at the lane's last call, 2026-10-06: this item first said, with no qualifier, that nothing has ever sent a channel.]
2. **An exact vocabulary.** `CanonicalCheck.channel` is `'table' | 'booth_event' | null`. `checkChannelOf` trims and lower-cases a string, then requires an exact member; anything else is null. Nothing is guessed from `tableRef` ("BOOTH") or from an order-type label.
3. **Said, not swallowed.** The import result carries a `channels` tally (`booth_event`, `table`, `none`, `unrecognised`), counted over every check received before any is stored, so a refused or failed check is counted too. A check that names a channel outside the vocabulary is counted as `unrecognised` and not written as a channel, and its name is given in one `errors[]` line (the first five names, then "and N more"), the ADR 0281 pattern, so absence is never reported as health. What is stored differs by case: a new check that names an unknown channel is stored with no channel, and a row with no stored channel reads as table service; a re-send of a stored check leaves its channel as it was (a stored `booth_event` stays `booth_event`); a check refused for its closed_at, or whose upsert fails, is not stored at all. The name is read back from `raw.channel` only on the canonical feeds (`generic_webhook` and `csv_import`), whose `raw` is the row the feed sent. A Square, Clover or Toast `raw` is that provider's own order or check object; whether any of them carries a top-level `channel`, and what it would mean, is not verified, so it is not read, and those checks count as `none` (their order types wait for the owner's mapping, method 4). [Corrected 2026-10-05 after the review of `9b76b2e40`: this item first said an unknown channel "is stored as table service", which is false for a re-send of a stored `booth_event` check, a refused check and a failed upsert; and `raw.channel` was read on every provider.] [Added 2026-10-07 after the ADR 0090 audit at `28c59e9f8`: the audit found that a named channel that is not a string could abort the whole import. The tally (`tallyChannels`) quoted every unrecognised name through `String()`, and it runs in `ingest` before the per-check try, so a check whose `raw.channel` was `{"toString":1}` (`TypeError: Cannot convert object to primitive value`) or an array nested 10,000 levels or more (`RangeError`, measured on Node 20) threw out of the tally. The controller turns that into a 400 for the whole request, and no check in it was stored, where before this PR a bad check failed alone. Fixed in this PR: only a string is quoted; any other value (an object, an array, a number, a boolean) is counted as `unrecognised` and named once under the fixed label *a value that is not text*, never converted to text. The label is one of the names the result says, so like any name it is cut by the five-name cap (`MAX_CHANNEL_NAMES_SAID`) when five unrecognised strings come first; the count still includes it. Pinned in `pos-hub.channel.spec.ts`: one good check beside one such check imports both, and the specs fail with the throw when the fix is reverted.]
4. **An order type is not a table.** Clover's adapter writes `tableRef: null` and `channel: null` under fork pick (d); the order type stays in `raw` for the later mapping. Clover's registry capabilities become `CAP_NO_TABLES`. Square and Toast are unchanged: neither ever mapped an order type to a table.
   - *Source.* Clover's order object has no table field. Its field list (`docs.clover.com/dev/reference/ordercreateorder`, read 2026-10-04) has `orderType` and the string fields `title` and `note`, and the docs call none of them a table. Their null-fields example (`docs.clover.com/dev/docs/displaying-null-fields`) shows `"title": "5"`, which some houses may use for a table number. The order type itself carries `customerIdMethod` (*"Method to identify the customer"*, one of `NAME`, `TABLE` or `NAME_TABLE`, same page), so a Clover house can set an order type to ask for a table; the page does not say which order field holds the answer. Reading `title` as a table would be a guess, as the order type was, so it is left to the owner's mapping PR, which should read `customerIdMethod` too. [The `customerIdMethod` sentence was added at the lane's last call, 2026-10-04, from a fetch of that page.] [Sourced 2026-10-04 after the round-1 review: this item, the adapter comment and the body of commit 27bae89a2 first said *"Orders v3 carries no table"* with no cite.]
   - *Beyond the pick.* The chosen option's text says *"Nothing for now"* and that *"the order type is kept in the raw check"*. Taking the order type out of `tableRef` and the registry change go further. [Corrected at the lane's last call, 2026-10-04: this item first quoted the plan's *"Cost: none now"*, which is not the text the founder saw.] The founder kept them. [Answered 2026-10-07 04:29:14Z, the tool result's time in the coordinating session's transcript (asked 04:26:12Z); the question and both options are read verbatim from that transcript. Was: *"They are method, proposed for review: no Clover house exists (registry status 'scaffolded'), so no figure moves today, and undoing them is two lines (`tableRef`, `capabilities`)."*] The question as he saw it (AskUserQuestion, header "#618 Clover"): *"#618 (booth/order types): you picked 'Wait, then owner maps' for POS order types. #618 also stops Clover's adapter from putting the order type into the table field (tableRef: null) and marks Clover as having no tables. No Clover house exists, so no figure moves; undoing it is two lines. Keep that?"*
     1. **"Keep it (Recommended)" — chosen.** *"An order type such as 'To Go' is not a table; keeping it out of the table field stops it being read as one when a Clover house connects. The order type stays in the raw check for your later mapping."*
     2. **"Undo it" — rejected.** *"Strictly 'nothing for now': Clover keeps writing the order type as its table ref until the owner-mapping work. Two-line revert in #618."*

     So Clover's `tableRef: null`, `channel: null` and `CAP_NO_TABLES` stand as built. No Clover house exists (registry status 'scaffolded'), so no figure moves today.
5. **Written only when named.** The ingest row carries `channel` only when the check names one the hub knows. A check that names none sends no `channel` key, so a gateway deployed before the column exists still stores it, and a re-send that names none, or names an unknown channel, leaves a stored channel alone (skew-safe). Before the column exists, a check that names a known channel sends a column the table lacks, and its upsert error is named in `errors[]` like any failed upsert (PostgREST's refusal is not measured here). [Corrected 2026-10-05 after the review of `9b76b2e40`: this item first said such a gateway "never names it", which holds only while no feed names a channel.]
6. **Readers (PR-2).** A `booth_event` check leaves the per-table, per-server, peer, table-adjusted fit, correlation, driver and hot-table figures. Those checks form one "Booth & events" row in /reports' "The room" and "Who served it" registers and in both exports, computed with the same per-check money basis as the server rows. They stay in takings, the revenue series, the basket and `feedStatus`. A payload without the row renders exactly as before.
7. **Order of merge.** PR-2 selects `channel`, so it merges only after PR-1's column is verified live in production; otherwise every analytics read fails with 42703.
8. **Lane tables.** Lane tables (learned tables from the POS) must not learn a table from a `booth_event` check. If it lands first, PR-2's per-table exclusion skips a learned "BOOTH" table's booth checks anyway.

What carried it: the founder's ruling settles *that* booth checks are their own row and *that* the POS names them. The method keeps the vocabulary closed, so the CHECK, the reader and the row all agree on two values, and it moves every guess (a table called BOOTH, an order type called "Street Fair") to the owner's later mapping.

## Rejected alternatives (method)

- **Match `tableRef` 'BOOTH' or 'EVENT'.** A guess from a name the house chose; it would credit a real table someone named "Event" and miss a booth rung on table 7.
- **Read the channel from `raw` jsonb on every read.** No vocabulary, no CHECK, and a per-row jsonb parse in the hottest readers.
- **A flagged row inside `waiters[]` or `tables[]`.** It breaks every ranker that reads those arrays (the significance gates, the recommendation registers, scenario-verify). The row is a separate key, `boothAndEvents`.
- **A side table `pos_check_channels`.** A join on every read for no gain over one nullable column.
- **A backfill.** No feed is known to have sent a channel (method 1), so it would match nothing anyone can show exists. Not checked against production (no production reads from this lane).
- **Unknown values refused by the gateway.** It would drop a real sale from takings because of a label; keeping the check, writing no channel for the unknown name, and saying so keeps the money and the warning.

## Consequences

- **Not changed by this alone.** Tuzlu's figures change only after the sim's generator (`gen.py`) emits `channel: 'booth_event'` on its BOOTH and EVENT checks and the coordinator re-posts 2026-08-22, 2026-08-23 and 2026-09-17. The upsert updates `channel` in place and a re-post is stock-idempotent. Until then Kerem keeps $7,709.52 of booth takings and Owen keeps a $5,283.47 server row. That work is outside this lane (production writes).
- **Asked and answered: take-out and delivery.** Take-out and delivery have no channel of their own, so their checks are also credited to a server as table service. The ruling above covers booth and event checks only. The fork was filed in `OPEN-DECISIONS.md` (the section appended from `feat/a-check-carries-its-channel`, OD-TBD, its number assigned at merge). On 2026-10-05 the founder picked *"Decide via order-type map (Recommended)"*. Take-out and delivery stay table service, as built, until a Clover, Toast or Square house connects; the owner's order-type mapping then decides them.
- **Later.** The owner's order-type mapping (fork pick (c), after (d)) is its own PR and ADR once a Clover, Toast or Square house connects.
- **Harder.** Every new analytics reader of `pos_checks` that attributes a check to a server or a table must skip `booth_event` checks. Today's other readers (ask-readings, the sale-record producer, goals, calendar, logs, dev-truth, beverages) attribute no check to a server or table, so they need no change. scenario-verify does read tables: it checks that each scenario check landed with a `table_id` (`apps/api-gateway/src/simpos/scenario-verify.service.ts:609-616` at `e2cbe426a`), and it compares per-table check counts read through `TableAnalyticsService.getTablePerformance` (`:1710`), which PR-2 makes skip booth checks. Scenario checks carry no channel (`simpos/scenario-types.ts` has no such field), so both comparisons hold unchanged. A scenario that posts a `booth_event` check would need its expected table counts to leave that check out. [Corrected 2026-10-04 at the lane's last call: this item first listed scenario-verify among the readers that attribute no check to a server or table, which is broader than its code.]
- **Revisit when** the first Clover, Toast or Square house connects. Its order-type mapping also decides take-out and delivery.
