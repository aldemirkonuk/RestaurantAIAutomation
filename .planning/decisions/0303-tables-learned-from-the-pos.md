## Options considered

1. **Learn tables from the till's words, in the database, and re-link from the stored word (chosen, the founder's pick of 2026-10-04).** Every writer of `pos_checks` gets it, history is re-linked by the same rule as new checks, and the owner's only job is naming. The cost is a production write on merge (see Consequences) and five new database objects. [2026-10-05: and, since the rename rework, two new columns on `restaurant_tables`, `till_words` and `former_labels` (Decision).]
1a. **Only a word with a digit in it makes a table (chosen, the founder's pick of 2026-10-05).** "T12", "12" and "Patio 3" are learned. "booth" and "Ayla" stay on the check as its word, make no table, and link to a table that answers them once one exists. The cost is his option text's: a table whose name has no digit ("Bar", "Window") is added once by hand. No screen adds one yet (residual 12); the founder made that screen the follow-up lane `addtable` (2026-10-05 ~16:00Z, Decision).
1b. **Every word, retire odd ones** (the build through fix round 2). Rejected by the 2026-10-05 pick. The owner would hide "booth" and each first name a till sends in the table field, and every new name would learn another table.
1c. **Every word but booth/event** (a deny list). Rejected by the same pick. A list catches only the words it names: the six first names at Sim Meyhouse would still be learned.
2. **Draw the room** (wire the existing `POST /analytics/tables` and `PUT /analytics/venue` to a screen). Rejected by the ruling: *"No drawing."*
3. **Learn in the gateway only** (pos-hub creates the row on ingest). SimPOS and any other writer would bypass it, and a re-link on rename would need a gateway-side scan of every unlinked check.
3b. **The gateway writes `pos_checks.table_ref` itself** (this lane's first build, replaced in fix round 1). The new gateway would name a column only the migration adds. If it deployed before the migration applied, or the migration failed, every check's upsert would fail on the missing column until the column existed. Reading the word out of `raw` inside the trigger needs no gateway change. The two then deploy in either order, and the gateway already running learns tables as soon as the migration applies.
4. **Resolve at read time and keep `table_id` empty.** The insight generator, the waiter adjustment and scenario-verify all read `table_id`, so each would need its own copy of the resolver, and a rename would silently rewrite history.
5. **Re-point existing links on rename.** A link is the till's record of the time; a re-link only fills NULLs. [**Corrected 2026-10-05, in place, after the `afda5d868` audit:** the principle held only for the two re-link UPDATEs. An upsert re-send could still move a past check: pos-hub's row names `table_id`, and the trigger let a non-NULL one stand. After a rename that dropped a spelling, the re-send's INSERT arm learned a twin table, and its UPDATE arm then moved the check onto it (the audit's probe; T24 replays it). Since this round the trigger itself keeps the check's table on every update that leaves its word as it was (the belt, Decision), so no write path moves a past check whose word stands; T15 and T25 pin it. The belt does not hold a re-send whose word changed (T18).]
5a. **A renamed table keeps every spelling (chosen, the founder's pick of 2026-10-05).** Every word on a check linked to the table, per source, its earlier `pos_refs` words and its old labels are kept on the row and read by the resolver. The cost is his option text's: this rework and another audit round.
5b. **Stop the move only** (rejected by the same pick). The belt alone: past checks stay, but the till's next "Table 5" check still learns a twin table, to be hidden by hand.
5c. **Disclose only** (rejected by the same pick). No code change: one physical table's history could split in two after a rename.
5d. **Keep the extra spellings inside `pos_refs`, as an array per source** (the lane's, rejected). pos-hub's `resolveTable` compares `String(t.pos_refs?.[source])` with the word, so an array would stop the gateway matching, and every reader of `pos_refs`' `{source: word}` shape would change. Two new columns leave `pos_refs` as it is.
5e. **A child table of aliases** (the lane's, rejected). It needs its own RLS policy and a join in the resolver. Two columns on the row the resolver already reads need neither.
5f. **Rank a remembered word above the labels** (the lane's, rejected). pos-hub's in-memory resolve reads only `pos_refs` and labels, and its answer stands on an insert. With remembered words above labels, the gateway would name a label's table where the trigger would prefer another table's remembered word. Ranked last, they never contradict an answer the gateway can give, so `pos-hub.service.ts` stays unchanged (residual 17).
5g. **Skip learning on an upsert's INSERT arm when the check already exists** (the lane's, not built). With every spelling kept, a rename leaves the INSERT arm nothing to learn. The one remaining path needs a writer that sets its own `table_id` under a word no table answers, and no writer does that today (residual 20).
6. **Give learned rows `seats` 2 by default.** Rejected: a column default would be an answer nobody gave. That is this ADR's wording of the rule in ADR 0020 (*a surface with no data says so; it never invents one*) and ADR 0051 (*a rebuilt page shows live data or says it does not know*). So seats and is_outdoor become nullable and a learned row writes NULL to both, and per-seat figures are then withheld.
7. **Delete a table instead of hiding it.** The next check with that word would learn it again.
8. **Re-link immediately from a learned insert.** It fires inside the `pos_checks` statement, and one `INSERT … ON CONFLICT DO UPDATE` batch then fails with *"ON CONFLICT DO UPDATE command cannot affect row a second time"* — the whole import aborts. The SQL test's T11 pins it. A learned insert re-links at commit instead (a deferred constraint trigger).
9. *(Doing nothing: the room stays empty for every house whose till names tables, and its instruction points at a tool that does not exist.)*

## Decision

A table is learned from a word the till names on a check, when that word has a number in it; the owner renames or hides it. The method, proposed for review:

- **The till's word is kept, and the database reads it.** `pos_checks.table_ref` holds it (trimmed; a number as its text; blank is NULL). `pos_table_ref_from_raw` reads it out of `raw` as the adapters read it (Square `ticket_name`; Toast `table.guid`, then `table.name`; otherwise `tableRef`, `table_ref`, `table`). The trigger below calls it on every insert and on every update that writes `raw`, and the backfill calls it for history. pos-hub is unchanged: it already stores the adapter's payload as `raw` (`pos-hub.service.ts:526`), and it names no new column, so the gateway and the migration deploy in either order (fix round 1, option 3b).
- **Clover gives no table word.** Its `tableRef` is the order type, and the founder's AW24 pick *"Own row, POS field (Recommended)"* made the order type a channel, not a table (ADR 0302). Until a Clover/Toast/Square house connects, order types are not mapped (booth fork, verbatim *"Wait, then owner maps (Recommended)"*). On a csv feed with no order type, BOOTH and EVENT carry no digit, so they stay on their checks as the word and make no table (the 2026-10-05 pick).
- **A BEFORE trigger on `pos_checks`** (`BEFORE INSERT OR UPDATE OF raw, table_id, table_ref`, no WHEN clause) first sets `table_ref` from `raw`. A word `raw` carries wins. When `raw` carries none, a writer's own `table_ref` stands, but a word that came from the old `raw` goes with it. On an upsert re-send, a changed word re-resolves any link the statement did not set itself. It then resolves the word with `resolveTable`'s precedence (the source's `pos_refs` entry, then the label, then `table <label>`), case- and space-insensitive, over active tables with hidden ones included. [**Amended 2026-10-05, after the `afda5d868` audit:** a fourth rule follows the three: a word the table remembers, from its `till_words` for that source or its `former_labels` by either label rule ("A renamed table keeps every spelling", below).] When nothing answers, the word has an ASCII digit in it, and no retired table answers either, it learns the table: `seats` NULL, `is_outdoor` NULL, `pos_refs {source: word}`, `learned_at now()`. Learning runs in its own exception block; a failure is a WARNING and the check is stored without a table. A sale is never refused for this. A re-sent check whose word has not changed keeps its link when nothing answers now. [**Corrected 2026-10-05, in place, after the `afda5d868` audit:** that rule covered only a re-send whose statement left `table_id` NULL. When pos-hub's row named another table, that table stood, so a past check could move. Replaced by the belt: an update that leaves the check's word as it was (trimmed, any case) keeps the table the check had, whatever the statement sets (T15, T25). And a word over 60 characters, the most PATCH lets a person name a table, now learns no table either: it stays on its check as `table_ref`, and the check is stored (T29).]
- **Only a word with a number makes a table** (the 2026-10-05 pick). The test is `v_ref ~ '[0123456789]'`, the same in the live trigger and the backfill, since the backfill runs the trigger. It lists the ten ASCII digits rather than `\d` or a range, so a non-ASCII digit does not count and no collation decides. A word with no digit is still written to `table_ref` and still links to an active table that answers it. So an owner-added "Bar" links "bar" checks: past ones through the re-link on add, new ones at ingest, and a rename into "Bar" does the same.
- **A rename keeps the till's words.** The most recent word per source already linked to the row is merged into its `pos_refs` (existing keys win), so "Window 7" keeps catching T7. [**Corrected 2026-10-05, in place, after the `afda5d868` audit:** broader than the code, and wrong in its detail. The code kept one word per source (`DISTINCT ON (c.source)`), and existing keys won, so a learned table kept its original word and dropped every other spelling. A table learned as "5" that had also caught "Table 5", once renamed "Patio", learned a twin "Table 5" table on the next such check, and a re-send moved the old check onto the twin. Replaced by the next bullet.]
- **A renamed table keeps every spelling** (the founder's pick; AskUserQuestion, asked 2026-10-05 ~23:22Z, answered before 00:06Z 2026-10-06; binding). The question as asked: *"#621 (tables learned from the till) was blocked by its audit. Say the till learned table '5', and a 'Table 5' check also landed on it. You rename that table 'Patio'. The till then re-sends the 'Table 5' check and sends a new one. The system learns a second table called 'Table 5', and the old check moves off Patio onto it. That happens because a renamed table remembers only one till spelling per till. How should a renamed table keep its till spellings?"* His pick, verbatim: *"Keep every spelling (Recommended)"*. The option text read: *"A table remembers every till spelling it was ever linked by, not just one. A rename never creates a twin table, and past checks never move. Cost: the larger rework (migration, the lookup, and a new SQL test), so #621 needs another audit round of about 1–2 hours. seatsnote and addtable wait on it."* He rejected *"Stop the move only"* (option text: *"Past checks stay on Patio. The till's next 'Table 5' check still creates a twin 'Table 5' table that you would hide by hand. The ADR says so plainly. A smaller fix (one rule in the trigger plus a test), but the twin table still shows up on the floor list."*) and *"Disclose only"* (option text: *"Change no code. The ADR and the migration's own notes are corrected to say a rename can create a twin table and move a past check onto it. The fastest path to merge, but table reports can split one physical table's history in two after a rename."*). The method, proposed for review:
  - `restaurant_tables` gains `till_words` (`jsonb`, `{source: [word, ...]}`) and `former_labels` (`text[]`), both NOT NULL and empty by default. When a table's label or `pos_refs` changes, `restaurant_tables_keep_till_names` (`BEFORE UPDATE OF label, pos_refs`) adds to `till_words` every distinct word, per source, on a check linked to the row, and the row's earlier `pos_refs` words. It adds the old label to `former_labels`, unless the rename changed only its case or spacing. A word or label already kept, in any case, is not added twice, and nothing kept is dropped. `pos_refs` itself is not written.
  - `pos_table_for_ref` reads both last: after the source's pos ref, the label and `table <label>`, a table answers a word in its `till_words` for that source, or a former label by the label or the `table <label>` rule. A table that remembers nothing skips those scans.
  - **What guarantees "a rename never creates a twin table":** a renamed or re-mapped table answers every word it answered before: its `pos_refs` (unchanged by a rename, kept in `till_words` by a re-map), its old label by both label rules (`former_labels`), and every word a check linked to it carried (`till_words`). The trigger learns only when no table answers, retired ones included, so no rename or re-map leaves a word for it to learn. A remembered word can rank below another table's current label (residual 17), but the renamed table still answers it, so it is not learned. A table that never caught a check keeps its old label all the same (T26, "11" renamed "Corner").
  - **What guarantees "past checks never move":** the belt in `pos_checks_find_or_learn_table`, on every write path: an update that leaves a check's word as it was keeps the table the check had, whatever the statement sets. A re-send whose word changed still re-resolves a link the statement did not set itself (T18). And the two re-link UPDATEs fill only rows with `table_id` NULL; T19 and T20 now also check that they leave a linked row unwritten, since the belt alone would hide the loss of that filter.
  - Settings → Point of sale lists a table's kept words beside its pos ref ("csv_import: 5, Table 5").
  - The sequence the fork was asked on is T24: one table, Patio, holds c1, c2 and c3, and no "Table 5" table exists. The hand-added variant is T26, every word rather than one per source is T27, a `pos_refs` re-map is T28, and the belt against a write that names another table is T25.
- **Re-link fills NULLs only.** Adding a table by hand, or changing a table's label, `pos_refs` or `is_active`, fills `table_id` on the house's unlinked checks whose word now resolves to it. A learned insert does the same at commit. No link is ever moved. [**Corrected 2026-10-05, in place, after the `afda5d868` audit:** at `afda5d868` this held for the re-links only; an upsert re-send could move a link (option 5's bracket). The belt now holds it on every update that leaves the check's word as it was; it does not hold a re-send that changes the word (T18).] A check whose word has no digit waits, word in hand, for a table that answers it.
- **Backfill** sets `table_ref` on every stored check whose `raw` carries a word; that runs the trigger row by row, so history follows the same digit rule in one statement: a word with a digit learns and links, and any other word is written and links only to a table that already answers it.
- **Rename and hide** through `PATCH /analytics/tables/:restaurantId/:tableId` (`analytics.controller.ts:620`), `@Roles('owner','manager')` per fork F1, verbatim *"Owner or manager (Recommended)"*. RolesGuard is exact (ADR 0164), and the class JwtAuthGuard pins the house. The body is validated before the id (label 1-60 characters, hidden boolean, an empty body is 400). A non-uuid or foreign id is 404, and so is a retired table. A name another table of the house already has (case-insensitive, retired ones included) is 409. Settings → Point of sale lists the tables behind a closed disclosure, reads them only when opened, and keeps loading, failed (ADR 0067) and empty apart. Only an owner or manager sees Rename and Hide.
- **Hidden: the ruling is out of every table figure; this branch builds the room's part** (fork F2, verbatim *"Out of every figure (Recommended)"*; option text *"Hidden means out of every table figure and ranking, insights included."*). A hidden table still catches its checks; they stay in takings. The room (`getTablePerformance`), its export and the hot list leave hidden tables out and say how many checks they left out: `checksWithoutTable`, `checksAtHiddenTables`, `hiddenTables`, `openChecksAtHiddenTables`. Checks at a retired table count with the hidden ones. The insight generator's part is **owed** to the follow-up branch `fix/hidden-tables-leave-insights` (2 files plus its spec; #602 is merged). Until it lands, the Settings copy, the PATCH description and the `hidden_at` column comment name only what a hidden table leaves today (the room register and its export), not every figure. [2026-10-05: built on `fix/hidden-tables-leave-insights`, stacked on this branch; see *Amendment 2026-10-05* below. The Settings copy and the PATCH description now name every table figure, insights included; the column comment already named no reader.]
- **The waiter adjustment keeps hidden tables in its table control.** Asked (2026-10-05 ~01:39Z) whether hidden tables leave the waiter adjustment's table control, the founder picked, verbatim, *"Keep them in the control (Recommended)"*: F2 covers table figures, and the control keeps hidden tables' checks. `getWaiterPerformance` reads no `hidden_at`: every check with a `table_id` enters the table fixed effects, hidden or not (`table-analytics.service.ts`, the `obs.table.push(c.table_id)` branch). A table is learned when a check arrives naming one with a number in it, such as T12, 12 or Patio 3; rename or hide it under Settings → Point of sale."* A window whose checks had no table says how many, and adds *"A till word with no number in it, such as Booth or a name, makes no table."* Settings → Point of sale says *"A table name the till sends on a check becomes a table here when it has a number in it (T12, 12, Patio 3). ## Ruling 2026-10-07 — the driver sentence passes the fit's F-test at alpha, and its r² is above 0.15

What is built:

1. **The test.** `regressionSignificance(r2, n, k)` in `engine/comparisons.ts` is the overall F-test of a fit with k predictors over n rows: F = (R²/k) / ((1 − R²)/(n − k − 1)), and p is the upper tail of F(k, n − k − 1). The upper tail is `fUpperTail`, computed as the regularized incomplete beta I_{d2/(d2 + d1·F)}(d2/2, d1/2) by a continued fraction. The engine had no t, F or beta tail before: ADR 0272's tests use normal approximations (Welch z, Fisher z) and an exact hypergeometric tail. So the function is new, and it is checked against textbook values.
2. **The gate.** `table.avg_check.driver_weights` prints only when n − k − 1 ≥ 1 and p ≤ `SIGNIFICANCE_ALPHA` (0.05). Here k is the number of attributes kept and n the number of tables fitted. With no residual degree of freedom there is no test, so there is no sentence. The r² > 0.15 gate is gone. [2026-10-07, his second answer (recorded 12:04:50Z [Corrected 2026-10-07: answered 12:02:43Z per the transcript; 12:04:50Z was the coordinator's later `date -u`.]): not gone. 3. **Which R².** The test reads the r² of the ridge fit (λ 0.1). That is the fit whose standardized weights the sentence prints and whose r² the record's score already carries (`effectPct`). For the same rows, the ridge penalty can only raise the residual sum of squares above least squares. [Narrowed 2026-10-07, after the verify of `12468fc92`: that holds under the F-test's assumptions (independent, normally distributed errors of equal variance; residual 5), not unconditionally.
