The cost is a production write on merge (see Consequences) and five new database objects.
1a. **Only a word with a digit in it makes a table (chosen, the founder's pick of 2026-10-05).** "T12", "12" and "Patio 3" are learned. "booth" and "Ayla" stay on the check as its word, make no table, and link to a table that answers them once one exists. The cost is his option text's: a table whose name has no digit ("Bar", "Window") is added once by hand. No screen adds one yet (residual 12); the founder made that screen the follow-up lane `addtable` (2026-10-05 ~16:00Z, Decision). [2026-10-05: built by lane `addtable` in Settings → Point of sale, for an owner or a manager; see the amendment before Evidence.]
1b. **Every word, retire odd ones** (the build through fix round 2). Rejected by the 2026-10-05 pick. The owner would hide "booth" and each first name a till sends in the table field, and every new name would learn another table.
1c. **Every word but booth/event** (a deny list). Rejected by the same pick. A list catches only the words it names: the six first names at Sim Meyhouse would still be learned.
2. **Draw the room** (wire the existing `POST /analytics/tables` and `PUT /analytics/venue` to a screen). Rejected by the ruling: *"No drawing."*
3. **Learn in the gateway only** (pos-hub creates the row on ingest). SimPOS and any other writer would bypass it, and a re-link on rename would need a gateway-side scan of every unlinked check.
3b. **The gateway writes `pos_checks.table_ref` itself** (this lane's first build, replaced in fix round 1). The new gateway would name a column only the migration adds. If it deployed before the migration applied, or the migration failed, every check's upsert would fail on the missing column until the column existed. Reading the word out of `raw` inside the trigger needs no gateway change. The two then deploy in either order, and the gateway already running learns tables as soon as the migration applies.
4. **Resolve at read time and keep `table_id` empty.** The insight generator, the waiter adjustment and scenario-verify all read `table_id`, so each would need its own copy of the resolver, and a rename would silently rewrite history.
5. **Re-point existing links on rename.** A link is the till's record of the time; a re-link only fills NULLs.
6. **Give learned rows `seats` 2 by default.** Rejected: a column default would be an answer nobody gave. That is this ADR's wording of the rule in ADR 0020 (*a surface with no data says so; it never invents one*) and ADR 0051 (*a rebuilt page shows live data or says it does not know*). So seats and is_outdoor become nullable and a learned row writes NULL to both, and per-seat figures are then withheld.
7. **Delete a table instead of hiding it.** The next check with that word would learn it again.
8. **Re-link immediately from a learned insert.** It fires inside the `pos_checks` statement, and one `INSERT … ON CONFLICT DO UPDATE` batch then fails with *"ON CONFLICT DO UPDATE command cannot affect row a second time"* — the whole import aborts. The SQL test's T11 pins it. A learned insert re-links at commit instead (a deferred constraint trigger).
9. *(Doing nothing: the room stays empty for every house whose till names tables, and its instruction points at a tool that does not exist.)*

## Decision

A table is learned from a word the till names on a check, when that word has a number in it; the owner renames or hides it. The method, proposed for review:

- **The till's word is kept, and the database reads it.** `pos_checks.table_ref` holds it (trimmed; a number as its text; blank is NULL). `pos_table_ref_from_raw` reads it out of `raw` as the adapters read it (Square `ticket_name`; Toast `table.guid`, then `table.name`; otherwise `tableRef`, `table_ref`, `table`). The trigger below calls it on every insert and on every update that writes `raw`, and the backfill calls it for history. pos-hub is unchanged: it already stores the adapter's payload as `raw` (`pos-hub.service.ts:526`), and it names no new column, so the gateway and the migration deploy in either order (fix round 1, option 3b).
- **Clover gives no table word.** Its `tableRef` is the order type, and the founder's AW24 pick *"Own row, POS field (Recommended)"* made the order type a channel, not a table (ADR 0302). Until a Clover/Toast/Square house connects, order types are not mapped (booth fork, verbatim *"Wait, then owner maps (Recommended)"*). On a csv feed with no order type, BOOTH and EVENT carry no digit, so they stay on their checks as the word and make no table (the 2026-10-05 pick).
- **A BEFORE trigger on `pos_checks`** (`BEFORE INSERT OR UPDATE OF raw, table_id, table_ref`, no WHEN clause) first sets `table_ref` from `raw`. A word `raw` carries wins. When `raw` carries none, a writer's own `table_ref` stands, but a word that came from the old `raw` goes with it. On an upsert re-send, a changed word re-resolves any link the statement did not set itself. It then resolves the word with `resolveTable`'s precedence (the source's `pos_refs` entry, then the label, then `table <label>`), case- and space-insensitive, over active tables with hidden ones included. When nothing answers, the word has an ASCII digit in it, and no retired table answers either, it learns the table: `seats` NULL, `is_outdoor` NULL, `pos_refs {source: word}`, `learned_at now()`. Learning runs in its own exception block; a failure is a WARNING and the check is stored without a table. A sale is never refused for this. A re-sent check whose word has not changed keeps its link when nothing answers now.
- **Only a word with a number makes a table** (the 2026-10-05 pick). The test is `v_ref ~ '[0123456789]'`, the same in the live trigger and the backfill, since the backfill runs the trigger. It lists the ten ASCII digits rather than `\d` or a range, so a non-ASCII digit does not count and no collation decides. A word with no digit is still written to `table_ref` and still links to an active table that answers it. So an owner-added "Bar" links "bar" checks: past ones through the re-link on add, new ones at ingest, and a rename into "Bar" does the same.
- **A rename keeps the till's words.** The most recent word per source already linked to the row is merged into its `pos_refs` (existing keys win), so "Window 7" keeps catching T7.
- **Re-link fills NULLs only.** Adding a table by hand, or changing a table's label, `pos_refs` or `is_active`, fills `table_id` on the house's unlinked checks whose word now resolves to it. A learned insert does the same at commit. No link is ever moved. A check whose word has no digit waits, word in hand, for a table that answers it.
- **Backfill** sets `table_ref` on every stored check whose `raw` carries a word; that runs the trigger row by row, so history follows the same digit rule in one statement: a word with a digit learns and links, and any other word is written and links only to a table that already answers it.
- **Rename and hide** through `PATCH /analytics/tables/:restaurantId/:tableId` (`analytics.controller.ts:620`), `@Roles('owner','manager')` per fork F1, verbatim *"Owner or manager (Recommended)"*. RolesGuard is exact (ADR 0164), and the class JwtAuthGuard pins the house. The body is validated before the id (label 1-60 characters, hidden boolean, an empty body is 400). A non-uuid or foreign id is 404, and so is a retired table. A name another table of the house already has (case-insensitive, retired ones included) is 409. Settings → Point of sale lists the tables behind a closed disclosure, reads them only when opened, and keeps loading, failed (ADR 0067) and empty apart. Only an owner or manager sees Rename and Hide.
- **Hidden: the ruling is out of every table figure; this branch builds the room's part** (fork F2, verbatim *"Out of every figure (Recommended)"*; option text *"Hidden means out of every table figure and ranking, insights included."*). A hidden table still catches its checks; they stay in takings. The room (`getTablePerformance`), its export and the hot list leave hidden tables out and say how many checks they left out: `checksWithoutTable`, `checksAtHiddenTables`, `hiddenTables`, `openChecksAtHiddenTables`. Checks at a retired table count with the hidden ones. The insight generator's part is **owed** to the follow-up branch `fix/hidden-tables-leave-insights` (2 files plus its spec; #602 is merged). Until it lands, the Settings copy, the PATCH description and the `hidden_at` column comment name only what a hidden table leaves today (the room register and its export), not every figure.
- **The waiter adjustment keeps hidden tables in its table control.** Asked (2026-10-05 ~01:39Z) whether hidden tables leave the waiter adjustment's table control, the founder picked, verbatim, *"Keep them in the control (Recommended)"*: F2 covers table figures, and the control keeps hidden tables' checks. `getWaiterPerformance` reads no `hidden_at`: every check with a `table_id` enters the table fixed effects, hidden or not (`table-analytics.service.ts`, the `obs.table.push(c.table_id)` branch). The lane spec pins it with two tables, one of them hidden: if the hidden one's checks were left out, the fit would have one table level and no model.
- **Nothing is drawn.** The register and the export say *"This house has no table yet, so no check can be attributed to a seat. ## Amendment 2026-10-05 — an owner or a manager adds a table by hand (lane `addtable`)

Built on `feat/add-a-table-by-hand` by Claude (lane `addtable`), stacked on this ADR's branch (#621). Like the rest of this ADR it is proposed, built for the founder's review; a lock is his.

**The answers it implements** (AskUserQuestion; each quoted verbatim):

- **Fork 1 of #621** (2026-10-05 ~16:00Z). His pick: *"Follow-up: 'Add a table' (Recommended)"*. The option text read: *"A small separate PR adds 'Add a table' to Settings → Point of sale, for owners and managers. Waiting checks with that word link to it automatically. About 4 files. #621 merges as it is."* He rejected *"Build it into #621"* and *"Leave it"*.
- **Who may change a table** (fork F1, 2026-10-04): *"Owner or manager (Recommended)"*.
- **The digit rule** (2026-10-05 ~14:15Z): *"Only words with a number (Recommended)"*, whose option text named the job this control does: *"a table named only 'Bar' or 'Window' must be added once by hand in the table control."*
- **Seats** (2026-10-05 ~16:00Z): *"Explain the empty chart now (Recommended)"*, rejecting *"Add a seats field"*. So the control asks for a name and nothing else.

**Who can add.** An owner or a manager of the house. `POST /analytics/tables/:restaurantId` (`AnalyticsController.addTable`, which replaces `upsertTable`) carries `@UseGuards(RolesGuard)` and `@Roles("owner", "manager")`, as the rename-and-hide PATCH does. RolesGuard is exact (ADR 0164), so staff and admin are refused with 403, and the class JwtAuthGuard pins `:restaurantId` to the caller's house. `route-access.expected.json` records the route as owner and manager (it was open to every member). Settings → Point of sale shows *"Add a table"* only to an owner or a manager; anyone else reads *"Only the owner or a manager can rename or hide a table. Adding one by hand is theirs too."*, or, with no table yet, *"Only the owner or a manager can add a table by hand."*

**What an add does.**

- **It only adds.** The old handler upserted on the label, so posting a name another table had overwrote that table's seats and geometry. Now nothing is overwritten. The name is trimmed and is 1 to 60 characters.
- **A name the house already answers to is a 409 whose sentence names the table.** The comparison ignores case and surrounding spaces. A shown table with that label: *"This house already has a table called "T7"."* A hidden one: the same sentence and *"It is hidden: show it again instead of adding it."* A retired one: *"A table this house no longer uses is already called "Old bar", so the name cannot be added again."* A word an active table already catches in its `pos_refs`: *"The till's word "T12" already goes to the table "Garden 12", so a new table by that name would catch no check."* That last case is refused because `pos_refs` outranks a label, so the new table would catch nothing. The database's unique index on (house, label) answers a race with a 409 too. Settings shows the sentence where the save failed and keeps the form open.
- **A value the body does not give is NULL, never a guess** (ADR 0020). The insert writes `seats` and `is_outdoor` as NULL explicitly, because the column defaults (2 and false) remain. That closes residual 4 for this route. A value the body does give is validated, and an invalid one is a 400:
  - seats: a whole number from 1 to 999;
  - is_outdoor: a boolean;
  - each distance: from 0 up to 10,000;
  - zone: text of up to 60 characters.

  The Settings form sends the name only.
- **The waiting checks join it in the same statement.** The insert carries no `learned_at`, so the migration's `restaurant_tables_relink_on_add` trigger fills `table_id` on the house's unlinked checks whose word now resolves to the new table. It uses the rule in Decision (`pos_table_for_ref`). The gateway keeps no copy of that matching rule, and no link is moved. T23 of the SQL test already pins that an owner-added "Bar" links both past and new "bar" checks.
- **The answer says how many it took.** It carries `checksLinked`, the number of the house's checks the new table holds right after the insert. A table that did not exist before holds only the checks it just took. When that count cannot be read, `checksLinked` is null, never 0. After an add the list is re-read, and the new row says one of:
  - *"Added just now. It took 2 checks that were waiting with its name."*
  - *"Added just now. No check was waiting with its name."*
  - *"Added just now. How many waiting checks it took could not be counted."*
- **After that it is a table like any other.** It can be renamed or hidden, and the waiter adjustment's control keeps it (Decision).

**Choices neither the brief nor the answers settle.** Each was built the least surprising way and is listed under "Forks deferred" in the PR, with its options. None is locked:

- **A retired table's name is refused, not re-activated.** Re-activating a table returns its checks to the table figures and re-links its waiting words. That is a different act from adding, and no answer asks for it.
- **A word another table already catches is refused.** A table added under it would catch no check.
- **The route still accepts the other columns.** It takes seats, is_outdoor, zone, distances and position when a caller sends them, validated and NULL when absent. The screen sends the name only, as the seats answer keeps it.

**Residuals, not built here:**

1. The register and export sentences in Decision ("Nothing is drawn") still name only rename and hide under Settings → Point of sale. The Settings copy names adding.
2. An add writes no audit row (as with rename and hide, residual 3).
3. The column defaults (`seats` 2, `is_outdoor` false) remain, so any other writer that leaves them out still gets them. Only this route writes NULL.
4. No screen re-activates a retired table. How many retired tables production holds was not checked; this lane reads no production data.
5. The `pos_refs` check compares words without their source. In a house with two tills, a word one till sends for one table also blocks that name for a table the other till would send it for.
6. The web change was tested in vitest, not in the Browser pane, for residual 11's reasons.
7. The `.planning/06-pages` doc for /settings is not updated (residual 10).
