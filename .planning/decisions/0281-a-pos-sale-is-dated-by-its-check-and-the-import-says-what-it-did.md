## Context

The owner-quarter sim back-filled July and August through the generic POS import in October. `pos_checks.closed_at` kept each check's own close time. Everything the import derived from the check did not:

- **The stock ledger (A-007).** `apply_stock_movement` and `record_glass_pour` took no instant and stamped `inventory_transactions.transaction_date = now()` (0141's body, and the baseline's for the pour). Two months of sales landed on one October day. /inventory velocity read about double (median 2.04x the truth over 112 rows) and runway about half; 34 rows showed five days of cover or less where the truth had 11.
- **The demand series (A-009).** `wine_consumption_log` rows took their column defaults, `recorded_at = created_at = now()`. /reports' week shape and the 14-day forecast were built from one import day, so Friday was the only trading day and the backtest error read 100%.
- **The import result (A-029).** About 811 July–August POS lines (847 pours) and 8 bottle lines moved no stock: 752 on the stranded-lot cause (AW08), 59 on rows whose book was already empty. `ingest()` had an `errors[]`, but `applyStockEffects` returned `void` and a refused write was only logged, so the import read as clean and the unresolved queue was empty.
- **The sale-unit review (A-041, AW11).** The review read each mapping without `sale_volume_ml`, called every row with a null `sale_unit` unanswered, and hard-coded `effect_if_unanswered: "depletes_nothing"` on every row. The import reads `sale_volume_ml` first (ADR 0011), so 57 glass, single and carafe buttons were reported as depleting nothing while their sales took stock out.

The same mis-dating happens in a real house whenever a webhook arrives late or is replayed, and on every CSV back-fill. The sim only made it large.

## Options considered

**Where the sale's instant goes.**

1. **Do nothing.** Every late or replayed check keeps landing on its arrival day, and every rate built on the ledger or the demand series is wrong by the size of the lag. Rejected.
2. **The gateway rewrites `transaction_date` after the RPC.** A second write per line, outside the function's transaction, against a table whose writes ADR 0141 routed through the wrappers on purpose. Rejected.
3. **A new `occurred_at` column beside `transaction_date`.** Every reader would have to change to use it, and `transaction_date` already means "when it happened" to all of them. Rejected.
4. **An optional `p_occurred_at` on both RPCs, written as `LEAST(COALESCE(p_occurred_at, now()), now())` (chosen).** NULL keeps today's behaviour, so the gateway that is still running during the deploy window keeps working. A future instant is clamped to now, so no caller can book stock into the future. `created_at` stays the entry time, so the ledger still shows when a row was typed in.

**How the function changes.** `CREATE OR REPLACE` with a new argument creates a second overload, and PostgREST resolves a named call by its argument names, so the old 8-argument pour call would become ambiguous. The migration drops each old signature and creates the new one with its body copied verbatim, then asserts that exactly one of each function survives with the new argument last. The two positional SQL callers (`set_stock_absolute` and `record_stock_count`, 11 arguments) still resolve; the SQL test proves it.

**What the consumption row's dates are.** `recorded_at` is the sale's instant. `created_at` is set to it too, because every reader of the series filters on `created_at` today. Moving those readers to `recorded_at`, so `created_at` can go back to meaning entry time, belongs to the cap lane, which owns them. Setting only `recorded_at` would have left A-009 standing until then.

**What the import reports.** Logging alone is what A-029 measured as invisible. One `errors[]` line per failed line would put 800 lines into one response. Chosen: a `stock` block that counts every line on a closed check into exactly one of `notStock`, `booked`, `alreadyBooked`, `queued.unmapped`, `queued.no_sale_volume` and `failed`, with `consumptionNotWritten` and `backdatedOver72h` as sub-counts of what moved, plus `errors[]` lines grouped by (failure kind, item), at most 50 groups and one line that counts the rest.

**What happens to a closed_at the import does not read (F4).** At `4bef334b4` the check kept the till's value for Postgres to read or refuse; when Postgres stored it, its stock and consumption were dated at import time, counted (`datedAtImportTime`) and said. So a string Postgres reads differently from what the till meant was stored as Postgres read it: with `DateStyle` `ISO, MDY`, a day-first `03.10.2026` is stored as 10 March. The founder ruled to refuse such a check and say why (F4, below). The question's other options were not relayed to this lane, so they are not quoted here.

**What the review reports.** A per-row `next_sale`, computed by the import's own `resolveSaleVolume` and the shared `inventoryVolumesFromRow` over the same columns, replaces the hard-coded constant.

## Founder ruling

- **F1. Does C02's 72-hour rule ("older needs a manager", ruled for door receipts, counts and orders) also hold for a POS check's closed_at when it dates stock and consumption?** The founder's pick, verbatim (AskUserQuestion, recorded in the lane brief as 2026-10-04 ~02:10Z): **"No: trust the till (Recommended)"**. A closed_at is trusted at any age, and the lines this import books more than 72 hours after their check closed are counted as back-dated in the import result (`stock.backdatedOver72h`). The reason given with the recommendation: revenue has read `pos_checks.closed_at` at any age since launch, so a bound on stock alone would date a sale's stock and its revenue on different days, which is the A-009 defect in a new place; and a till's close time is written by a machine, not claimed by a person about the past, which is what C02 guards. The rejected options were (b) C02 literally, with a closed_at older than 72 hours dating the row only on an owner or manager import and server time otherwise, and (c) trust at any age with no back-dated count.
- **F4. What happens to a closed_at the import does not read?** Asked with AskUserQuestion on 2026-10-05 and relayed to this lane by the fix-lane coordinator. The question, verbatim: "A till that sends a date like 03.10.2026 is read today as March 10. What should happen to dates written that way?" The founder's pick, verbatim: **"Refuse, say why (Recommended)"**. The option text he saw, verbatim: "Accept only unambiguous dates (2026-10-03 21:00, ISO). Anything else is not imported and the import result says 'date not readable — write it as 2026-10-03 21:00'. Cost: a house whose CSV uses 03.10.2026 or 10/03/2026 must re-export. Nothing is ever silently misdated."
  How it is built, and the choices the option text left open:
  - **"Unambiguous (ISO)" is what `readClosedAt` reads** (the grammar under Decision). `2026-10-03 21:00`, the form the message asks for, is a date and time with no zone, read in the gateway's own zone (not verified on Railway; under Assumptions).
  - **A refused check is not imported.** `ingest()` refuses it right after `saleInstant`, before anything is written for it: no `pos_checks` row, no stock, no consumption row, no review-queue row. A row an earlier import stored for the same check is left as it was, so a check stored open and re-sent closed with such a date stays open. `errors[]` names each refused check, up to 50, as `<check>: not imported, date not readable — write it as 2026-10-03 21:00 (closed_at was "03.10.2026")`, then one line that counts the rest, so an export written in one such format does not put a line per check into the response.
  - **Counts.** The result gains `refusedUnreadableDate`. A refused check is counted there and in `received`, and in no other count: not in `upserted`, `wineItemsDetected` or any `stock` count. Every other check received is upserted or named in `errors[]` as not stored.
  - **An open check is not refused.** A closed_at of `null`, or none at all, is an open check, stored as before with no stock moved: there is no date to misread.
  - **Any other value that is present and not read is refused**, so the gateway never guesses at it: an empty or blank string (it is not `null`), a number (epoch seconds and epoch milliseconds look alike, and the option text accepts only ISO), and a boolean or any other value that is not a string.
  - **What is removed.** The fallback that dated stock at import time is gone, with its count `datedAtImportTime` and its `errors[]` group. `saleInstant` still reports `fellBack`, but in `ingest()` that now covers two cases only, and neither dates anything at import time: an open check, which moves no stock, and a refused one. `applyStockEffects` throws if it is handed a closed_at that was not read, so a direct caller cannot date stock at import time either.

## Decision

A POS sale's stock movement and its consumption row are dated by the check's `closed_at`, by the same single reading of it that `pos_checks` stores, never later than now. A check whose `closed_at` the import does not read (it reads only a strict ISO-8601 instant, below) is not imported, and the import says why (founder ruling F4). The import result counts every line on a closed check it stored, and says in `errors[]` which lines moved no stock and are not in the review queue: grouped by item, at most 50 groups by name, then one line that counts the rest. What carried it: the database already held the true time on `pos_checks`, so the only honest date for what the import derives from a check is that one. A count that partitions every line is the only shape in which "nothing failed" can be checked rather than assumed (the absence-reported-as-health failure A-029 measured).

How it is built:

- **Migration `a_pos_sale_is_dated_by_its_check`.** It gives `apply_stock_movement` (now 19 arguments) and `record_glass_pour` (now 9) a last argument, `p_occurred_at timestamptz DEFAULT NULL`, and dates the ledger row by `LEAST(COALESCE(p_occurred_at, now()), now())`. The `apply_stock_movement` body is 0141's, with its house refusal. The `record_glass_pour` body is ADR 0285's (migration `a_short_pour_opens_the_next_bottle`, merged first): it finishes the open bottle and opens the next from any lot, and writes one ledger row for every bottle a pour opens, so the one dated line dates the bottles opened from the next lot too. Both bodies are copied verbatim apart from the argument and that line, and the migration asserts that exactly one of each function survives and that 0141's refusal and 0285's cross-lot draw, guards and refusals are still in the bodies. The pour's `pour_events.created_at` stays entry time; nothing reads it as the time of the pour. The migration sorts after `a_short_pour_opens_the_next_bottle` (see F3 below for why that order is required).
- **`saleInstant(closedAt, nowMs)`** (`pos-hub.service.ts`, exported, pure). `ingest()` calls it once per check, before it stores the check. It reads the till's string once, with `readClosedAt`, which reads only a strict ISO-8601 instant. The string, trimmed, must be an extended calendar date `YYYY-MM-DD`, optionally followed by `T` or one space and `hh:mm`, `hh:mm:ss` or `hh:mm:ss.f` (1 to 9 fraction digits, cut to the millisecond), optionally followed by `Z` or a numeric offset `±hh`, `±hhmm` or `±hh:mm` of at most 14 hours, with minutes up to 59. Its written year, month, day, hour, minute and second must come back unchanged from the UTC calendar, so `2026-09-31`, `2026-02-30`, `24:00` and a leap second `:60` are not read. A string that passes is read like this:
  - with `Z` or an offset, the instant is the written wall clock minus the offset, computed without `Date.parse`;
  - a date alone is UTC midnight, which is how ECMAScript reads a date-only form;
  - a date and time with no zone is `Date.parse`'s reading in the gateway's own time zone, kept only when it lies within 14 hours of the written wall clock.

  When it is read, every date the import writes for the check comes from that reading, sent on as an ISO-8601 UTC string. Postgres reads such a string as the same instant in any session time zone (checked 2026-10-04 in PostgreSQL 17 under UTC, Europe/Istanbul and America/Los_Angeles), so Postgres never reads a string the gateway has already read. Where the reading goes:
  - `pos_checks.closed_at` gets the reading as it is, not clamped.
  - `p_occurred_at` on both RPCs, and the consumption row's `recorded_at` and `created_at`, get the same string when it is not in the future. A future one is clamped to import time on these rows only, so the check keeps its future close time while its stock and consumption are dated now.
  - The ledger row is `LEAST(p_occurred_at, now())` with the database's clock. It is earlier than the other rows only when the database's clock runs behind the gateway's and the instant sent falls inside that gap: a sale that closed moments before the import, or a clamped one.
  - A closed_at that is present and that `readClosedAt` does not read is refused by `ingest()` before anything is written for the check (F4): no check row, no stock, no consumption, counted in `refusedUnreadableDate` and said in `errors[]`. No till string reaches Postgres to be read a second time.

  Outside those cases, a sale's check, its ledger rows and its consumption rows carry one instant. This was added after the ADR 0090 audit of PR #603 at `01ac04eaa` (BLOCK). That head read the string with JavaScript only to decide past, future and 72 h, then passed the till's own string on. Postgres read that string a second time, so when the two readings differed the rows could come apart:
  - a reading Postgres placed in the future was clamped on the ledger only, while `pos_checks.closed_at` and the consumption row kept it;
  - a reading JavaScript placed in the future dated the stock and consumption now, while the check kept Postgres's earlier time.

  The strict read was added after the ADR 0090 audit of PR #603 at `1a7a4137d` (BLOCK). That head read the string with V8's `Date.parse`, which reads strings Postgres refuses (the fourth kind under Assumptions), so a check that failed loudly on main was stored and dated on an instant the till never sent.

  **RFC 2822 is not read.** No adapter in `pos-adapters.ts` builds one: Clover's closed_at is `new Date(modifiedTime).toISOString()`, and Square, Toast, the generic webhook and the CSV import pass the payload's value as sent. It is a second grammar, with its own zone names, and a weekday that neither reader checked when measured: `Mon, 03 Oct 2026 22:00:00 +0300` names the wrong day (3 October 2026 is a Saturday), and V8 and PostgreSQL 17.11 both read it as 19:00 UTC (`p4-scratch/sim-run/fixes/audits/603-closed-at-casts.txt`, outside the repo). A check that carries one is refused (F4), and the import says so on that till's first import, so the format can be added then, with its own tests, rather than guessed at now.
- **Voids.** A void is dated by the `closed_at` the voided check carries. That is the sale's own instant only when the till re-sends the original close time on the void. Only the generic adapter marks a void today (`pos-adapters.ts:60`, `voided`), and it passes the payload's `closed_at` through as sent; Square reads `closed_at ?? updated_at` and Clover `modifiedTime`. A till that stamps the void with its own time therefore dates the return at that later instant: the sale's day keeps the depletion and the void's day gets the return.
- **`recordConsumption`** takes the instant, writes `recorded_at` and `created_at` from it, and returns `logged`, `already` (a 23505 replay) or `failed`. The one `logger.error` on failure is kept.
- **`queueUnresolvedLine`** returns ok or failed. A 23505 means already queued and counts as queued. Any other error counts as failed, because a line that moved no stock and is not in the queue is lost from every list a person reads. The three queue call sites are left as they were, because the `iswine` lane edits that branch. The queue counts its own outcome into the check's report.
- **`ingest()`** returns `stock` and `refusedUnreadableDate`, refuses a check whose closed_at is present and not read (F4), and appends the grouped stock lines to `errors[]`.
- **The sale-unit review.** It selects `sale_volume_ml`, reads the inventory of every mapping, and gives each row `sale_volume_ml` and `next_sale` (`whole_bottle`, `volume` with its ml, or `depletes_nothing` with a reason and `queued_as`). `needing_unit` counts the mappings whose sale volume the import cannot resolve. The default list is those rows. `queue_on_next_sale` counts every mapping whose next sale lands in `pos_unresolved_lines`. `EFFECT_IF_UNANSWERED` is deleted, and the DTO's stale `?? "bottle"` docstring is corrected.
- **`setSaleUnit`** now passes the mapping's own `sale_volume_ml` back to `upsertItemMapping`. Before, answering "glass" on a 150 ml button wiped the volume the import reads first, so the button's next sale queued. Found while building this; adjacent to A-041.

## Deviations from the plan, said plainly

- **`queue_on_next_sale` also counts wine rows that queue as `unmapped`** (no inventory id, or an id this house's scoped read does not return), and it counts over all mappings, not only the returned rows. The plan named the `no_sale_volume` rows. The field's name is "lands in the queue on its next sale", and an `unmapped` row does land there, so counting only half of them would repeat the A-041 error in the other direction. In the existing spec this moves the count from 1 to 2.
- **`needing_unit` reads a `'glass'` label as unanswered** while the inventory row it reaches has no pour size, because that is how the import resolves it. Two existing review tests gained an inventory fixture with a pour size for this reason.
- **The stock counters drop `noQuantity`.** A zero-quantity line counts as `notStock`, under the plan's own list of counters.
- **The defect-register lines went to `tech-debt.d/`**, not to `v3.0-TECH-DEBT.md`. That file is frozen by ADR 0240, and the build fails on any added line.

## Consequences

- **Easier.** From this change forward, a late webhook, a replay and a back-fill all land on the day the check closed, in the ledger and in the demand series. Rows written before it keep their import-day dates until F2 is ruled; the July–August back-fill on Tuzlu Rüzgar is one of them, and it keeps inflating velocity until it ages out of the 30-day window or is repaired. Velocity, runway, the week shape and the forecast read the true days without any reader changing. An import that moved no stock says so, with counts that add up to the lines on the closed checks it stored. The review's "does nothing" now means what the import does.
- **Harder or given up.**
  - **Revenue's date for a closed_at the gateway reads moves with its stock, and a check that carries any other format is no longer imported.** `pos_checks.closed_at` used to hold Postgres's reading of the till's string; when `readClosedAt` reads it, it now holds that reading, as UTC.
    - For an ISO string with `Z` or an offset, Postgres read the same instant the gateway now computes where measured (`+03`, `+0300` and a year-50 `Z` string, in the cast table cited under Decision); the jest cases read `+03`, `+0300`, `-02:30` and `Z` forms by that rule.
    - Two kinds can differ from Postgres's reading. A date and time with no zone is read in the gateway's zone, where Postgres reads it in its session zone; the two agree while those zones match. A date alone is UTC midnight, where Postgres reads midnight in its session zone; the two agree while the session zone is UTC.
    - Any other format is refused (F4): RFC 2822, `04.10.2026 15:00`, `10/04/2026 3:00 PM`, `03.10.2026`, `1/1/50`, `… UTC+3`, and the strings Postgres refuses (the fourth kind under Assumptions). So is a closed_at that is an empty string or not a string at all. The check is not imported, and `errors[]` says `date not readable — write it as 2026-10-03 21:00`. On main, Postgres stored the check with its own reading of each string it reads and refused the rest. At `1a7a4137d`, V8's `Date.parse` read every string in the list above and dated the check, its stock and its consumption by that reading. At `4bef334b4`, the check kept the till's string for Postgres to read or refuse, and when Postgres stored it, its stock and consumption were dated at import time.
    - `03.10.2026` in particular: PostgreSQL 17.11 in the local container, with `DateStyle` `ISO, MDY`, reads it month first, 10 March, and V8 did too. On main the check was stored as 10 March. It is now refused, so it is read neither month first nor day first (F4). `10/03/2026 3:00 PM`, which the same Postgres reads as 3 October, is refused too: a day-first till means 10 March by it (`p4-scratch/sim-run/fixes/snap/postime-ruling/casts-ruling.txt`, outside the repo). Production's `DateStyle` was not read.
    - **The cost F4 names.** A house whose export writes dates as `03.10.2026` or `10/03/2026` imports none of those checks until it re-exports them in ISO, and each import says so. A check main already stored from such a string keeps Postgres's reading until it is re-sent in ISO, which the upsert, keyed on the check, then replaces. Its stock ledger rows, keyed on the check and the line, are not written again on that re-send, so they keep the date they were booked on (F2).
    - The generic adapter keeps the whole payload in `pos_checks.raw`, so the till's own string is still on the row there. `opened_at` is still stored as the till sent it; nothing in this ADR dates by it.
  - `wine_consumption_log.created_at` no longer means entry time for POS rows until its readers move to `recorded_at`. Those readers belong to the cap lane, whose branch as read 2026-10-04 still reads `created_at`.
  - One reader's meaning shifts with it. For a `bottles_sold` goal, `goal-reached.producer.ts:263-269` (`crossingInstant`) reports the newest `wine_consumption_log.created_at` of the house as the moment the goal was crossed. For POS rows written from this change on, that is the newest sale's instant, not the newest import. A back-fill of older checks, imported after newer rows, no longer moves the reported crossing to the import time. Its code is unchanged.
  - A back-dated ledger row keeps the `quantity_before` and `quantity_after` the function computed when it was written, so they are the running balance at entry, not at the dated instant. `get_inventory_balance_at` (baseline) returns the `quantity_after` of the newest row by `transaction_date`, so a balance asked for an instant inside a back-dated span can read wrong. It read wrong there before as well, when the sales sat on the import day. No web screen calls its route (`GET inventory-ledger/inventory/:inventoryId/balance`).
  - `setSaleUnit` hands the stored `sale_volume_ml` back to `upsertItemMapping`, which refuses a volume outside 10–30000 ml. A stored value outside that band (writable only by direct SQL) now makes answering the unit fail with that refusal. A stored volume larger than the bottle stays unresolved after the unit is answered, because the answer no longer wipes it; the row's `next_sale.reason` names it, and the volume is corrected through `POST /pos-hub/mappings/:restaurantId`. The same holds for any stored volume: the import reads `sale_volume_ml` before `sale_unit` (ADR 0011, `resolveSaleVolume`), so answering the unit changes only the label. Answering `bottle` on a button that stores 150 ml still imports 150 ml a sale; only a stored volume equal to the inventory row's bottle size imports as a whole bottle. The answer's response says `sale_unit: "bottle"` and nothing about the volume. Such a row resolves, so the default review list leaves it out; with `includeAnswered=true` its `next_sale` reads `volume`, 150 ml. The volume is changed through the same route.
  - Both RPCs gained an argument, and any lane that later redefines either one starts from this migration's body and keeps the argument (F3). The `doortime` lane (C02) was expected to reuse `p_occurred_at`; its worktree, read 2026-10-04, does not touch either function.
  - `stock.booked` is read from the consumption row on a sale, so a line whose consumption write failed on its first import counts as booked again when it is replayed. A replayed void always counts as booked, because the RPC answers a known key exactly as it answers a new one.
  - A check that arrives already voided still adds stock it never took (`tech-debt.d/2026-10-03-fix-pos-sales-dated-at-sale-time.md`). It is now dated and counted, but it is not fixed.
  - The Toast door still dates its stock at arrival (same fragment).
  - **Deploy order: the migration first, then the gateway.** The new gateway passes `p_occurred_at` to both RPCs. Against the old functions that call fails, so a gateway that lands first counts every line that reaches either RPC as `failed` and says so in `errors[]`, grouped by item (none is silently mis-dated) until the migration applies. This is the order ADR 0141 relies on: migrations apply when the PR merges, and the gateway deploys after. The old gateway against the new functions keeps working, because the argument defaults to NULL.
  - The sale-unit review now reads the inventory of every mapping, not only the unanswered ones, so its inventory read grows with the menu. It is read in chunks of 150 ids (the bound `procurement/overdue-order-reads.ts` uses), so a large menu neither outgrows the request URL nor meets the API's row cap in one read.
  - A mapping labelled `glass` whose inventory row has no pour size counts in `needing_unit`, and answering the unit alone cannot clear it: the reviewer has to give the pour size on the inventory row, or a `sale_volume_ml` on the mapping. The row's `next_sale.reason` names the gap, and the response type's `needing_unit` comment says so; no web screen reads this route today.
- **Assumptions, not verified.**
  - **The till's string is read only when it is a strict ISO-8601 instant (`readClosedAt`, under Decision).** The audits measured four kinds where V8's `Date.parse` and Postgres read a string differently. Each is now settled by that read:
    - A zone-less date and time (`2026-10-04 15:00:00`) is still read, in the gateway's own time zone, on every row of the sale, revenue included. Postgres reads it in its session zone.
    - A two-digit year from 50 to 69 (`1/1/50`): V8 reads 19xx, Postgres 20xx. It is no longer read; its check is refused (F4).
    - A POSIX-style zone (`… UTC+3`): V8 reads it with ISO's sign, three hours ahead of UTC, and Postgres with POSIX's sign, three hours behind. It is no longer read; its check is refused (F4).
    - **A string Postgres refuses and V8 reads**, found by the ADR 0090 audit at `1a7a4137d`: `12` and `Table 12` (V8: 1 December 2001), `0` (1 January 2000), `2026-02-30` (2 March 2026) and `2026-09-31T21:00:00Z` (1 October 2026). PostgreSQL 17.11 refuses each (cast table under Decision). At `1a7a4137d` such a check was stored with V8's instant and its stock and consumption dated by it; a reading more than 72 hours old was counted only in `backdatedOver72h`, and one inside 72 hours left no trace. On main, Postgres refused it and `errors[]` said so. **Closed by the strict read:** none of these matches the grammar or survives the round trip, so each falls back, and a fallback is never counted in `backdatedOver72h`. At `4bef334b4` its check went to Postgres as sent and was refused there, as on main; since F4 the gateway refuses it first, with the F4 message. Jest cases fail at `1a7a4137d` and pass here: `saleInstant` falls back on each of the five and on `2026-02-30T10:00:00Z`, and an import of each of the five is refused with nothing written for it.
  - **The strings each vendor's API sends are not checked against the grammar here.** A format outside it is refused on every check that carries it, so that vendor's closed checks import nothing until the format is added, and each import says so.
  - **The gateway's time zone on Railway is not verified.** If it is not the house's zone, a zone-less closed_at is dated in the wrong zone, the same way on every row of that sale. The jest case for it injects an Istanbul reading through `Date.parse`, because setting `process.env.TZ` inside a jest test does not reach the test's `Date` (measured 2026-10-04).
  - The database session's time zone and `DateStyle` no longer read any till string: `ingest()` sends `pos_checks.closed_at` only null or a UTC string the gateway wrote.
  - The SQL tests ran in PGlite on a build of every migration (last call, before the merge) and in PostgreSQL 17.11 in Docker on builds of every migration at `fb862aa57`, `1aa4dcb8c` and `28d32de36`, each plus this branch's (after it), not in Supabase's hosted Postgres.
