# 0033 — The design map is a zoomable atlas over one generated graph

- **Status:** Locked
- **Date:** 2026-08-27
- **Decider:** Aldemir (founder) — decisions are locked by the founder, never by an agent
- **Keywords:** design map, atlas, architecture, canvas, traceability, overlay, semantic zoom, 06-pages, endpoints
- **Links:** [[0004-obsidian-as-backlink-layer]], [[0026-schema-has-one-home]] (its guard's extractor is reused verbatim), [[0032-vault-cleanup-cut-line]], `scripts/generate_design_atlas.py`, `.planning/00-index/atlas-graph.json`, `.planning/00-index/atlas-overlay.json`, `.planning/00-index/DESIGN-MAP.html`

## Context

The founder asked for a design map: *every function leading to where*, the way an
architecture team would draw it, with a schema translatable enough to survive
tool changes. The repo had partial maps that never met: the system atlas
generator (endpoints + page graph, its JSON thrown away after rendering),
`06-pages/` (50 page docs with founder-maintained §1a feature lists and
`archetype:` frontmatter), `foundation/ENDPOINTS.md`, and the org/loop layer —
no chain from a product function down to the table it writes, and no canvas.

Six candidate looks were sketched and reviewed on a design canvas
(Traceability Board, Domain Clusters, Tree + Inspector, Metro Map, Flow
Ribbons, Zoomable Atlas), scored on the founder's three long-term axes:
whole-map overview, detail understanding, and what happens when function #151
lands.

## Options considered

1. **A — Traceability Board** (function rows × layer lanes). The meeting view;
   degrades linearly with growth, needs filters by ~200 functions.
2. **B — Domain Clusters** (Obsidian-canvas groups). Vault-native, stable
   domains; chains must be read inside boxes.
3. **C — Tree + Chain Inspector.** Scales indefinitely, carries the review
   facts; never shows the whole system.
4. **D — Metro Map.** Unbeatable at shared-dependency hotspots; every new line
   is hand-routed — a poster, not a system of record.
5. **E — Flow Ribbons** (aggregated Sankey). Whole-map at any scale, zero
   curation; individual chains always a click away.
6. **F — Zoomable Atlas** (semantic zoom: city → district → street). All three
   axes solved by altitude; the cost is a real interactive renderer.
7. **Mechanism fork:** hand-drawn canvas vs one committed generated graph.
   Hand-drawn was rejected on the same evidence as ADR 0032's archive rule —
   curated copies of code truth rot; the register proved it again the same day.

## Decision

**F — the zoomable atlas — over one committed, generated graph, with an
additive-only curated overlay** (founder, 2026-08-27: "the most technically
advanced and scalable one, and visibility and functionality").

- **`atlas-graph.json` is the source of truth**, regenerated by
  `scripts/generate_design_atlas.py`, never hand-edited. Every edge carries a
  `basis` naming its derivation: endpoints from controller decorators, features
  from `06-pages` §1a, page→endpoint from the `services/api` layer's real
  calls, service/agent→table from ADR 0026's proven extractor
  (`check_queried_tables_exist.extract`), model tasks from
  `taskType`/`task_type` literals.
- **`atlas-overlay.json` may add, never redefine.** Allowed keys: domains
  (match rules — the generator assigns nothing to a domain itself), badges
  (open defects by OD id), notes, extra nodes/edges. The generator **exits 2**
  on a collision with a generated id or an unknown key — the overlay cannot
  shadow or break the map, which was the founder's condition.
- **`DESIGN-MAP.html` is a generated view**, self-contained, three altitudes:
  domains city (counts, defect badges, shared-infrastructure strip), domain
  district (functions, pages, endpoints, services, data), chain street
  (feature → page → endpoints-with-basis → services → data/model, plus a
  blast-radius node view both ways). Open it in a browser; regenerate after
  code changes.
- The unchosen looks are **future lenses over the same graph**, not losers:
  A/C/E are candidate render modes the atlas can absorb, D is the curated
  overlay's occasional poster, B falls out as an Obsidian `.canvas` export
  whenever wanted. First measured build: **186 features · 47 pages · 464
  endpoints · 38 services · 25 agents · 162 tables · 39 model tasks · 1,142
  edges**; every page, service and agent domain-assigned except the shared
  Python services bucket, which stays visibly Unassigned rather than
  misfiled.

## Consequences

- One committed diffable graph: a PR that adds an endpoint changes
  `atlas-graph.json` in review, and the map can never drift ahead of or behind
  the code it renders.
- The §1a feature lists become load-bearing (they are the function layer), which
  is pressure to keep maintaining them — the standing founder mandate already
  requires exactly that.
- Feature→endpoint mapping rides at page level (basis is honest about it);
  finer granularity is future work, not a claim.
- Regeneration is manual for now (`python3 scripts/generate_design_atlas.py`);
  a CI freshness guard (regenerate and diff, fail on drift) is the natural
  next ratchet — deliberately not added in the same PR that adds the tool.
- **Retire-to-write:** this ADR names `foundation/PAGE_MAP.md` (a generated
  page-graph rendering) as the supersession candidate — to be retired via the
  ADR 0032 tombstone rule once the atlas verifiably carries its content;
  not retired today.
