# Plan 20-05: NotificationAgent DLQ Escalation Guard

## Objective

Fix the DLQ re-trigger loop: after `_send_to_dlq` is called for an `event_id`, all further
deliveries of that same `event_id` must be dropped immediately — no handler, no new DLQ call,
no counter increment. Currently `_notification_retry_counts` is never cleared or capped, so a
4th delivery calls `_send_to_dlq` again (with `retry_count=3` hardcoded), and a 5th, and so on.

**Risk without fix:** DLQ flooding. Each redelivery of a poison message after the 3rd failure
escalates again — multiplying DLQ entries and potentially triggering downstream alerts repeatedly.

## Root Cause

`process_message` increments `_notification_retry_counts[event_id]` on every dispatch exception
and calls `_send_to_dlq` when count `>= 3`. There is no "already escalated" guard, no counter
cap, and `_mark_processed` only runs on success — so idempotency never blocks retries.

## Fix

### 1. Add `_dlq_escalated: set` to `__init__`

```python
self._dlq_escalated: set = set()
```

### 2. In `process_message`, check before dispatch

After the idempotency gate and before `_track_notification_delivery`, add:

```python
if _effective_event_id in self._dlq_escalated:
    self.logger.warning(f"Notification already DLQ-escalated, dropping: {_effective_event_id}")
    return
```

### 3. After `_send_to_dlq` call, mark escalated and stop re-raising

```python
if self._notification_retry_counts.get(_effective_event_id, 0) >= 3:
    await self._send_to_dlq(
        message,
        error=str(dispatch_exc),
        retry_count=self._notification_retry_counts[_effective_event_id],
        original_exchange="notification.events",
        original_routing_key="notification.send",
    )
    self._dlq_escalated.add(_effective_event_id)
    return  # do not re-raise after DLQ — message is handled
raise  # re-raise if not yet at DLQ threshold
```

Note: change `retry_count=3` (hardcoded) to the actual counter value so the DLQ payload is accurate.
