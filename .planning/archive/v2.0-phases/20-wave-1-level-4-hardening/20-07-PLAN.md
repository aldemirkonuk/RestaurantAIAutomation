# Plan 20-07: ReportingAgent UTC Midnight Idempotency Boundary Fix

## Objective

Fix the UTC midnight duplicate-report risk: if two identical report requests arrive for the same
restaurant within the same calendar day (local time) but straddling UTC midnight, they get
different idempotency keys and both generate reports. For a restaurant in UTC-5 (Americas), this
window is 19:00–24:00 local = 00:00–05:00 UTC next day.

**Risk without fix:** Scheduled daily reports generated twice for restaurants in UTC-negative
timezones — doubled PDF exports, doubled S3/storage writes, doubled notification sends.

## Root Cause

`date_str = datetime.utcnow().strftime("%Y-%m-%d")` in `process_message` uses UTC date, not the
restaurant's local date. A report requested at 23:55 local and again at 00:05 local (next UTC day)
gets keys `rest:inventory:2026-04-10` and `rest:inventory:2026-04-11` — both unique, both processed.

## Fix

### Option A (Preferred): Accept `date` from message, default to UTC date — document the contract

The message sender (scheduler) is responsible for passing a consistent `date` field. The agent
should not guess timezone. Fix is to:

1. Document in docstring that `date` must be supplied by the caller for timezone-correct dedup.
2. Add a `date_source` field to the `log_decision` output so operators can audit which reports
   used caller-supplied vs UTC-defaulted dates.
3. Add a warning log when `date` is absent (signals misconfigured scheduler):

```python
if not (message.get("date") or message.get("payload", {}).get("date")):
    self.logger.warning(
        f"No date in report message for restaurant {restaurant_id} — "
        f"defaulting to UTC date {date_str}. Scheduler should supply explicit date."
    )
```

### Option B (Future): Lookup restaurant timezone from DB and convert

Deferred to Phase 22 (observability + config). Requires a `restaurant_config.timezone` field.

## Tests to Add
