## Goal

Three frontend gaps that make chain grouping unusable:
1. No way to assign your original (registered) restaurant to a chain.
2. Creating a chain gives no feedback — it's invisible until you add a new location.
3. `AuthContext` has no `refreshBranches()` — every chain/location change requires
   a full page reload to appear in the branch switcher.

## Premortem — What Will Go Wrong Without Care

| Risk | Blast Radius | Mitigation |
|------|-------------|-----------|
| `refreshBranches` refetches from `/organizations/branches` but AuthContext builds `availableRestaurants` in multiple places | Inconsistent state if only one path is updated | Centralize branch fetch into a single `fetchBranches(userId)` helper inside AuthContext, reused by both init and refresh |
| "Assign current restaurant to chain" checkbox — which restaurant is "current"? | Wrong restaurant silently gets reassigned | Use `activeRestaurantId` from context; show its name next to the checkbox so user can confirm |
| After PATCH, Settings `locationsList` is stale (derived from `availableRestaurants`) | UI shows old grouping even after refetch | `refreshBranches()` updates context; Settings reads `availableRestaurants` from context reactively |
| Edit Location dialog allows changing chain while viewing restaurant B, but PATCH uses `branch.id` from the item clicked | Correct — but must confirm the right id is passed | Pass `branch.id` explicitly from the map() in the Settings location list |
| Empty chain UX: chain created without auto-assign, then user closes dialog — chain exists in DB but never appears | User thinks "Create Chain" is broken | After chain creation, show inline success: "Chain created. Add Location or use Edit to assign existing locations." |
| `refreshBranches` called inside Settings causes race if user rapidly toggles dialogs | Possible duplicate fetches, flicker | Debounce or use a `isRefreshing` flag; safe to call multiple times (idempotent GET) |
| The "Assign current restaurant" checkbox on Create Chain: what if user has already assigned that restaurant to a different chain? | Silent overwrite | Before sending restaurantId, check if `activeRestaurant.chain_id` is already set; if so, warn "This will move it from [old chain] to [new chain]." |

## Tasks

### T1 — AuthContext: add refreshBranches()

File: `apps/web/src/contexts/AuthContext.tsx`

Extract the branches-fetch logic into a reusable private function `fetchAndSetBranches(userId)`.
Expose `refreshBranches: () => Promise<void>` on the context value.

```typescript
// Inside AuthContext provider
const fetchAndSetBranches = useCallback(async (userId: string) => {
  const token = localStorage.getItem('accessToken');
  const res = await fetch(`${API_URL}/api/v1/organizations/branches`, {
    headers: { Authorization: `Bearer ${token}` },
  });
  if (res.ok) {
    const branches = await res.json();
    setAvailableRestaurants(Array.isArray(branches) ? branches : []);
  }
}, [API_URL]);

const refreshBranches = useCallback(async () => {
  if (!user?.userId) return;
  await fetchAndSetBranches(user.userId);
}, [user, fetchAndSetBranches]);

// IMPORTANT: refreshBranches reuses the same fetchBranches logic which checks
// localStorage('activeRestaurantId') against the new branch list. Since the
// currently active restaurant is still valid after a chain edit, it will be
// preserved. Do NOT reset activeRestaurantId on refresh — the existing
// validSaved check handles this correctly.
```

Add `refreshBranches` to `AuthContextType` interface and context value.
