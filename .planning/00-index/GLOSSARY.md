# Glossary

> This corpus coins terms with narrow meanings. A reader who guesses from the English will get
> several of them wrong, and **several were misused during generation** — those misuses are
> recorded below under *Often confused with*, because knowing the wrong reading is what stops
> you repeating it.
>
> Each entry names **where the term is canonically defined**. This page defines nothing on its
> own authority; if it disagrees with the linked source, the source wins.

## The metric spine

### Neural Footprint
**The durable, structured trace a decision-maker leaves behind — enough signal to model *why* it
chose what it chose, not merely *what* it chose.**
→ Canonical: [`foundation/README.md` §4.1](../foundation/README.md) · architecture in
[ADR 0006](../decisions/0006-neural-footprint-architecture.md).

*Often confused with:* a dashboard, or "our metrics" generally. It is a **record shape** —
`stimulus → internal state → choice → outcome` — not a set of KPIs. Also note the term is
**ours**: no external source defines it. TRIBE is Meta's fMRI brain-encoding model and The
Sapient Company is a separate brain-decoding company; neither supplies this definition. Citing
them as the source of the term is wrong.

### NF-A / NF-B / NF-C
The three **subjects** of one Neural Footprint schema: **NF-A = agents**, **NF-B = guests**,
**NF-C = biological** (a gated research track, reserved and unused).
→ Canonical: [`foundation/README.md` §4.2–4.3](../foundation/README.md) ·
[ADR 0006](../decisions/0006-neural-footprint-architecture.md).

*Often confused with:* three separate systems. They are **one table discriminated by
`subject_type`** — that is the whole point of ADR 0006, and it is what lets NF-C plug in later
without a migration. Also confused with what already exists: `api_spend` is **not** NF-A (no
agent, no task type, no join key) and `AgentMetrics` is **not** NF-A (no cost, no verdict).
NF-A emits nothing today — see [[METRICS]].

### `subject_type`
The column that says whose footprint a row is: **`agent` | `guest` | `operator` | `bio`**. It is
the mechanism that keeps one production table polymorphic instead of forking into four, with
partial indexes per value so sparse columns do not tax dense reads.
→ Canonical: [ADR 0008 §"Decision"](../decisions/0008-nf-column-contract.md) · reserved by
[ADR 0006](../decisions/0006-neural-footprint-architecture.md).

- `bio` — reserved and gated; NF-C has no path to emitting anything today.
- `operator` — **added 2026-08-24** by the founder's tracking decision: staff and owner actions
  in the product ride the same spine as agent telemetry and product analytics. Note this is
  newer than most of the corpus, so `subject_type` is described as three-valued in older docs.

*Often confused with:* a nullable "kind" tag added for convenience. It carries a locked
architectural commitment — table-per-track was **considered and rejected**. Also confused with
NF-A/NF-B/NF-C, which are *tracks*: `operator` is a fourth `subject_type` and does **not** have
an NF-letter.

### doneability
**Whether the task was actually done** — the criteria, named in advance, by which an agent task
is judged to have succeeded. Step 2 of the skill-creation protocol is literally "name the
doneability criteria."
→ Canonical: [`foundation/README.md` §3.3 and §4.2](../foundation/README.md) · enforced (in
design) by [[agent-evaluation-gates-charter]] and [[evaluation-doneability-charter]].

*Often confused with:* **`AgentMetrics.success`, which means "did not throw."** That conflation
is the defect: a retried failure records cost with no task, and a handler that returns an empty
result records `success`. **No doneability verdict exists anywhere in the codebase today.** Also
distinct from a passing test — tests judge the code, doneability judges the task instance.

## The loop layer

### loop
A named feedback cycle: **what it measures → what it changes → how fast it closes.** Every unit
owns some. A loop that cannot state its close-time is a diagram, not a loop.
→ Canonical: [`foundation/ORG_STRUCTURE.md` §5](../foundation/ORG_STRUCTURE.md) · index at
[[LOOP-MAP]] · machine-readable arrays generated by `scripts/build_loop_index.py`.

*Often confused with:* a **schedule**. `schedule.md` lists recurring work; a loop must also
name the thing that *changes* as a result. Recurring work that changes nothing is a chore.
Also confused with a metric: a metric is a reading, a loop is the cycle that acts on it.

### `close_time`
**The loop's primary cadence — the one that governs it in the phase it is in today**, drawn from
a closed nine-value set: `per-pr` · `hourly` · `daily` · `weekly` · `fortnightly` · `monthly` ·
`quarterly` · `per-event` · `one-shot`. Nuance the closed value drops moves into the optional
free-text `close_time_note:`; if normalising loses information, the note is missing, not the
vocabulary.
→ Canonical: [`foundation/ORG_STRUCTURE.md` §5.1](../foundation/ORG_STRUCTURE.md) (OD-47).

*Often confused with:* a **deadline or a trigger**. `72h`, `30d_hard`, `per statutory deadline`,
`on second occurrence` are all `per-event` — a deadline is not a cadence. Before OD-47, 99
independent generators produced **102 distinct values across 482 loops**, 67 of them free text.

*Related trap — `status` inflation.* `active` and `running` require evidence in the block (a
`file:line`, a workflow path, a query). **The code running is not the loop closing**; a loop with
no owner or no measurement is `proposed` regardless of what executes underneath it.

## The org layer

### unit
**Any org entity that owns the full 8-artifact set** — department, sub-layer, team, or advisory
function alike. There are 99. Unit anatomy: `charter` · `premortem` · `agenda-full` ·
`agenda-board` · `directive` · `loops` · `schedule` · `questions`.
→ Canonical: [`foundation/ORG_STRUCTURE.md` §4](../foundation/ORG_STRUCTURE.md) · assignment list
in `00-index/UNIT-MANIFEST.json`.

*Often confused with:* "department". A department **is** a unit, but so is every team and every
advisory function. 99 units × 8 artifacts = **792 documents** — the number the retire-to-write
rule now guards.

### division / department / sub-layer / team
Three nesting levels plus one exception: **Division → Department → Sub-layer / Team**, with
**Advisory** sitting outside the line entirely.
→ Canonical: [`foundation/ORG_STRUCTURE.md` §1–2](../foundation/ORG_STRUCTURE.md) ·
[ADR 0007](../decisions/0007-org-structure.md) · navigable at [[ORG-MAP]].

- **Division** — a cluster of departments, so twenty departments are not twenty peers reporting
  into one point. Seven of them.
- **Department** — the unit that owns a mandate end to end. Nineteen.
- **Sub-layer** — a department-shaped unit nested *under another department* rather than under a
  division: **Guest Experience** (under Product & Vision) and **Finance & Pricing** (under
  Growth). Two of them.
- **Team** — a leaf inside a department or sub-layer. Seventy-five.

*Often confused with:* sub-layer vs team. A sub-layer carries its own teams; a team does not.
Also note **Research & Math is a division, not a department** — it was promoted (OD-28) to honour
the compensation term recorded in ADR 0001's review trail. Earlier drafts filed it under
Intelligence, and that contradiction is the reason the promotion had to be made explicit.

### advisory (findings-only)
An independent function that owns a department-equivalent charter but **cuts across every
division**, and whose authority is **findings only — it does not approve and does not block**. A
finding is written against a named unit and lands in that unit's `questions.md`, and in
`OPEN-DECISIONS.md` if it implies a decision. Three exist: Architecture Review, Red Team,
Decision Office.
→ Canonical: [`foundation/ORG_STRUCTURE.md` §3](../foundation/ORG_STRUCTURE.md) (OD-15, OD-16).

*Often confused with:* a **review board or approval gate**. Advisory cannot stop a change; it can
only make the finding undeniable and escalate to the founder. This is deliberate — an advisory
function that reports inside the line it reviews is not independent. Note also that Red Team is
scoped to **decisions and premortems**, *not* general security testing; Security builds defenses
in the line.

### provisional banner
The literal line `> **PROVISIONAL — no work done yet.**` that **must** open every `agenda-full.md`
and `agenda-board.md` until the unit has done real work. Its job is to stop a forecast reading
as a fact.
→ Canonical: [`foundation/ORG_STRUCTURE.md` §4](../foundation/ORG_STRUCTURE.md) artifacts 3–4 ·
[`foundation/GENERATION_BRIEF.md`](../foundation/GENERATION_BRIEF.md).

*Often confused with:* a draft marker. It is not about polish — a beautifully written agenda for
a unit that has done nothing still carries the banner. It comes off when work exists, not when
the prose is finished.

### retire-to-write
**Adding a document means naming one to retire, merge, or supersede.** Adopted org-wide
2026-08-24 (OD-34); the initial 693-document generation is exempt, everything after it is not.
→ Canonical: [`CLAUDE.md` §4](../../CLAUDE.md) · OD-34 in
[`OPEN-DECISIONS.md` §Resolved](../decisions/OPEN-DECISIONS.md).

*Often confused with:* deletion. **Merging and superseding count** — the scenario layer paid for
itself by retiring 44 byte-identical duplicates, and [[TIER-MAP]] paid for itself by superseding
a section of [[SCENARIO-MAP]]. The rule exists because the corpus was measured to name split
triggers in 11–15 documents against merge triggers in 3: structures only ratcheted upward.

### the L0–L6 stack
Seven foundation layers where **each layer may depend only on layers below it**: L0 data
substrate · L1 domain core · L2 module softwares · L3 agent harness · L4 Neural Footprint ·
L5 departments · L6 surfaces.
→ Canonical: [`foundation/README.md` §1](../foundation/README.md) · the dependency rule is
Architecture Review's mandate ([`ORG_STRUCTURE.md` §3](../foundation/ORG_STRUCTURE.md)).

*Often confused with:* a build order or a tech stack diagram. It is a **dependency rule**, and
the ordering is argued: **L4 sits *under* L5 deliberately**, because departments are evaluated
*by* metrics — define departments first and each invents its own success criteria. L4 is also
the current bottleneck: it emits nothing, which is why 476 of 482 loops cannot run.

## The scenario layer

### scenario / ritual
A **scenario** is one real-world restaurant event walked end to end through 11 mandatory
sections; the corpus also calls it a **ritual**, and the two words mean the same thing. There
are 17. A scenario without named signals is rejected — if nothing is captured, everything
downstream is fiction.
→ Canonical: [[SCENARIO-CONTRACT]] · index at [[SCENARIO-MAP]].

*Often confused with:* a user story or a process. **Scenarios are patterns, not processes** —
they name where they bend (see *flex point*) so a small library fits many kitchens. Also note
`status` is earned: `simulated` requires a recorded synthetic run, `live` requires the ritual
observed at a real restaurant. Everything is `proposed` today.

### flex point
**The named places a specific restaurant bends a scenario** — counting unit (case vs each),
who receives a delivery, window length, order cadence, service level. Every scenario lists its
own.
→ Canonical: [[SCENARIO-CONTRACT]] §5 · one `**Flex points:**` line per scenario file.

*Often confused with:* an **open decision**. A flex point is *deliberately* variable per tenant
and is meant to stay variable; a fork is undecided globally and is meant to close. Filing a flex
point as a fork creates a decision that can never be made.

### Core / Plus / Pro
The three subscription tiers, cutting **through §10 of every scenario rather than through
pages**: **Core = operate** (checklists, alerts, one-tap) · **Plus = understand** (scorecards,
drafts, digests) · **Pro = optimize** (cross-entity intelligence, proposals, forecasting).
Price points are founder-deferred (OD-23) and appear nowhere.
→ Canonical: [[SCENARIO-CONTRACT]] §2 row 10 (OD-48) · what each tier actually delivers today:
[[TIER-MAP]].

*Often confused with:* page-level or feature-flag gating — the entitlement axis is the scenario,
not the route. Also confused with a scenario's `tier:` frontmatter value, which records the
tier a scenario *belongs to* (16 `core`, 1 `plus`, 0 `pro`), **not** the tier at which its
capabilities land. Every scenario has Core, Plus and Pro rows in [[TIER-MAP]].

### "satisfiable"
An insight type is **satisfiable when the signals needed to compute it exist** — regardless of
whether anything renders it. **Today 144 of 573 insight types (25.1%) are satisfiable without
POS data; the other 429 (74.9%) need POS `checks`.**
→ Canonical: [[SCENARIO-CONTRACT]] §5 · [[analytics-bi-charter]] · matrix in [[TIER-MAP]].

*Often confused with:* "shipped" or "visible". Satisfiable is a statement about **available
signal**, not about product surface — a type can be satisfiable and never rendered. Also
confused with the insight-type denominator itself: **573 is the measured count, but 348, 375 and
`>=200` all still circulate** (OD-33), and the only test asserts `>= 200`, so every one of them
passes. Quote 25.1% with its denominator or not at all.

## Failure vocabulary

### confused deputy
**A control that is intact, green, and authenticating the wrong thing** — so a trusted component
performs a privileged action on an untrusted caller's behalf. The canonical instance: `simpos`
has no guard, and `POST check/:checkId/close` makes **our own server** HMAC-sign a webhook into
`pos-hub`, which correctly verifies the signature and depletes stock. The signature authenticates
the *sender* (us) rather than the *originator* (an anonymous caller).
→ Canonical: [[security-charter]] §"Live findings" · [[perimeter-ingress-integrity-charter]] ·
[[perimeter-ingress-integrity-directive]] · filed as OD-35.

*Often confused with:* a broken control. **The control is not broken** — it is working perfectly
and answering a question nobody needed answered. That is why per-module security labels are
dangerous: the label points an auditor at the HMAC, which is already green, while the actual gap
is a missing guard owned by a different team.

### vacuously green
**A check that passes because its input set is empty or its precondition was never met** — so the
green light is evidence of nothing. Distinct from a passing check: a vacuous pass cannot fail,
therefore it cannot inform.
→ ⚠️ **No canonical definition exists.** The corpus expresses this idea in at least four
independent phrasings and never defines it once. Nearest instances:
`PRODUCER_REPUTATION_PLAN.md:557` ("`wine_regions` is empty… any validation that joins it passes
vacuously"), [[decision-office-schedule]] ("the rule is live and vacuous" — 0 of 0 skills),
[[privacy-engineering-schedule]] (a job that "refuses to run without its DB secret rather than
passing vacuously"), and OD-35's "the control is green and answering the wrong question".
**Worth adopting as a defined term** — it names the corpus's most common instrumentation failure,
and today every reader has to reconstruct it from context.

Live examples in the corpus, all currently true:
- The **schema-parity job** has never compared anything — its connection string is unset (OD-49).
  A green run would prove nothing.
- The **skill anti-sprawl rule** ("unfired in 30 days → review for deletion") passes because
  there are **0 committed skills**.
- The **insight-count assertion** is `toBeGreaterThanOrEqual(200)`, so all four circulating
  counts pass (OD-33).
- A **guard allowlist** with no callers behind it — `privacy.consent_call_sites` is **0**.

The counter-pattern the corpus already models: fail loudly when a required input is missing
rather than passing vacuously.

## Decision vocabulary

### fork vs decision vs ADR
Three different objects that the corpus routinely blurs:

| Term | What it is | Where it lives | Who can create it |
|---|---|---|---|
| **fork** ⬦ | An open question found during the work. Not yet anyone's call | A row in [`OPEN-DECISIONS.md`](../decisions/OPEN-DECISIONS.md) | Any session, any advisory function |
| **decision** | The founder's call resolving a fork | The Resolved table + wherever it binds | **Founder only** |
| **ADR** | The written record of a decision, including its **rejected alternatives** | `decisions/NNNN-slug.md` | Written after the call |

→ Canonical: [`CLAUDE.md` §0.1–0.2 and §5](../../CLAUDE.md) ·
[`decisions/README.md`](../decisions/README.md) · pipeline diagram in [[DECISION-INDEX]] §4.

*Often confused with each other, in three specific ways:*

1. **A fork treated as a decision.** If it is not written in `decisions/`, it is open — including
   when an earlier draft doc states it confidently. OD-23 is the live case: pricing was cited as
   "locked" and no ADR records it.
2. **A decision treated as an ADR.** Not every resolved fork gets its own file — several were
   recorded into the contract document they govern (OD-12, OD-17, OD-47), with a Resolved row
   pointing there. That is correct, not a gap.
3. **Fork IDs that collide.** `OD-nn` in the register is *not* the same namespace as the local
   `⬦ FORK` IDs used inside generated unit docs. **Seven namespaces exist**, and 9 Engineering
   files cite `OD-19/20/23` meaning their own local forks (OD-30, OD-42). Commercial avoided this
   with `CM-Fn` prefixes. When citing a fork, say which register.
