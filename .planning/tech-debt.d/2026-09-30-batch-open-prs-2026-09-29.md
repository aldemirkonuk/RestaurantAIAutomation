## The deploy own-run guard does not pin how ci-gate executes, or workflow-level keys — OPEN — 2026-09-30

Filed from the ADR 0090 audit of #534 (rounds 3 and 4, Opus planner), on the founder's pick, verbatim: *"Honest record (Recommended)"*. `scripts/check_deploy_own_pushes.py` (gate-owned) holds `deploy.yml` to this repository's own CI runs on main, a push or a manual run (ADR 0097, 2026-09-30 amendment). It pins the refusal step's text and each job's `if`, and its self-test plants 52 breaks.

It does not pin how `ci-gate` executes, or any workflow-level key other than `on:` and `defaults:`. These pass the guard unnoticed:
- a job-level key on `ci-gate` other than `if`;
- another step or action in `ci-gate`;
- an env or path-file write other than the literal `GITHUB_ENV` or `GITHUB_OUTPUT`;
- a workflow-level `env:` (including `BASH_ENV` or a `BASH_FUNC_*` function), `permissions:` or `run-name:`;
- a column-0 comment inside `on:`, which hides a trigger added after it.

**What still holds, and what does not.**
- Changes that only alter whether `ci-gate` goes green on a foreign or non-push run are still refused by every stage's and `deploy-audit`'s job-level `if`. The guard pins those `if`s exactly, and no such change touches them.
- Founder, 2026-09-30, verbatim: *Describe the whole class, then fix the key (Recommended)*. Any ci-gate step that runs, sources, or interpolates into a shell anything the triggering run controls reopens the original exposure. That includes its checkout, its artifacts or caches, and event fields the fork writes, such as `head_commit.message` and `display_title`. ci-gate has no `if` and inherits `ADMIN_API_KEY`, so only gate ownership stops it.

**Known examples.** Each passes the guard at this writing:
- `concurrency: |` placed before the refusal step;
- `container:`, `runs-on: self-hosted` or `services:` on `ci-gate`;
- a job-level `env: BASH_ENV`;
- a workflow-level env entry `BASH_FUNC_exit%%: "() { return 0; }"`, which makes the refusal step exit 0 in local bash (GitHub untested);
- a `uses: actions/github-script` step exporting `BASH_ENV`;
- a `GITHUB_PATH` write, or an indirect write to the env file;
- `ci-gate` steps that run what the triggering run controls: checking out `head_sha` and running a script, running a downloaded artifact of that run, or echoing `${{ github.event.workflow_run.head_commit.message }}` into a shell;
- a column-0 comment inside `on:` followed by an added trigger.

**The fix.**
- Pin `ci-gate` whole: its job-level keys, its step list in order (an unbroken `steps:` sequence, no `uses:` or checkout step), and no write to `$GITHUB_*` files.
- Pin the workflow-level keys, or move `ADMIN_API_KEY` out of the workflow env and into only the steps that need it.
- Read comment lines as part of `on:`.
- Plant each example in the self-test.
- Then update ADR 0097's "Not held", the claim `DEPLOY-RUNS-ONLY-ON-OWN-PUSHES`, and this entry.

**Severity.** Low while `deploy.yml` has no `ci-gate` step that runs, sources or interpolates anything the triggering run controls. Such a step would reopen the original exposure, with only gate ownership in the way, until `ADMIN_API_KEY` is scoped (next entry).

## `ADMIN_API_KEY` is workflow-level env in `deploy.yml`, so every job and step inherits it, `ci-gate` included — OPEN — 2026-09-30

The founder's answer, 2026-09-30, verbatim: *Describe the whole class, then fix the key (Recommended)*. The class above, a `ci-gate` step that runs anything the triggering run controls, is stopped only by gate ownership, because `ADMIN_API_KEY` sits in `deploy.yml`'s workflow-level `env:` and so reaches every step.

**The fix.** It is approved in the same answer and follows #534 as its own `fix/` PR, which is gate-owned.
- Scope `ADMIN_API_KEY` to only the steps that need it, so that no `ci-gate` step inherits it.
- Add a guard check that the workflow-level `env:` holds no secrets.

**Severity:** medium until done. No step uses the key wrongly today, but the key's reach is wider than its use.
