## The deploy own-run guard does not pin how ci-gate executes, or workflow-level keys — OPEN — 2026-09-30

Filed from the ADR 0090 audit of #534 (rounds 3 and 4, Opus planner), on the founder's pick, verbatim: *"Honest record (Recommended)"*. `scripts/check_deploy_own_pushes.py` (gate-owned) holds `deploy.yml` to this repository's own CI runs on main, a push or a manual run (ADR 0097, 2026-09-30 amendment). It pins the refusal step's text and each job's `if`, and its self-test plants 52 breaks.

It does not pin how `ci-gate` executes, or any workflow-level key other than `on:` and `defaults:`. These pass the guard unnoticed:
- a job-level key on `ci-gate` other than `if`;
- another step or action in `ci-gate`;
- an env or path-file write other than the literal `GITHUB_ENV` or `GITHUB_OUTPUT`;
- a workflow-level `env:` (including `BASH_ENV` or a `BASH_FUNC_*` function), `permissions:` or `run-name:`;
- a column-0 comment inside `on:`, which hides a trigger added after it.

**Two kinds of harm.**
- Most of these can only turn `ci-gate` green on a foreign or non-push run. For those, every stage's and `deploy-audit`'s job-level `if` still refuses the run: the guard pins those `if`s exactly, and none of these changes an `if`.
- One reopens the original exposure: a `ci-gate` step that checks out the triggering run's `head_sha` and runs its code. `ci-gate` has no `if`, so it runs on every `workflow_run`, a fork's included, and it inherits `ADMIN_API_KEY` from the workflow env. For that one, only the gate ownership of `deploy.yml` protects; the stage `if`s do not.

**Known examples.** Each passes the guard at this writing:
- `concurrency: |` placed before the refusal step;
- `container:`, `runs-on: self-hosted` or `services:` on `ci-gate`;
- a job-level `env: BASH_ENV`;
- a workflow-level env entry `BASH_FUNC_exit%%: "() { return 0; }"`, which makes the refusal step exit 0 in local bash (GitHub untested);
- a `uses: actions/github-script` step exporting `BASH_ENV`;
- a `GITHUB_PATH` write, or an indirect write to the env file;
- a `ci-gate` step that checks out `head_sha` and runs a script;
- a column-0 comment inside `on:` followed by an added trigger.

**The fix.**
- Pin `ci-gate` whole: its job-level keys, its step list in order (an unbroken `steps:` sequence, no `uses:` or checkout step), and no write to `$GITHUB_*` files.
- Pin the workflow-level keys, or move `ADMIN_API_KEY` out of the workflow env and into only the steps that need it.
- Read comment lines as part of `on:`.
- Plant each example in the self-test.
- Then update ADR 0097's "Not held", the claim `DEPLOY-RUNS-ONLY-ON-OWN-PUSHES`, and this entry.

**Severity.** Low while `deploy.yml` has no such step: today the stage `if`s carry the protection for every member except the checkout step. A checkout step in `ci-gate`, or any step running the triggering run's code there, would reopen the original exposure, with only gate ownership in the way.
