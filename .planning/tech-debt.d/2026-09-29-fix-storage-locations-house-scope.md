## Storage locations took a location id from another house on trust — ~~OPEN~~ CLOSED 2026-09-29 (fix/storage-locations-house-scope) — 2026-09-29

Filed by the lane that fixed it, on a report from the #510 builder and verifier that `storage-locations.controller.ts` "has only JwtAuthGuard and no check that `:restaurantId` is the caller's own house". Filed and closed in one PR so it can be checked again.

**What the report said, re-checked on `origin/main` @ `aca12b244`: not so.** `JwtAuthGuard` is not authentication only: right after passport it runs `assertTenantMatch` (`apps/api-gateway/src/auth/guards/jwt-auth.guard.ts`, the call after `super.canActivate`), which compares every `restaurantId` in the path, query and body with the house the token names and throws 403 on any other; `JwtStrategy` has already refused a token naming a house the person is not a member of (`auth/strategies/jwt.strategy.ts`, `validateJwtPayload`). This is the same mechanism the cellar controller relies on (`cellar.controller.ts`, class comment). A signed-in user of house A who puts house B's id in the path of any of the eight routes gets 403 before the handler runs; `storage-locations-house-scope.spec.ts` part 1 proves it for every route Nest declares, with the real guard and a real `Reflector`, and removing the `assertTenantMatch` call turns its 8 house-B cases red (measured on the base service: 12 failed, the 8 guard cases plus the 4 service cases below).

**What was wrong instead.** The ids after the house were not checked against it, and the service's client is **service-role** (`database.service.ts` builds it from `SUPABASE_SERVICE_ROLE_KEY`), so RLS stands behind none of these queries. (1) `POST /:rid/mappings` wrote a mapping in the caller's house whose `location_id` was any zone of any house: the column is only a foreign key to `storage_locations(id)` (`20260805000000_baseline_from_production.sql:13830`, `ON DELETE CASCADE`, so a hard delete by house B would also have removed house A's row). (2) `GET /:rid/locations/:locationId/wines` answered another house's zone as an empty one. (3) `PATCH /:rid/:locationId` on a zone not the caller's matched no row and `.single()` turned that into a 500. (4) `DELETE /:rid/:locationId` on a zone not the caller's (or one already deleted) touched nothing and answered `{ success: true }`. No read or write of house B's rows was possible in any of the four; each was a trusted id or a lie about a write.

**Fix.** `StorageLocationsService.assertLocationIsTheHouses` reads the zone by id, house and `deleted_at IS NULL`, and answers 404 "No storage location of this house has that id." when it is not the caller's — identical to a missing id, so it does not confirm another house's id exists (ADR 0147, review round 2). Assign and wines-at-location call it before anything else. Update reads with `.maybeSingle()` so no row is the existing 404. Delete filters `deleted_at IS NULL`, returns the ids it matched, and answers 404 when there were none.

**Evidence.** `apps/api-gateway/src/storage-locations/storage-locations-house-scope.spec.ts`, 24 cases: part 1 (18, the guard pin) green on `aca12b244`; part 2 (6, over a fake client that applies the filters) 4 red on `aca12b244` (assign, wines-at, update, delete of house B's zone) and all green after. CLAIMS `TECHDEBT-STORAGE-LOCATIONS-HOUSE-SCOPE` (`resolved`, static): fails with the base service restored, holds after.

**Not covered.** `DELETE /:rid/mappings/:wineId` still answers success when the house holds no mapping for that wine: it is keyed on the caller's house, so it cannot touch another house's row, and making it a 404 would change what the zone manager sees on removing a wine whose assignment never persisted (PR #510 territory). `wineId` on assign is not checked against the house's inventory; it names a catalogue wine (`master_wine_library`), which is not house data. No role gate was added; see the fork below. The spec does not boot Nest over HTTP; it drives `JwtAuthGuard.canActivate` with passport stubbed.

**Founder fork, not decided here: who may edit zones.** All eight routes admit any member of the house, staff included, and so does the cellar's own zone write `PUT /cellar/:restaurantId/zones/:zoneId` (`cellar.controller.ts`, no role check). The only role gate on the inventory side is price (ADR 0193, `inventory.controller.ts` `assertMayPrice`); counts, transfers, pours and `DELETE /inventory/:restaurantId/item/:itemId` carry none. So no precedent exists for zones, and adding a gate would be inventing one. The count (`PATCH …/:locationId` with `current_count`, the per-wine `quantity` on `POST …/mappings`) shares routes with the zone edits. Paths: (A) every member, as today; (B) owner/manager for create, rename, capacity and delete, staff keep counting and placing wines, which needs the count split from the edit in `UpdateStorageLocationDto` and a web gate in `StorageLocationManager`; (C) owner/manager for every zone and mapping write, which takes counting from staff. Not filed as an `OPEN-DECISIONS` row by this lane: inserting a register row moves 57 line citations across about 30 files (`check_citation_pairing.py --fix`), past this lane's file cap.

**Severity:** low. The cross-house read and write the report described did not exist on `main`; what did was a foreign-key reference and wrong status codes.
