## What OPS-02 and SETUP-05 leave owed after `fix/a-capped-list-says-it-is-capped` — OPEN — 2026-10-07

Filed with the fix for OPS-02 (/recommendations) and SETUP-05 (/settings Ledger) from the scenario walk of 2026-10-07 (`p4-scratch/sim-run/pages/SCENARIO-WALK-2026-10-07.md`). The branch reads the house's recommendation book whole or refuses (ADR 0292 applied). History now answers `{ items, total, capped, limit }` and the page says "Newest 200 of N". The settings trail now answers `total` and `complete`, and the Ledger says "latest 100 of N" and "oldest shown". Claims: `claims.d/fix-a-capped-list-says-it-is-capped.jsonl`. What it does not do:

- **No guard names `recommendation_actions`.** The walk's fix asked for the table on ADR 0292's row-cap guard list. That list is not on `main`: no `scripts/*.py` at `origin/main` a323cc80b mentions `readWholeWindow`, and the guard lives only on the unmerged branch `fix/analytics-window-reads-guard`, scoped to `pos_checks` and `wine_consumption_log`. When that guard lands, it should add `recommendation_actions` (read through `readActionRows` in `apps/api-gateway/src/analytics/recommendation-actions.service.ts`). Until then, only the claims rows and the specs hold the fix.
- **The Ledger has no "show older" action.** SETUP-05's fix asked for one beside "latest 100 of N". The page now says how many rows exist and where its window stops, but it cannot reach past that window. The gateway already caps a read at 200 (`settings-audit.service.ts` `list`).
- **History still stops at 200.** It now says "Newest 200 of N acted entries. The other N-200 are kept and are not listed here." Nothing pages past the newest 200.
- **A per-setting trail can still say "Nobody has changed it" when someone has.** `ConsentPanel.tsx:91` asks `/settings-audit?register=<r>&limit=10` (`TRAIL_ROWS = 10`, `:87`). The service applies the row cap to every register first and filters by register afterwards (`settings-audit.service.ts:446`). Suppose a register's last change is older than the house's 10 latest changes across all registers. The panel then draws "Nobody has changed it since changes started being recorded on …" (`ConsentPanel.tsx:113`). The readout's new `complete` flag can tell "none in the latest 10" apart from "none at all", but the panel does not read it yet. Fixing it would have been this branch's 16th file. The other half of that trail's defect, that `readRegister` knew only five registers, was fixed on `main` by #613 (a323cc80b) after this branch's base.
- **A refused leaf read reaches the page as a 500, not a 503.** `listByStatus` throws `WholeReadError`, a `ServiceUnavailableException` (`read-whole-window.ts:105`). `listRecommendationActions` wraps every error in `HttpException(…, INTERNAL_SERVER_ERROR)` (`analytics.controller.ts:1295`). The page still says the leaf could not be read, never that it is empty; only the status code is wrong.
- **The cost of reading whole.** `readDispositions` now makes one exact-counted request per 1,000 rows of the book on every feed load. Past `WHOLE_READ_CEILING` (100,000 rows, `read-whole-window.ts:77`), it answers `readable: false`. This branch prunes nothing.
