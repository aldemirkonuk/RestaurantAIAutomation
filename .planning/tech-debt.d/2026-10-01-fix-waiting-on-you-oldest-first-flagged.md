## The approve gate seals when a rule cannot be tested, a failed last-price read included — OPEN (ruled, not built) — 2026-10-01

Filed by `fix/waiting-on-you-oldest-first-flagged` ([ADR 0256](../decisions/0256-waiting-on-you-is-flagged-first-then-oldest-by-the-houses-own-rules.md)), found while reusing the gate's facts for the "Waiting on you" flag. Ruled by the founder 2026-10-01 (ADR 0256, answers 8 and 10). Not built on this branch: a change to the gate is a separate operation, for a follow-up PR. Line numbers are as this branch leaves the files. At 5a330a88e, the branch's merge-base with main, the same code was `procurement.service.ts:4374` (`assertApprovalAllowed`) and `:4672-4698` (`pricePremiumPct`, `if (error) return null;`).

**What.** `assertApprovalAllowed` (`apps/api-gateway/src/procurement/procurement.service.ts:4391`) builds the order's facts with `orderUnderTest` (`:4686-4715`), which calls `readPricePremium` (`:4726-4754`). That returns `{ pct: null, unread: true }` when the read of the item's last price fails (`:4744`, and the `catch` at `:4752`). The gate takes only `test` and drops `priceUnread` (`:4446-4450`). `decideApproval` reads a `null` premium as "the `price_jump` rule does not apply" (`apps/api-gateway/src/settings/approval-thresholds.ts:185-189`), and the gate seals on `if (!decision.requiredRole) return;` (`:4453`). So when the read fails, a house with `price_jump` switched on seals the order as if the price had not moved, and nothing records that the check was skipped. This is the absence-reported-as-health fault (ADR 0020). The "Waiting on you" flag already reports `unread` as unknown.

The other two rules fail open the same way. `decideApproval` puts a rule it cannot test in `untestable` without setting `requiredRole`: `manager_ceiling` when the order has no total (`approval-thresholds.ts:154-157`), `new_vendor` when the first-order count failed (`:169-172`). The gate then seals at `procurement.service.ts:4453`. `apps/api-gateway/src/procurement/order-approval-gate.spec.ts:414-428` pins it: a first-order count that errors, and the order is `APPROVED`.

**Ruling (verbatim), answer 8.** Chosen: "Park for the rule's role (Recommended)": "Hold the order for whoever the price-jump rule names, the same way an untestable rule is handled today." Turned down: "Refuse, in words": "Refuse the approval with a sentence saying the last price couldn't be read; try again later."

**Correction.** Answer 8's option text rested on a false premise: an untestable rule held nothing, it sealed (above). This entry's earlier text said the same thing ("as an untestable rule already does"). The founder was asked again with the premise corrected.

**Ruling (verbatim), answer 10.** Asked: "Correction: I told you an order whose rule can't be checked is held today. It isn't: when the new-vendor or large-order rule can't be checked, the approval goes through. You chose 'park' for a failed last-price read. Which rules should park the order for the rule's role when they can't be checked?" Chosen: "Any rule that can't check (Recommended)": "Price jump, new vendor and large order all park for that rule's role when unreadable. Consistent, and follows ADR 0020. While a read is down, orders wait for someone holding that role." Turned down: "Only the last-price read": "Smallest change. New-vendor and large-order checks keep letting the approval through when unreadable, so 'couldn't check' is handled two ways."

**Follow-up PR.** Ruled (answers 8 and 10): any enabled rule that cannot be tested requires that rule's role, as a fired rule does: `price_jump` on an unread price, `manager_ceiling` on a missing total, and `new_vendor` on a failed first-order count. A person who holds the rule's role still seals; anyone below it parks the order `APPROVAL_NEEDED`. `order-approval-gate.spec.ts:414-428` flips from `APPROVED` to parked. *Proposed, not ruled:* the parked order carries a reason in words, such as "the last price couldn't be read", and the refusal record lists the rule as untestable. The founder chose park over refuse and named which rules park; he was not asked what the park says or records. Add gate spec cases for each of the three unknowns, for an actor below and an actor at the rule's role. The flag needs no change: a parked order reads `APPROVAL_NEEDED`, which the flag already marks "needs a signature", and the unchecked fact stays unknown.

## Two readings of "the last price" disagree — OPEN (ruled, not built) — 2026-10-01

Filed by `fix/waiting-on-you-oldest-first-flagged` (ADR 0256). Ruled by the founder 2026-10-01 (ADR 0256, answers 9 and 11). Not built on this branch, for the same follow-up PR. Line numbers are as this branch leaves the files. At 5a330a88e, the merge-base, the gate's query was `procurement.service.ts:4680-4687`.

**What.** There are three implementations and they disagree:

1. The approve gate, and so the "Waiting on you" flag: `readPricePremium` (`apps/api-gateway/src/procurement/procurement.service.ts:4736-4743`, `.neq("id", orderId).order("requested_at", { ascending: false }).limit(1)`). It takes the most recently requested OTHER order for the item: any status, any age, and even an order requested after this one.
2. `approvalGate` (`GET /procurement/order-approval-gate`, `:4504`) through `walkOrdersUnderTest` (`:4764-4828`). It walks forward inside a 365-day window (`APPROVAL_GATE_WINDOW_DAYS`, `:258`; `.gte("requested_at", since)`, `:4779`) and takes the order just before, any status (`lastPriceByItem`, `:4786-4812`).
3. The settings retrospective, `readOrdersUnderTest` (`apps/api-gateway/src/settings/approval-thresholds.service.ts:297-362`). It uses the same 365-day window (`RETROSPECTIVE_WINDOW_DAYS`, `:56`; `.gte`, `:311`), does not read status at all (`:309`), and does the same walk (`:334-351`).

So for an item with a newer order, or with no order in the last year, (1) and (2) can answer `price_jump` differently. DASH-W21 (recorded on `origin/fix/review-dashboard`, not yet on main) has the dashboard card read (2) to show an order as "held", so the card's "held" line and the flag can disagree on the same order.

**Ruling (verbatim), answer 9.** Chosen: "Last approved/delivered before (Recommended)": "Use the last approved or delivered order placed before this one." Turned down: "Just before, within 365 days": "The 'held' line's current meaning." and "Most recent of any age": "The approval check's current meaning; it can include a later order."

**Ruling (verbatim), answer 11.** Asked: "'Last approved or delivered order before this one': which order states count?" Chosen: "Any order that went ahead (Recommended)": "Approved, confirmed, in transit, delivered, partly received or completed." Turned down: "Only approved and delivered": "Read literally. A completed order, whose goods did arrive, would not count."

**Follow-up PR.** Ruled (answers 9 and 11): write one definition and use it in all three places, then delete the other two: the last order for the item placed before this one whose state is `APPROVED`, `CONFIRMED`, `IN_TRANSIT`, `DELIVERED`, `PARTIALLY_RECEIVED` or `COMPLETED` (the state vocabulary is `supabase/migrations/20260905230000_an_order_changes_state_by_the_table.sql:103-116`). Because the state set is ruled, the settings walk must start reading `status` (`approval-thresholds.service.ts:309` does not select it). The flag follows the gate through `orderUnderTest` with no change of its own.

*Proposed, not ruled* (the founder was not asked these; each is a fork for the follow-up PR to put to him):
- Which field "placed before" means. Proposed: an earlier `requested_at`, the field all three implementations already order by. Alternatives: `created_at`, or the time the earlier order went ahead.
- Whether the lookup has a window. The ruling names none. Proposed: no window. Alternative: keep 365 days, as the "held" line and the retrospective do today.
- What the two windowed walks do. Proposed: keep counting orders inside 365 days, but take each order's last price from before the window too. This follows only if the lookup has no window.
