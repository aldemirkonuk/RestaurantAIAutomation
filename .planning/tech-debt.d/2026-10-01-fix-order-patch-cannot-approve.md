## Any house member can approve an order and set its price through PATCH orders/:id — ~~OPEN~~ CLOSED by `fix/order-patch-cannot-approve` — 2026-10-01

Filed by `fix/order-patch-cannot-approve` ([ADR 0254](../decisions/0254-editing-an-order-never-approves-it-and-an-approved-order-keeps-its-prices.md) rules 1–2). This **closes** the OPEN entry of the same title in `tech-debt.d/2026-10-01-fix-closed-stays-closed.md`, which lives on the unmerged branch `fix/closed-stays-closed`; whichever of the two branches merges second strikes that heading to `~~OPEN~~ CLOSED by fix/order-patch-cannot-approve`. Line numbers in **What** are at `origin/main` 4bd11a00e; in **Fix**, on this branch.

**What.** `PATCH procurement/orders/:id` carries no `@Roles` and passes no user to the service (`procurement.controller.ts:251-263`). `updateOrder` refused only a move to CANCELLED without a reason (`procurement.service.ts:3302`); every other move went through `assertStatusTransition` (`:3312`), and the transition table makes PENDING, APPROVAL_NEEDED and NEGOTIATING → APPROVED legal edges (`order-transitions.ts:103-126`), because the sealed act walks them. So any member of the house could PATCH `{ "status": "APPROVED" }` and skip the seal (`POST orders/:id/seal-challenge` then `POST orders/:id/approve`, `procurement.controller.ts:513`, `:538`) and the approval-rule gate that runs inside it. The same PATCH wrote `quotedPrice`, `negotiatedPrice`, `finalPrice` and `totalCost` on an order in any state, so a sealed approval's total could be changed after the seal.

**Fix.** `updateOrder` now refuses `status: APPROVED` from anyone, before it reads anything (`procurement.service.ts:3383`): 422, reason `approve_through_the_sealed_act`, message "An order is approved through its own act — holding Approve, which checks this house's approval rules and seals the approval to the person holding — not by editing its status. Nothing was changed." A body carrying any of the four price fields, zero included, is refused with 422, reason `price_settled_by_approval`, unless the order is in `ORDER_PRICE_OPEN_STATUSES` (PENDING, APPROVAL_NEEDED, NEGOTIATING; `order-transitions.ts:222`), with words from `refusePriceChange` that end "Nothing was changed."; a stored state outside the vocabulary is refused too (`:3520`). The state is read as it is, not as the body asks, so a body stepping APPROVED back to NEGOTIATING with a new price is refused. The UPDATE repeats the allowlist (`:3468`), so an order approved between the read and the write is refused, not repriced. Notes and the other non-price fields stay editable in every state. ADR 0175 D7 (approval always needs authority) is **not** built here; its claim `ADR-0175-APPROVE-ORDER-ALWAYS-NEEDS-AUTHORITY` stays open.

**Pinned by** `apps/api-gateway/src/procurement/order-patch-cannot-approve.spec.ts`: 37 cases, 30 red against 4bd11a00e (measured with this branch's spec on that commit's service and transition table); the 7 green there pin what must keep working. Thirteen mutations, each applied alone and restored byte-identical, each turned it red: approve refusal removed (5 failed), moved after the transition read (4), price read check removed (9), price test by truthiness (2), unknown state let through the read (1), its sentence replaced (1), PATCH write guard removed (1), merge lookup back to the old denylist (3), merge write guard removed (1), APPROVAL_NEEDED admitted to the mergeable set (2), APPROVED admitted to the price-open set (10), merge line write unguarded (1), line guard always refusing (1).

**No route-access row.** The refusal is the same for every role and sits in the service, and the route-access census (`auth/guards/route-access.spec.ts`) measures only what `RolesGuard` lets through on controllers carrying `@Roles(`. A row would read "every role: allowed" both before and after this fix.

## A second order request overwrote an approved, parked or half-received order — ~~OPEN~~ CLOSED by `fix/order-patch-cannot-approve` — 2026-10-01

Filed by `fix/order-patch-cannot-approve` (ADR 0254 rule 3), found alongside the entry above. Line numbers in **What** are at `origin/main` 4bd11a00e; in **Fix**, on this branch.

**What.** `createOrder` folds a new request for the same restaurant + inventory + provider into the newest open order. "Open" was a denylist of seven statuses (`procurement.service.ts:1078-1086`, applied at `:1109`), so APPROVED, APPROVAL_NEEDED and PARTIALLY_RECEIVED orders matched. The merge UPDATE (`:1123` onward) then wrote the new request's quantity, prices and total over them: a sealed approval's figures changed with no seal, an order parked by the approval gate had the figures it was parked on replaced, and a half-received order had its quantity rewritten under the receipts already booked against it.

**Fix.** The lookup and the merge UPDATE both name the states a request may fold into, `ORDER_MERGEABLE_STATUSES` = PENDING and NEGOTIATING (`order-transitions.ts:239`; `procurement.service.ts:1109`, `:1148`). If the open order leaves those states between the lookup and the write, the UPDATE matches no row and `createOrder` starts a new order instead (`:1162`). The order line, written after the header, is rewritten only if the order is still in those states when `upsertOrderLine` is about to replace it (`:1191`, `:1612`); otherwise the line is left alone and the mismatch is logged as an error. That matters because the line write also moves the header price (`trg_procurement_line_price_echoes_to_header`) and carries money the seal does not bind: the seal hashes only `total_cost` and `provider_id` (`readOrderSealArgs`), not the line's currency, price unit or fees. Pinned by the spec's third block.

**Not closed.** PostgREST cannot make a DELETE or INSERT on `procurement_order_items` conditional on the parent order's status, so an approval landing between that last read and the line's two writes still lands. If the line is skipped, the approved header carries the merged request and the line does not, and the receiving check reads the line. Closing either gap needs the header and the line written in one transaction (a database function), not built here.

## PATCH orders/:id still moves an approved order onward without the seal — OPEN — 2026-10-01

Filed by `fix/order-patch-cannot-approve`, observed while fixing the entries above and left out because the fix was scoped to the move into APPROVED and to prices.

**What.** The transition table lets an APPROVED order move to NEGOTIATING, CONFIRMED, IN_TRANSIT, DELIVERED, PARTIALLY_RECEIVED, REJECTED or FAILED (`order-transitions.ts:130-139` at 4bd11a00e), and `PATCH orders/:id` still walks those edges for any member, with no seal. CANCELLED is not among them: `updateOrder` refuses it unless `cancelOrder` passes a reason code (`procurement.service.ts:3363-3372` on this branch), and the PATCH route passes none. A PATCH to DELIVERED books no stock: `updateOrder` makes no ledger call. A member can also step an APPROVED order back to NEGOTIATING and then reprice it in a second PATCH; it then has to be approved again through the sealed act, so this is an un-approval, not an approval bypass. Whether a member may approve an order no rule fires on is ADR 0175 D7, not built.

**Also seen.** `apps/web/src/services/api/orders.ts:92` (`updateOrder`) and `:107` (`updateOrderStatus`) call this route, and `apps/web/src/lib/supabase.ts:264` (`updateOrderStatus`) writes `procurement_orders` directly; a search of `apps/web/src` and `apps/mobile/src` found no screen calling any of the three.

**Fix (deferred).** Ruled by ADR 0254 rule 4: moving an approved order on needs an owner, a manager or someone given the right, and "delivered" comes only from receiving at the door. Not built here; it is the next fix.

## A re-quote at a new price into an open order with a line fails at the price-echo trigger — OPEN — 2026-10-01

Filed by `fix/order-patch-cannot-approve`, found while reading the merge's line write. Read from the SQL and the code, **not run against a database**.

**What.** The merge's header UPDATE writes `final_price` directly (`procurement.service.ts:1139`), and the line is written after it (`:1183-1192`). `trg_procurement_header_price_is_an_echo` (`20260905072000_the_header_price_echoes_the_line.sql:171-226`) refuses with 23514 any change to `final_price` that disagrees with the order's priced line. So a request at a new price, folded into a PENDING or NEGOTIATING order that already has a line, is refused by the database at the header UPDATE, and `createOrder` rethrows the raw error (`:1152-1159`) instead of merging. The confirm path writes the line first for this reason (`confirmDeal`, `:9501-9503`).

**Fix (deferred).** Write the line before the header, as the confirm path does, without reopening the race the line guard above narrows; one transaction would do both.
