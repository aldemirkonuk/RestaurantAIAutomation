## What ADR 0292's whole-window reads left open — OPEN — 2026-10-03

Filed by branch `fix/analytics-reads-past-row-cap` (lane `cap`, F-131 / C15). The fix reads the `pos_checks` and `wine_consumption_log` windows that ADR 0292's readers table names whole through `readWholeWindow`, or refuses with `WholeReadError` [narrowed 2026-10-04: this first said every analytics window of those tables, which the baselined reads below contradict]. The items below are what it did not fix. Line numbers are at this branch's head.

**Reads still capped, held in the guard's shrink-only baseline** (`scripts/check_window_reads_are_whole.py`, `BASELINE`). The guard ships in its own PR, stacked on this branch (`fix/analytics-window-reads-guard`), because of ADR 0231's 15-file cap. Until it merges, nothing fails on these reads. Once it has merged, the PR that removes or wraps one of these deletes or lowers its row, or CI fails it as stale:
- `dashboard/dashboard.service.ts` `getStats`, its `wine_consumption_log` read (`:521-522`). #579 (R1b, paused) and lane dash both touch it; whichever removes the read deletes the row.
- `pos-hub/pos-hub.service.ts` `getStatus` (`:1854`), 30 days of `pos_checks` (the read at `:1858`) [cite re-pointed 2026-10-06: it said about `:1285`]. It summarises sources, so a 1,000-row slice can understate a feed's last check.
- `communications/scheduled-tasks.service.ts`, the weekly top-sellers digest: 7 days of `wine_consumption_log` (`:1272`) [cite corrected 2026-10-04, verify round 2: it first said about `:1239`]. At about 131 lines a day, this is under the cap today and over it at about 143 a day.
- `analytics/dev-truth.service.ts` as-of split, 2 reads (`:238`, `:243`). The counts are exact, but the rows are capped.
- `notifications/producers/sale-record.producer.ts:232-238`: `.limit(CHECK_CAP + 1)` (`:238`) with `CHECK_CAP = 2000` (`:84`). That is above the server's 1,000, so its `truncated` branch can never fire. This is a latent defect: the read covers one local day, which holds far under 1,000 checks (the ADR's measured average is about 58). [Corrected 2026-10-04, verify round 2: it first cited the `.limit` at `:232` and said about 80 checks a day, a figure no measurement here backs.]
- `pos-hub/pos-mapping-review.service.ts` `loadObservedPrices`: `.limit(checkLimit)` (`:501`), where the DTO allows `@Max(2000)` (`dto/pos-mapping-review.dto.ts:64`). The default is 500, so a caller asking for more than 1,000 gets the latest 1,000. Its `checks_scanned` reports 1,000 (`checksScanned: checks.length` at `:564`, returned by `listNeedingSaleUnit` at `:404`) [cites re-pointed 2026-10-06: they said `:385`, `:448` and `dto:75`], so the count is honest, but nothing says the request was clipped. This is reachable today, not latent. [Corrected 2026-10-04, verify round 2: it first said the caller is told it scanned what it asked for; `checks_scanned` is `checks.length`.] **The plan's grep census missed this read, because grep reads this file as binary; the guard's Python scan found it.**

**Fork 3, after the founder's answer of 2026-10-06** (*"Say 'could not be read' (Recommended)"*, ADR 0292 Founder answers). - `analytics/analytics.service.ts` `loadConsumption` no longer degrades: a refused or failed page propagates, so the financial summary, inventory science, risk and the 120-day forecast refuse whole. Built on this branch; ADR 0292's readers table says where each consumer shows it.
- **Owed: the lens refuses whole, not figure by figure.** The financial summary's inventory value, COGS, ratios and days of stock (so a `days_of_inventory` goal) and the risk profile's vendor and revenue concentration need no pours, but are withheld with the lens. Splitting them is a product fork (deferred on the PR), not a defect.
- **Owed: the four routes answer 500, not 503.** `analytics.controller.ts` `getFinancial`, `getInventoryScience`, `getRisk` and `getForecast` wrap every error as `HttpException(message, 500)`. The sentence is in the body; /reports prints axios's status line either way (see "The web refusal state" below). Left for a controller PR: open PRs #625, #616 and #564 already touch that file (checked 2026-10-06).
- `analytics/insights/insight-generator.service.ts` `loadBundle` lets a refused read reject inside its `allSettled`, and that slice reads as `[]`. Every family that reads it is gated on it, so the family is not generated and states no figure. **Owed:** `generate()` still answers, so /recommendations does not name `insights` in `sourcesUnread`, and when only a bundle slice was refused its quiet tier can still say every source answered. That was already so on main for a slice that failed with an error; this branch does not change it.
- **Owed to the cellar lane: `beverages/beverages.service.ts` `readTillPages`** (`:1147-1175`, from #627). It pages the set-returning RPCs `house_till_names` and `house_till_lines` with `TILL_PAGE_ROWS = 1000` (`:174`) and stops at the first short page (`:1173`), with no exact count. That is whole only while 1000 is at or under `max_rows` (1000 locally, `supabase/config.toml:18`; the hosted value is not in the repo), so its "nothing is capped" (`:1042-1043`) rests on two numbers nothing ties together. The guard scans `.from(...)` reads of `pos_checks` and `wine_consumption_log` only, so it does not see this. Not fixed here.

**Not measured.**
- **Latency (fork 2; the founder's answer of 2026-10-06: measure the real time after merge, and build database totals only if it is slow).** For the 365-day ribbon (`/analytics/pos-revenue?days=365`), the estimate is about 22 check pages plus 48 consumption pages at about 60 ms each: roughly 4 s in sequence. If the measured time passes about 3 s, move that window to an RPC that returns jsonb (a set-returning RPC is capped too).
- **The overview's fan-out (verify round 1, 2026-10-04).** `/analytics/overview` runs five lenses that each read their own 90-day consumption window (financial, risk, inventory science, menu engineering, seasonality): about 60 page requests in five parallel chains of 12, where it used to be five capped requests. Nothing is shared between them. Measure it with the ribbon; sharing one read is a cache with a lifetime, which needs its own decision.
- **The /recommendations fan-out (verify round 2, 2026-10-04).** `recommendations.service.ts` `getRecommendations` (the `Promise.allSettled` at `:319`; cite re-pointed 2026-10-06 from `:187`) runs the same five lenses plus a live `generate()`, whose bundle reads its own 90-day consumption and check windows: six whole consumption reads and one check read, roughly 78 page requests in seven parallel chains. Not timed, locally or in production.
- **The web refusal state, never eyeballed.** On a refusal, /reports prints "The till register could not be read (Request failed with status code 500). Nothing below is claimed." The till route maps every error to a 500 (`analytics.controller.ts` `getPosRevenue`), and `failureOf` (`apps/web/src/pages/reports/next/rp-format.ts:148-153`; cite corrected 2026-10-04, verify round 2, from `:133-137`) takes axios's own `error.message`, not the gateway's body, so the WholeReadError sentence does not reach the page. That is how every /reports register names a failure today, not something this branch changed. [Corrected 2026-10-04: this line first said the page would print the gateway's "…could not be read whole…" sentence; `failureOf` reads `error.message`, which for an axios error is the status line.] Read from code only: no page was rendered against a refusing gateway.
- **`createGoal` returns 400, not 503.** Its controller maps any error to 400, so a refused baseline arrives as a 400 that carries the refusal sentence.
- **The helper's one blind spot, in code and not reachable today.** With no count in the response, a short page ends the read. Every reader asks for `count: "exact"`, and the guard's PR enforces it at every call site, so only test doubles take that path. A lowered `max_rows` together with a dropped count would pass unseen.
