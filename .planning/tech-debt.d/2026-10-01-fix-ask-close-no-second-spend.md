## Closing the Ask panel mid-answer dropped the answer, and asking again paid twice — ~~OPEN~~ CLOSED by `fix/ask-close-no-second-spend` — 2026-10-01

Filed by `fix/ask-close-no-second-spend` ([ADR 0145](../decisions/0145-mudavym-answers-out-of-a-reading.md), "Amendment, 2026-10-01"). Found by the audit of PR #575 on 2026-10-01, which rated it a note, not a block: it was pre-existing, and #575 only added a more visible trigger. Line numbers are at `origin/main` 5a330a88e.

**What.** `AskPanel` returns null when closed (`AskPanel.tsx:579`), so its body unmounts in both placements. The question in flight, its request id (`lastRequest`, `:237`) and the answers (`folios`, `:234`) lived in that body. Closing mid-answer dropped them. `askApi.submit` has no abort, so the gateway still answered and saved the folio, which was paid for. The panel reopened blank, and a new question minted a new request id (`:342`), so the house paid a second time.

**Fix.** The founder chose "Keep answering (Recommended)". `useAskSession` holds that state and `useAskPanel` owns it, so it outlives the body. Reopened mid-answer, the panel says it is still answering and stays busy. "Check again" re-sends the same id, which the gateway never charges twice for one person in one house (`bound-ask.service.ts`). [Narrowed in gate round 2: this said "never charges twice". The once-per-id key is unique on house, person and id (`supabase/migrations/20260922220000_mudavym_bound_reading_folios.sql:26`), so the same id sent with another house's token is a new call; see the OPEN entry "A request can carry another house's token" below.] Pinned in `AskPanel.test.tsx` ("closing keeps the question in flight"). [Corrected in round 1: this said six tests render the real owner, each mutation-tested. Five render the real owner and the sixth calls `useAskSession` through `renderHook`; and six guards (the verify's M1-M6) survived mutation. Round 1 pins five and removes the sixth (M2), which guarded only the closed body's own state; see the ADR's "Round 1" note.]

**Narrowed in round 1.** A close keeps the question in flight, its answer, a failure that offers "Check again" with its request, the proposer's refusal and the proposals still waiting. It drops a failure with nothing to retry, the proposer's transport error, and any proposal already applied, discarded, handled or failed, so none of them comes back on a reopen. [Corrected in round 2: the code kept a failure by its kind alone, so a folio re-read that timed out while no earlier question's request was held, and so with nothing to re-send, came back after a reopen as an alert with no button. It now keeps a failure only when its alert offers "Check again" (`useAskSession.ts`, the close effect); see the ADR's "Round 2".]

## The Ask session outlived a house switch, so "Check again" could pay in the wrong house — ~~OPEN~~ CLOSED for a switch made in the same tab by `fix/ask-close-no-second-spend` round 1 — 2026-10-01

Found by the Sonnet verify of this branch's first build (not on `main`: the session came with that build). Line numbers are at the branch's first head, 2958a4590.

**What.** `useAskSession()` and `useAskPanel()` took no person or house (`useAskSession.ts:55`, `useAskPanel.ts:24-27`). The shell is mounted once by the layout route (`App.tsx:355-358`) and a branch switch happens in place (`RestaurantBranchSwitcher.tsx:44-50`, `AuthContext.tsx:608-640`). So house A's answers, failure and kept request showed in house B. "Check again" re-sent house A's request id in house B, and the once-per-id key includes the house (`supabase/migrations/20260922220000_mudavym_bound_reading_folios.sql:26`), so that was a new paid call. A house-A answer in flight landed in house B's list.

**Fix.** `useAskPanel` keys the session by `<person>@<house>`, as `bindHouseSaid` does (`houseSaid.ts`), and a change starts it again. An epoch discards an answer, refusal, proposal or failure begun under the old key, and stops its end from releasing a newer request's gate. The open panel's body is keyed by the same scope, so it re-reads the new house's proposals and pickers. Pinned by the "one person in one house" tests in `AskPanel.test.tsx`; each guard turned a test red under mutation, and an epoch check on a folio re-read's answer, which no test could see (the reset empties the list it maps over), was removed (ADR 0145, "Round 1"). [Corrected in round 2: true only of the 32 mutations round 1 ran. The verify's own 60 left twelve real gaps green, four of them guards of this fix (clearing the old house's proposals, refusal and error, and moving the bound scope on). Round 2 pins all twelve; of the 64 mutations it ran, 61 turn a test red and 3 were judged equivalent (ADR 0145, "Round 2").]

[Gate round 2, 2026-10-02: CLOSED covers a switch made in place in the same tab, from the render in which the scope moves. It does not cover two routes in which a request carries another house's token while the session still holds the old house: a switch made in another tab, and the interval in the same tab between storing the new token and that render. The audit at 55a52ad05 (`.planning/07-reference/pr-audits/584-55a52ad05.md`) found this entry claimed more than the code. Both routes are filed in the OPEN entry below.]

## A request can carry another house's token while the Ask session still holds the old house — OPEN — 2026-10-02

Filed by `fix/ask-close-no-second-spend` gate round 2, from the ADR 0090 audit at 55a52ad05. Line numbers are at `origin/main` e25ebf537; this branch changes none of the files cited here except `useAskPanel.ts`, cited at this branch's head.

**What.** The session's scope is `<person>@<house>` from this tab's React state (`apps/web/src/components/askai/useAskPanel.ts:31`). Each request the panel sends carries the token `localStorage` holds at that moment: the request interceptor reads it on every call (`apps/web/src/services/api/client.ts:74-84`), and the gateway takes the house from the token (`apps/api-gateway/src/auth/strategies/jwt.strategy.ts:36-37`). Two routes let the token and the scope name different houses.

- **(a) A house switch in another tab.** A browser's tabs share `localStorage`, and the switch stores the new token there (`apps/web/src/contexts/AuthContext.tsx:625`). Nothing in the web app moves this tab's house on a `storage` event: the only `storage` listeners are `apps/web/src/lib/sessionRenewed.ts:57`, for the session-renewed key, and `apps/web/src/lib/mudavym/groundChoice.ts:433`. This tab's house state is set only by its own `AuthContext` (`:485`, `:597`, `:630`, `:839`). The setter that re-reads the token's house is `fetchAndSetBranches` (`:483-485`), which runs when this tab's `user` changes (`:602`) or from `refreshBranches` (`:588-590`). Until one of those runs, or a reload, this tab's scope stays on house A while its requests carry house B's token. A send from it goes to house B, and its answer lands in this tab's list under house A, since the epoch has not moved. "Check again" re-sends house A's request id with house B's token. The once-per-id key is unique on house, person and id (`supabase/migrations/20260922220000_mudavym_bound_reading_folios.sql:26`), so for a question that names no earlier folio this is a new paid call in house B. One that names house A's folio is refused before any paid work (`apps/api-gateway/src/ask-readings/reading-folio.store.ts:90`). This route was already on `main`.
- **(b) The same tab, between storing the token and the render.** `setActiveRestaurantId` stores house B's token (`AuthContext.tsx:625`) and then sets the house state (`:630`). The scope moves at the next render. A send in that interval goes out with house B's token under house A's scope; its answer is dropped if it arrives after the reset moves the epoch. The interval is short and may be unreachable by a click. That is inferred from how React 18 schedules updates; it was not measured. Separately, when the token names a different house from the one asked for, `:627` returns before the house state is set, so the token and the scope stay apart until `fetchAndSetBranches` next runs. Whether the gateway ever returns such a token was not checked.

**Fix (not built).** Two possible fixes:
- Store the token only once the scope has moved. That means after the render, not merely after the `setState` call in the same block, since both run before React renders. This closes (b) only. It also moves the window rather than removing it: a send made between the render and the store would carry house A's token under house B's scope.
- Before a send, including a re-send, check that the house named by the token in `localStorage` (`tokenHouse`, `apps/web/src/lib/houseMemory.ts:243`) matches the session's scope, and refuse the send when it does not. Done where the request interceptor reads the token (for example, the request carries the scope's house for the interceptor to compare), this covers both routes for the panel. Done earlier, in the session, it leaves the gap between the check and that read.

Neither was built in this PR. The audit asked for the two routes to be filed (`.planning/07-reference/pr-audits/584-55a52ad05.md`, "Why it blocks", item 2). Route (a) was already on `main`.

## The proposer has no request id, so a reload mid-draft can pay twice — OPEN — 2026-10-01

Filed by `fix/ask-close-no-second-spend` (ADR 0145, "Amendment, 2026-10-01").

**What.** `proposeAction` posts `{ utterance }` only (`services/api/askAi.ts:173-174`). There is no id the gateway could use to recognise a repeat. The fix above keeps this panel busy across a close, so a person cannot draft twice from it. A reload mid-draft, or a second tab, still sends a second paid call, and a second proposal row.

**Fix (deferred).** Give `POST /ask-ai/propose` a request id with the same once-per-id rule the bound ask has, and send it from the panel.
