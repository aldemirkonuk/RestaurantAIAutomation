## Closing the Ask panel mid-answer dropped the answer, and asking again paid twice — ~~OPEN~~ CLOSED by `fix/ask-close-no-second-spend` — 2026-10-01

Filed by `fix/ask-close-no-second-spend` ([ADR 0145](../decisions/0145-mudavym-answers-out-of-a-reading.md), "Amendment, 2026-10-01"). Found by the audit of PR #575 on 2026-10-01, which rated it a note, not a block: it was pre-existing, and #575 only added a more visible trigger. Line numbers are at `origin/main` 5a330a88e.

**What.** `AskPanel` returns null when closed (`AskPanel.tsx:579`), so its body unmounts in both placements. The question in flight, its request id (`lastRequest`, `:237`) and the answers (`folios`, `:234`) lived in that body. Closing mid-answer dropped them. `askApi.submit` has no abort, so the gateway still answered and saved the folio, which was paid for. The panel reopened blank, and a new question minted a new request id (`:342`), so the house paid a second time.

**Fix.** The founder chose "Keep answering (Recommended)". `useAskSession` holds that state and `useAskPanel` owns it, so it outlives the body. Reopened mid-answer, the panel says it is still answering and stays busy. "Check again" re-sends the same id, which the gateway never charges twice for one person in one house (`bound-ask.service.ts`). [Narrowed in gate round 2: this said "never charges twice". The once-per-id key is unique on house, person and id (`supabase/migrations/20260922220000_mudavym_bound_reading_folios.sql:26`), so the same id sent with another house's token is a new call; see the OPEN entry "A request can carry another house's or person's token" below.] Pinned in `AskPanel.test.tsx` ("closing keeps the question in flight"). [Corrected in round 1: this said six tests render the real owner, each mutation-tested. Five render the real owner and the sixth calls `useAskSession` through `renderHook`; and six guards (the verify's M1-M6) survived mutation. Round 1 pins five and removes the sixth (M2), which guarded only the closed body's own state; see the ADR's "Round 1" note.]

**Narrowed in round 1.** A close keeps the question in flight, its answer, a failure that offers "Check again" with its request, the proposer's refusal and the proposals still waiting. It drops a failure with nothing to retry, the proposer's transport error, and any proposal already applied, discarded, handled or failed, so none of them comes back on a reopen. [Corrected in round 2: the code kept a failure by its kind alone, so a folio re-read that timed out while no earlier question's request was held, and so with nothing to re-send, came back after a reopen as an alert with no button. It now keeps a failure only when its alert offers "Check again" (`useAskSession.ts`, the close effect); see the ADR's "Round 2".]

## The Ask session outlived a house switch, so "Check again" could pay in the wrong house — ~~OPEN~~ CLOSED for a switch made in the same tab by `fix/ask-close-no-second-spend` round 1 — 2026-10-01

Found by the Sonnet verify of this branch's first build (not on `main`: the session came with that build). Line numbers are at the branch's first head, 2958a4590.

**What.** `useAskSession()` and `useAskPanel()` took no person or house (`useAskSession.ts:55`, `useAskPanel.ts:24-27`). The shell is mounted once by the layout route (`App.tsx:355-358`) and a branch switch happens in place (`RestaurantBranchSwitcher.tsx:44-50`, `AuthContext.tsx:608-640`). So house A's answers, failure and kept request showed in house B. "Check again" re-sent house A's request id in house B, and the once-per-id key includes the house (`supabase/migrations/20260922220000_mudavym_bound_reading_folios.sql:26`), so that was a new paid call. A house-A answer in flight landed in house B's list.

**Fix.** `useAskPanel` keys the session by `<person>@<house>`, as `bindHouseSaid` does (`houseSaid.ts`), and a change starts it again. An epoch discards an answer, refusal, proposal or failure begun under the old key, and stops its end from releasing a newer request's gate. The open panel's body is keyed by the same scope, so it re-reads the new house's proposals and pickers. Pinned by the "one person in one house" tests in `AskPanel.test.tsx`; each guard turned a test red under mutation, and an epoch check on a folio re-read's answer, which no test could see (the reset empties the list it maps over), was removed (ADR 0145, "Round 1"). [Corrected in round 2: true only of the 32 mutations round 1 ran. The verify's own 60 left twelve real gaps green, four of them guards of this fix (clearing the old house's proposals, refusal and error, and moving the bound scope on). Round 2 pins all twelve; of the 64 mutations it ran, 61 turn a test red and 3 were judged equivalent (ADR 0145, "Round 2").]

[Gate round 2, 2026-10-02: CLOSED covers a switch made in place in the same tab, from the render in which the scope moves. It does not cover two routes in which a request carries another house's or person's token while the session still holds the old scope: a house or person switch made in another tab, and the interval in the same tab between storing the new token and that render. The audit at 55a52ad05 (PR #584 comment 5963268424) found this entry claimed more than the code. Both routes are filed in the OPEN entry below.]

## A request can carry another house's or person's token while the Ask session still holds the old scope — OPEN — 2026-10-02

Filed by `fix/ask-close-no-second-spend` gate round 2, from the ADR 0090 audit at 55a52ad05. Route (a) was widened from a house switch to a house or person switch in that round's second push, after tracing a sign-out and a sign-in as another person in another tab. Its trace was made conditional on person B in gate round 3, from the audit at 3d847e44f (PR #584 comment 5973211787), and its reloads and redirects were given their conditions after the audit at 4867c4a37, which the gate's comment numbers gate round 3 (PR #584 comment 5973720893; this entry's "gate round 3" above is the round after the audit at 3d847e44f). At 4867c4a37 the planner first held the gate on one PR-body sentence, which was corrected in the body alone before any audit marker existed; then Reviewer A approved, and Reviewer B blocked on two sentences in route (a): the reloads, stated without their conditions, and "Each redirect or reload above loads the page again". Gate round 4, at 795803f42 on 2026-10-03 (PR #584 comment 5975574964), blocked on two phrases in the PR body that named no commit, and on nothing in this entry. Line numbers are at `origin/main` 661068ab3; this branch changes none of the files cited here except `useAskPanel.ts`, cited at 4867c4a37, and `HouseShell.tsx` and `AskAiSurface.tsx`, whose cited lines are the same at 661068ab3 and 4867c4a37. [Gate at 4867c4a37: this said `useAskPanel.ts` was "cited at this branch's head", and named no other file.]

**What.** The session's scope is `<person>@<house>` from this tab's React state (`apps/web/src/components/askai/useAskPanel.ts:31`). Each request the panel sends carries the token `localStorage` holds at that moment: the request interceptor reads it on every call (`apps/web/src/services/api/client.ts:74-84`), and the gateway takes the house from the token (`apps/api-gateway/src/auth/strategies/jwt.strategy.ts:36-37`) and the person from its `sub` (`apps/api-gateway/src/auth/auth.service.ts:1432`). Two routes let the token and the scope name a different house or person.

- **(a) A house or person switch in another tab.** A browser's tabs share `localStorage`. A house switch stores the new token there (`apps/web/src/contexts/AuthContext.tsx:625`). So does a person switch: signing out removes the pair (`:964-965`), and signing in as another person stores theirs (`storeSession`, for example in `login` at `:671`). No `storage` listener in this tab acts on either. The only `storage` listeners in the web app are `apps/web/src/lib/sessionRenewed.ts:57`, which acts only on the session-renewed key (`:54`), written only when a password change hands back a new pair (`:39`, called from `apps/web/src/services/api/profile.ts:48`), and `apps/web/src/lib/mudavym/groundChoice.ts:559`, which re-reads only the ground setting of the person it already holds (`:548-557`). This tab's house state is set only by its own `AuthContext` (`:485`, `:597`, `:630`, `:839`), and its person only by that `AuthContext`'s own `setUser` calls: on mount (`:380`, in an effect with no dependencies, `:436`), in its sign-in, register and switch paths, and at its sign-out (`:988`). The setter that re-reads the token's house is `fetchAndSetBranches` (`:483-485`), which runs when this tab's `user` changes (`:602`) or from `refreshBranches` (`:588-590`). What reaches this tab before a send depends on the pair the other tab stored, and on B, the person it names (A again after a house switch). Each case below was read in the code, not run. None makes a paid call. On a route that does not opt out, both 403s are raised in `JwtAuthGuard`, before the route's handler runs (`apps/api-gateway/src/auth/guards/jwt-auth.guard.ts:84`, `:94`), and neither Ask controller opts out of either check (outside tests, `@AllowUnverified()` and `@AllowsNoHouse()` are applied only in `auth.controller.ts` and `organizations.controller.ts`). After a refresh answered `houseAccessEnded`, the request that drew the 401 is not retried (`apps/web/src/services/api/client.ts:138-140`, `apps/web/src/contexts/AuthContext.tsx:270-279`), and a reload re-sends nothing from the session it empties. [Gate at 4867c4a37: this said a reload sends no request; the page it loads sends its own.]
  - If B is not verified, a request this tab then makes through `apiClient` to a route that does not opt out is refused 403 `EMAIL_NOT_VERIFIED`, and the tab is sent to `/verify-email` (`apps/web/src/services/api/client.ts:147-155`).
  - If B's pair names no house, a request this tab then makes to a house-bound route, through either client, is refused 403 `HOUSE_REQUIRED` (`apps/api-gateway/src/common/tenant/assert-house-chosen.ts:19`), and the tab is sent to `/choose-house` (`client.ts:158-164` and `AuthContext.tsx:283-288`, both through `apps/web/src/lib/houseMemory.ts:333-338`). A sign-in names no house when B is a member of none, or of several with no recent hint for one of them on that device (`apps/api-gateway/src/auth/house-choice.ts:104-115`). `login` stores that pair (`AuthContext.tsx:657-658`, `:671`), and `storeSession` removes `activeRestaurantId` (`houseMemory.ts:260-266`). A query refetched when this tab regains focus (`apps/web/src/App.tsx:154`) can be the first such request.
  - A refresh answered `houseAccessEnded` sends the tab to the chooser too (`client.ts:48-49`, `apps/web/src/lib/sessionRefresh.ts:56-57`).
  - Independently of the switch, a stale chunk or a service-worker update can reload the tab, each under a condition. [Gate at 4867c4a37: this said they reload it, without the conditions.] A stale-chunk error reloads it only when a route page wrapped by `lazyWithRefresh` fails to load with an error that `isStaleChunkError` matches (`App.tsx:10-21`, `:33-36`), or an error whose message the boundary's own test matches (`apps/web/src/components/ErrorBoundary.tsx:80-86`, which leaves out `text/html`) reaches an error boundary (`:87-89`), and only while this tab's `sessionStorage` holds no `chunk_reload` flag; the reload sets the flag. Only a later successful load of a page wrapped by `lazyWithRefresh` clears it (`App.tsx:28-30`). With the flag set there is no reload: the route page's error is thrown (`App.tsx:41`) to the nearest error boundary, which shows it (its fallback, `ErrorBoundary.tsx:199-212`, or else its own screen from `:213`). A service-worker update reloads the tab only if a service worker controlled the page when `registerServiceWorker` ran, as the page loaded (`apps/web/src/lib/register-sw.ts:15`, called from `apps/web/src/main.tsx:26`), not under Vite's dev server unless `VITE_FORCE_SW` is `1` (`register-sw.ts:11-12`), and at most once per page load (`:16-20`).

  A redirect or reload above that runs loads the page again, which empties the Ask session, held only in this page's memory; one that does not run leaves no session to send from, or leaves the tab in whichever case B puts it (for a verified B whose pair names a house, the case below). [Gate at 4867c4a37: this said "Each redirect or reload above loads the page again"; not each runs.] The redirect to the chooser does not run when the tab's pathname is exactly `/choose-house`, `/no-access` or `/login` (`houseMemory.ts:335-337`), and the one to `/verify-email` does not run when it is exactly `/verify-email` (`client.ts:152`). Those routes render outside `DashboardLayout` (`App.tsx:192`, `:196`, `:198`, `:199`; the layout's route is `:355-359`), and the Ask session lives only inside it: outside tests, `useAskPanel` is called only from `apps/web/src/components/mudavym/HouseShell.tsx:138` and `apps/web/src/components/askai/AskAiSurface.tsx:32`, mounted at `apps/web/src/components/layout/DashboardLayout.tsx:66` and `:149`. A reload that does not run leaves the session where it was, with one exception: a stale-chunk error thrown while a routed page renders, which does not reload, is shown under the shell by the boundary around the routed page (`HouseShell.tsx:290`), which leaves the shell and its session mounted, but in the legacy layout by the root boundary (`App.tsx:167`), which unmounts the session. When B is verified and B's pair names a house, neither 403 applies. Between the sign-out and the sign-in, a request through `apiClient`, the panel's client, carries no token, and the 401 that follows finds no refresh token, so it is rejected without navigating (`client.ts:107-108`). `AuthContext`'s own client then gets no new token from `doRefresh` on a 401 and does not navigate either (`AuthContext.tsx:259-279`, `sessionRefresh.ts:39-40`). After the sign-in, B's token is valid, so no 401 comes back until it expires. A refresh that succeeds without `houseAccessEnded` then stores B's new pair and calls no `setUser`, so it moves no scope (`client.ts:45`, `sessionRefresh.ts:51`). In the two response interceptors (`client.ts:96`, `AuthContext.tsx:252`), the only redirect to `/login` follows a refused refresh on `apiClient` (`client.ts:120-123`). Outside them, `apps/web/src/stores/authStore.ts:296` also redirects to `/login`, in `loadUser`, which that module calls once, when it loads (`:327`). The websocket's connection error only records the error (`apps/web/src/lib/websocket.tsx:513-517`). So in that case, until this tab's own `AuthContext` moves its scope to match the token, or the tab loads again, its scope stays on person A in house A while its requests carry the other token. After a person switch, `fetchAndSetBranches` alone does not do that, since it moves the house and not the person. A send from it goes out with that token, and its answer lands in this tab's list under A's scope, since the epoch has not moved. "Check again" re-sends A's request id with that token. The once-per-id key is unique on house, person and id (`supabase/migrations/20260922220000_mudavym_bound_reading_folios.sql:26`), so for a question that names no earlier folio this can be a new paid call, in the other house or under the other person. One that names A's folio is refused before any paid work, since the folio is read by house and person (`apps/api-gateway/src/ask-readings/reading-folio.store.ts:90`). The person switch was traced in the code; it was not run in a browser. This route was already on `main`.
- **(b) The same tab, between storing the token and the render.** `setActiveRestaurantId` stores house B's token (`AuthContext.tsx:625`) and then sets the house state (`:630`). The scope moves at the next render. A send in that interval goes out with house B's token under house A's scope; its answer is dropped if it arrives after the reset moves the epoch. The interval is short and may be unreachable by a click. That is inferred from how React 18 schedules updates; it was not measured. Separately, when the token names a different house from the one asked for, `:627` returns before the house state is set, so the token and the scope stay apart until `fetchAndSetBranches` next runs. Whether the gateway ever returns such a token was not checked.

**Fix (not built).** Two possible fixes:
- Store the token only once the scope has moved. That means after the commit of the render that moves the scope, not merely after the `setState` call in the same block, since both run before React renders. Of the two routes it addresses only (b): another tab's store never moves this tab's scope, so (a) is untouched. It covers (b)'s `:627` case only if a token naming a house other than the one asked for is not stored at all. It does not remove the interval; it reverses it. Between that commit and the store, the scope names house B while `localStorage` still holds house A's token, so a send made then would carry house A's token under house B's scope. Whether a send can be made in that interval depends on where the store is done; it was not measured.
- Before a send, including a re-send, check that the person and the house named by the token in `localStorage` (its `sub`, read by `tokenClaims`, and `tokenHouse`: `apps/web/src/lib/houseMemory.ts:225`, `:243`) match the session's scope, and refuse the send when either does not. Done where the request interceptor reads the token (for example, the request carries the scope for the interceptor to compare), this covers both routes for the panel. A check on the house alone would miss a person switch within one house. Done earlier, in the session, it leaves the gap between the check and that read.

Neither was built in this PR. The audit asked for the two routes to be filed (PR #584 comment 5963268424, "Why it blocks", item 2). Route (a) was already on `main`.

## The proposer has no request id, so a reload mid-draft can pay twice — OPEN — 2026-10-01

Filed by `fix/ask-close-no-second-spend` (ADR 0145, "Amendment, 2026-10-01").

**What.** `proposeAction` posts `{ utterance }` only (`services/api/askAi.ts:173-174`). There is no id the gateway could use to recognise a repeat. The fix above keeps this panel busy across a close, so a person cannot draft twice from it. A reload mid-draft, or a second tab, still sends a second paid call, and a second proposal row.

**Fix (deferred).** Give `POST /ask-ai/propose` a request id with the same once-per-id rule the bound ask has, and send it from the panel.
