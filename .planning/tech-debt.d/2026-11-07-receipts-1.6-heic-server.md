## The door still uploads a HEIC photo as it was taken — OPEN — 2026-11-07

Filed by `fix/photo-arrives-readable` (proposal `p4-scratch/sw-menu-receipts/proposal-receipt.md` §3, Phase 1A row 1.6). Every fork in this lane was the session's call under the founder's /goal of 2026-11-07 ("Do not ask me any questions I approve you decide them all").

**What is true.** This branch is the server half only. `DocumentExtractorService.extract` now stores a HEIC/HEIF or AVIF photo unread, with a sentence asking for a JPEG or a re-take, instead of sending it to the model labelled JPEG (`claims.d/fix-photo-arrives-readable.jsonl:1`). The receiver still loses the read: the paper lands in `needs_review` with no fields.

**What closes it.** The client half, on its own branch: a new `apps/web/src/lib/imageDownscale.ts` (`createImageBitmap` → canvas → JPEG, long-edge cap, keeps the original when it cannot decode) wired into `DoorNext.tsx`, with a Browser-pane run on a real HEIC and measured before/after sizes in its PR. jsdom has no real canvas, so its unit test covers only the fallback.

## Decisions taken in the server half, and what they leave — OPEN — 2026-11-07

Filed with the entry above.

- **AVIF is refused too, by its own name.** The model takes JPEG, PNG, GIF and WebP images only (https://platform.claude.com/docs/en/build-with-claude/vision#supported-formats), so AVIF labelled JPEG is the same defect. `mif1`/`msf1` (generic HEIF) are named HEIC; only the major brand at bytes 8-11 is read, so an AVIF whose major brand is `mif1` is called HEIC. Both are refused either way; only the word differs.
- **The refusal runs before the `ANTHROPIC_API_KEY` guard**, so it needs no model. The intake still checks `available()` first (`document-intake.service.ts:698`), so with no key configured the intake's own "no extraction model" sentence wins; untouched here because PR #688 edits that file.
- **The bare fallback is no longer `image/jpeg`.** Unrecognised bytes with no supported declared type now come back unread with `UNREADABLE_FILE_FORMAT`. Two things now take that path that used to reach the model and fail there: a PDF with bytes before `%PDF` and no `pdf` in its declared type, and a `text/*` invoice that is not X12 (`isDocumentLike` admits both). Neither was read before; now each says why. Not measured on production: no count was taken of how many stored papers carry those shapes.
- **A declared supported type still beats the bytes** (unchanged): JPEG bytes declared `application/pdf` go as a PDF. Only HEIC/AVIF bytes override the label.
