## /inventory zone writes were shown as saved when refused, and the in-zone bottle stepper never saved — ~~OPEN~~ CLOSED 2026-09-28 (fix/storage-location-writes) — 2026-09-28

Filed by the web endpoint sweep (`.planning/handoff/evidence/WEB-ENDPOINT-SWEEP-2026-09-28.md` on `main-1ll9rp`, §2 rows 4, 5 and 6, lane B). Re-verified on `2ba1326e3` before fixing; all three reproduced. Filed and closed in one PR, so it can be checked again.

**What.** (#4) The zone editor's PATCH body was the web's camelCase object, so any zone with a parent sent `parentId`; `UpdateStorageLocationDto` declares `parent_id`, and main.ts's pipe runs `forbidNonWhitelisted`, so the whole edit was a 400. (#5) `useStorageLocations.persistToServer` caught and discarded every error, so that 400, and every failed assign, remove, edit or delete, stood on screen as saved until the next refetch; auto-locate's toast was `selected.length` whatever the writes did. (#6) `updateWineQuantityAtLocation` moved the cache and made no request, so the count went back on refresh. **Found while fixing:** `storage_locations` has no parent column at all (baseline `20260805000000_baseline_from_production.sql:5487-5511`), and `StorageLocationsService` never read `parent_id`, so a parent that got past the pipe would have been answered 200 and dropped: the same "shown as saved" defect one layer down.

**Fix.** The hook builds the PATCH body from a whitelist (`toUpdateBody`): `parent_id` (null when the picker is empty, which is how it clears), `current_count`, and the fields the DTO declares. Both DTOs type `parent_id` as `string | null`. The service refuses a non-null `parent_id` on create and update with a 422 that says zone parents are not stored yet, and writes nothing. `persistToServer` now resolves true or false; on failure it runs a per-write rollback (the prior zone, the removed zone and its wines, the prior mapping, the pre-burst count), shows an error toast with the gateway's reason, and resolves false. The editor stays open on a refused save. Auto-locate goes through `assignMany` and reports what was accepted (success, partial warning, or error). The stepper saves the last value of a burst to the existing `POST /storage-locations/:rid/mappings` upsert after `QUANTITY_SAVE_DEBOUNCE_MS` (500 ms), flushes a pending save on unmount, and rolls back on refusal. A wine assigned to a zone still on its temp id is refused in words instead of counted.

**Behaviour that did change.** Choosing a parent in the zone editor, on create or edit, now fails with a toast instead of appearing to save. That picker is now a control that can only fail, and whether to store zone hierarchy (a migration) or remove the picker is a founder fork, not taken here.

**Evidence.** `apps/web/src/hooks/useStorageLocations.writes.test.tsx`: 8 cases, 8 red on `2ba1326e3`, 8 green after; removing the rollback call turns 5 of them red again. `apps/api-gateway/src/storage-locations/storage-locations-parent.spec.ts`: runs `UpdateStorageLocationDto` / `CreateStorageLocationDto` through a pipe built from main.ts's own options (parsed from source): 2 of 8 red on `2ba1326e3` (the 422 refusals); the null and camelCase pipe cases already held and pin that. CLAIMS `SWEEP-2026-09-28-ZONE-WRITES-4-5-6` (`resolved`, static), every sub-check red on `2ba1326e3`.

**Not covered.** The service still drops `description`, `temperature` and `humidity` on create and update (only name, capacity, count, colour and notes are written), so those edits also look saved and are not. No component-level test drives the editor or the auto-locate page; the page change is covered by tsc and the hook tests only. Zone `current_occupancy` is never written by a mapping write: `POST`/`DELETE /storage-locations/:rid/mappings` touch `wine_location_mappings` only (`storage-locations.service.ts` writes `current_occupancy` at `:166` on create and `:199` on an explicit `current_count` update, nowhere else, and no migration has a trigger on it), and the hook's count moves are cache-only, so after the next refetch the zone pickers and auto-locate read a stale count: `LocationPickerCell.tsx:40` (full / not full) and `:130` (the `n/capacity` label), `autoLocateEngine.ts:61` (the running count it fills zones against). The manager's "recalculate" button (`recalculateLocationCounts`) is cache-only too. Found by the ADR 0090 audit of #510, 2026-09-29; not fixed here.

**[Amended 2026-09-29, ADR 0090 audit of #510 at `ba6c8f353`, blocker R2.]** The stepper's unmount flush read the house from the latest render: click under house OLD, switch to NEW, close the sheet inside the 500 ms debounce, and the hook POSTed OLD's wine and OLD's zone to `/storage-locations/<NEW>/mappings` (the gateway did not stop it: the session's house matched the path, and `locationId` is not checked against `restaurant_id`; PR #516 fixes that side separately). The pending arguments now carry the house the click was made in, and `saveQuantity` POSTs to and rolls back in that house. Chosen over dropping the pending click on a house change: both never write to another house, but a drop loses the click in silence, while a flush lands where it was made or, if the server refuses it because the session has moved on, rolls back and says so with the same error toast. Evidence: three `R2` cases in `useStorageLocations.writes.test.tsx`, two red at `ba6c8f353` (the timer case already held and pins it); CLAIMS `AUDIT-0090-PR510-R2-STEPPER-FLUSH-KEEPS-ITS-HOUSE`, red on the base hook.

**[Amended 2026-09-29, ADR 0090 audit of #510 at `283382ca3`, create blocker.]** The create form closed and reset on click while `addLocation` was still fire-and-forget, so a refused create (always, with a parent chosen: the 422 above) removed the optimistic zone and toasted only after the form and the typed input were gone. `addLocation` now resolves the stored zone or `null`; `handleCreate` awaits it, disables Create while it is in flight, and closes only on a stored zone. The parent picker is no longer rendered on create and `handleCreate` sends no `parentId`, so a create cannot walk into the 422; edit keeps the picker (it can still clear a parent, and a refused edit already keeps its form). This narrows the "Behaviour that did change" paragraph to edits; the store-or-remove-the-picker fork is unchanged. Evidence: `StorageLocationManager.create.test.tsx` (3 cases, 2 red on the pre-fix component) and two create cases in `useStorageLocations.writes.test.tsx`. The merge of main brought #516's `.maybeSingle()` into `updateLocation`, so `storage-locations-parent.spec.ts`'s mock chain gained `maybeSingle`.

**Severity:** medium while open. No money moves, but a manager's cellar map and bottle counts said things the server did not hold.
