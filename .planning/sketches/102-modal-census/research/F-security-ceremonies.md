# F — Security ceremonies catalogue

Scope: second-authority / commitment-protection ceremonies used by real products and
standards, for comparison against Mudavym's existing set (hold-to-approve "seal",
sealed order state transitions ADR 0125, approval tiers ADR 0128, challenge-and-redeem
tool-write seal, two-person rule for money, manager passcode at point of action,
presence on shared records). Founder's brief: adopt all applicable second-authority
ceremonies, "and any other possible security like that." This file is the survey;
adoption calls are not made here.

Legend: **V** = verified against a primary source (vendor doc, help centre, standard).
**U** = could not fully verify the specific claim; flagged inline.

## 1. Ceremony catalogue (24 rows)

| 1 | Step-up re-auth (sudo mode) | Session-riding: someone else at an already-unlocked device/tab performs a sensitive action | GitHub — [Sudo mode docs](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/sudo-mode) (V) | Person re-enters password/passkey/2FA; server timestamps a "sudo" grant good for 2h, any sensitive action resets the timer; every sensitive action is still individually authorized, not just gated once | Config change by the assistant (before it's allowed to write), publish a week | Low-medium — one re-auth prompt per session window, not per action | None — this is a session gate, not a per-write ceremony; doesn't touch "draft never looks sent" |

| 5 | Transaction-bound cryptogram (Apple Pay) | A captured or replayed payment credential being reused for a different amount/merchant | Apple — [Payment Token Format Reference](https://developer.apple.com/documentation/passkit/payment-token-format-reference) (V for `onlinePaymentCryptogram`/`eciIndicator` fields existing; **U** — could not independently confirm the specific term "Authorization Random" in Apple's public docs via search; the mechanism it names — a per-transaction random bound into the cryptogram — is standard practice for EMV-style tokenization, see row 6) | Device's Secure Element mints a one-time cryptogram per authorization, cryptographically bound to that transaction; issuer rejects any authorization request whose cryptogram doesn't match a live, unused, correctly-derived value | Release a payment, a tool write (as the model for binding a mint to one specific use) | None at the user layer — invisible; cost is entirely on the implementer | This *is* the challenge-and-redeem pattern Mudavym already has for tool writes — same shape, different domain |
| 6 | Dynamic linking (PSD2 SCA) | A man-in-the-middle altering the amount or payee after the customer authenticated | EU — [EBA RTS on Strong Customer Authentication](https://www.eba.europa.eu/eba-response/331); explainer at [okaythis.com](https://okaythis.com/blog/what-is-dynamic-linking) (V) | Authentication code is cryptographically generated from the exact amount + payee; PSP must show both to the payer before auth; any change to amount or payee post-auth invalidates the code and the transaction fails | Release a payment, approve an order | Regulatory floor for EU/UK card-not-present — not opt-in there | Directly generalizes Mudavym's two-person rule and seal: binding the seal to specific (amount, payee) is the domestic analogue |
| 7 | EMV 3-D Secure authentication | Card-not-present fraud using stolen card numbers without the true cardholder present | EMVCo — [EMV 3-D Secure](https://www.emvco.com/emv-technologies/3-d-secure/); dynamic-linking detail via [FIDO SPC white paper](https://fidoalliance.org/white-paper-secure-payment-confirmation/) (V) | Merchant/issuer exchange transaction + device data; issuer may challenge the cardholder (OTP, biometric via SPC); resulting cryptogram (dCVV/ARQC/DPA) encodes merchant ID + amount so it can't be replayed elsewhere | Release a payment (if Mudavym ever pays a card, not just ACH/wire) | User-facing friction only on "challenge" flows (frictionless flows are silent) | None |
| 8 | Scheduled/delayed release of payment | Fat-finger or coerced payment executing before anyone can catch it | Mercury — [Scheduling payments](https://support.mercury.com/hc/en-us/articles/28772869118100-Scheduling-payments) / [Canceling a payment](https://support.mercury.com/hc/en-us/articles/28775812171668-Canceling-a-payment) (V) | Payer schedules a future date; payment sits cancelable up to the processing cutoff (9am ET on the date); once ACH/wire submits, it's no longer cancelable — the delay window is the only recourse | Release a payment | Low — no extra step for the payer, but removes "instant" as a default | Could sit awkwardly against "wax for real commitment": a delay is not itself a ceremony a person performs, it's a standing policy — pairs well with the seal rather than replacing it |
| 9 | New-payee cooling-off / Confirmation of Payee | Authorized-push-payment (APP) fraud: paying a scammer's account because the name didn't match | UK Finance / regulators — [Confirmation of Payee](https://www.ukfinance.org.uk/policy-and-guidance/guidance/confirmation-payee); 24h gap noted at [Trustpair](https://trustpair.com/blog/confirmation-of-payee-regulation/) (V for CoP; the specific "24-hour delay on first payments" was a UK parliamentary *recommendation*, not universally implemented law — mark **U** for enforcement status) | System matches the name typed against the name on the receiving account before the payer confirms; mismatches surface a warning the payer must act on; some banks additionally can't run CoP in the account's first 24h and flag that as reduced assurance | Add a payee/vendor bank detail | Low — a warning screen, only blocks on explicit override | None — this is exactly the shape of a "first payment hold" Mudavym could add on new vendor banking details |
| 10 | First-payment hold / allowlisted payees | A single compromised session moving money to a brand-new, unverified destination | Composite pattern from bank treasury docs — [U.S. Bank fraud prevention checklist](https://www.usbank.com/corporate-and-commercial-banking/insights/risk/mitigation/fraud-prevention-checklist.html) (V for the general "review payee exceptions" / multi-approval-for-new-payee pattern; exact "first payment always held N hours" as a named feature is **U** — not confirmed as a single vendor's branded feature, it's an assembled best practice across several) | New payee added → held or extra-approved on the first transaction only; once a payee has cleared once, subsequent payments to it move at normal speed | Add a payee/vendor bank detail, release a payment (first time to a given vendor) | Low ongoing cost once broken in; one-time friction per new vendor | Fits "ceremony is rationed": apply the heavier check only on the *first* payment to a payee, not every payment |
| 11 | Per-role / per-day / per-payee limits | A single approver (or a single compromised credential) moving unbounded amounts | Ramp — [Card limits and spend programs](https://support.ramp.com/hc/en-us/articles/10881975647763-Card-limits-and-spend-programs); Brex — [Spend limits](https://www.brex.com/platform/spend-limits) / [Vendor limits](https://www.brex.com/implementation/premium/8-create-a-vendor-limit) (V) | Admin sets a ceiling scoped to a person, a card, a vendor, or a period; the ceiling is enforced at authorization time (declined outright), not after the fact; some limits can be shared across several people | A price override by staff, release a payment, approve an order | None for normal spend inside the limit; friction only at the boundary (request an increase) | Complements the two-person rule rather than replacing it — a limit caps blast radius even when the second approver is compromised too |
| 12 | Break-glass access with written reason + audit | Legitimate emergency access becoming an unlogged backdoor | AWS Well-Architected — [Implement break-glass procedures](https://docs.aws.amazon.com/wellarchitected/latest/devops-guidance/ag.sad.5-implement-break-glass-procedures.md) (V) | Person invokes a dedicated emergency-access path (often MFA-hardened, separate credential); access is time-boxed, triggers an alert, and is manually reviewed/signed-off afterward; the reason is captured at invocation, not reconstructed later | A config change by the assistant, a tool write, when the founder must override a seal in an outage | Rare-path cost only — near-zero in normal operation, deliberately heavy when invoked | Aligns with "seal is rationed for real commitment" — break-glass is the emergency valve *around* the seal, not a substitute for it, and must leave the same audit trail a normal seal would |
| 13 | Recall / undo window | An action completed correctly at the moment, but wrong in hindsight, with no way back | Gmail — [Send or unsend messages](https://support.google.com/mail/answer/2819488) (5–30s undo send) (V); Linear — [Delete and archive issues](https://linear.app/docs/delete-archive-issues) (30-day recoverable trash) (V); Toast — [Redisplaying tickets with recall and unfulfill](https://doc.toasttab.com/doc/platformguide/adminRedisplayingTickets.html) (V) | A short client-side buffer (Gmail) or a soft-delete window (Linear) or an explicit recall action (Toast KDS) keeps the artifact recoverable; recall on Toast re-marks a fulfilled ticket unfulfilled and stamps it CHANGED so the kitchen sees the edit, not a silent revert | A door delivery on a shared tablet (recall a bump), publish a week (undo before it's read) | Very low — the whole point is that it costs nothing to use and nothing if unused | Strong fit — this is the "draft never looks sent" principle already, applied to something that *did* go out: cheap reversibility for correctable classes, distinct from irreversible commitments that need the seal instead |
| 14 | Tamper-evident audit trail (hash-chained log) | An insider (or a compromised admin) editing history after the fact without detection | AWS — [Validating CloudTrail log file integrity](https://docs.aws.amazon.com/awscloudtrail/latest/userguide/cloudtrail-log-file-validation-intro.html) (hourly digest files, RSA-signed, each referencing the prior digest's hash) (V); Microsoft — [SQL Server / Azure SQL Ledger](https://learn.microsoft.com/en-us/sql/relational-databases/security/ledger/ledger-overview) (append-only tables + periodic digests exportable to WORM storage) (V) | Every write/log entry is hashed; digests chain to the previous digest so any retroactive edit breaks the chain and is detectable by independent verification, not by trusting the log's own claim | The recorded proof behind every sealed act — orders, payments, write-offs, published weeks | Low ongoing cost (background hashing); verification is opt-in/periodic | This is the concrete technique for "the seal is verifiable after the fact" — worth adopting as the storage layer under the seal stamp, not a user-facing ceremony |

| 17 | Notify-on-every-money-move (push + out-of-band confirm) | A payment moving without the account owner noticing until a statement arrives | Chase — [Account Alerts](https://www.chase.com/personal/mobile-online-banking/login-alerts) (V); American Express in-app purchase alerts (V, per Amex app settings described in search results, not a single stable doc URL — mark **U** for a citable permalink) | Every transaction (or every transaction over a threshold) triggers an immediate push/SMS/email; the channel is separate from the one that initiated the payment, so a compromised approval flow doesn't also suppress the notice | Release a payment, write off stock (as the notify-only variant for lower-tier acts) | Very low — passive, no action required unless something's wrong | Good fit for acts *below* the seal threshold — visibility without ceremony, keeps ceremony "rationed" per house rule |
| 18 | Velocity / anomaly holds for review | A single valid credential being used for a burst of transactions consistent with fraud or a bug, not a person's normal pattern | Stripe — [Radar rules & review queue](https://docs.stripe.com/radar/rules) (payment still authorized but routed to a human review queue if it matches a risk rule) (V); Ramp — [Policy Agent](https://ramp.com/blog/why-poor-spend-control-can-hurt-your-revenue) reviewing 100% of transactions, flagging vendor-spend spikes (V) | System scores each event against learned/normal patterns; a match holds the action in a review state rather than blocking or allowing outright; a human clears or reverses it | Release a payment, approve an order, a price override by staff | None for normal activity; only unusual activity pays the cost | Fits well as a *background* check that triggers extra ceremony only when needed — the essence of "rationed," since it doesn't add friction to the common case |
| 19 | Separation of duties (SoD) matrix | One person having end-to-end control of a financial process (create vendor → approve invoice → release payment → reconcile), enabling undetected fraud or error | SOX-derived AP practice — [Segregation of Duties in Accounts Payable](https://ramp.com/blog/accounts-payable/segregation-of-duties-in-accounts-payable) (V) — names the 5-function split: vendor master maintenance, invoice entry, invoice approval, payment release, reconciliation | Roles are assigned so no single person can both originate and finally authorize the same transaction; enforced structurally (permissions), not just by policy memo | Add a payee/vendor bank detail (vs. approve an order vs. release a payment should ideally be 3 different capable people, or the same person barred from wearing 2 hats on one transaction) | Organizational cost (needs ≥2–3 distinct role-holders) — hard in a very small restaurant, explicitly called out below in §3 | Directly underlies the two-person-rule the founder already adopted; the catalogue's job is to note it generalizes beyond payments to vendor-master changes too |

| 22 | Manager PIN at point of action ("Toast-style") — already adopted, included for comparison | A line employee overriding a control (void, comp, price change) that requires a supervisor's judgment | Toast — [Voiding checks](https://doc.toasttab.com/doc/platformguide/adminVoidingOrders.html) (manager POS code or swipe required for bulk-void without the specific permission) (V) | Staff attempts a restricted action; system blanks the screen for a manager credential; the manager's own identity (not the staff member's) is stamped as the authorizer of record | A price override by staff (already the named fit) | Low — manager is usually on-site; friction is proportional to how often overrides happen | Already adopted by the house; listed here to anchor the comparison table, not to re-propose it |

## 2. A fit per act

- **Approve an order** — (1) four-eyes with a comment (#20) if the order crosses a value threshold, so the second approver's tap means something; (2) passkey-backed seal (#23) to bind *who* held the gesture, not just that a hold happened.
- **Release a payment** — (1) dynamic linking (#6) so the seal is cryptographically bound to the exact amount+payee, not just "a payment happened"; (2) velocity/anomaly hold (#18) as a silent background check that only adds friction when something looks off; (3) notify-on-every-money-move (#17) as the passive backstop underneath the two-person rule.
- **Add a payee / vendor bank detail** — (1) new-payee cooling-off + name-match warning (#9); (2) out-of-band confirmation (#24) specifically for bank-detail *changes* on an existing vendor, the highest-fraud single act on this list; (3) separation of duties (#19) so the person who can create a vendor isn't also the one who can release the first payment to it.
- **Write off stock** — (1) per-role/per-day limits (#11) so a write-off above a threshold needs escalation; (2) tamper-evident audit trail (#14) so a pattern of "write off, restock, write off" is provably visible later, not just logged.
- **A price override by staff** — manager PIN at point of action (#22) — already adopted, no addition needed beyond what's there; device trust/kiosk lock (#16) is the precondition that makes the PIN meaningful on a shared tablet.
- **Publish a week** — (1) recall/undo window (#13), Toast-KDS-recall-shaped: publishing is cheap to reverse for a short grace period, distinct from acts that need a seal because they can't be undone; (2) tamper-evident audit trail (#14) so a republished/edited week is provably distinguishable from the original.
- **A config change by the assistant** — (1) step-up re-auth / sudo-mode-shaped gate (#1/#2) before the assistant's proposed change can be *applied* by a person; (2) time-boxed elevated session (#21) if "apply mode" is itself a privilege that should auto-expire rather than stay on.
- **A door delivery on a shared tablet** — (1) device trust/kiosk lock (#16); (2) recall window (#13) for correcting a receiving-count mistake logged seconds ago, without needing a full write-off ceremony.
- **A tool write** — (1) MFA-gated / challenge-bound temporary credential (#3), which is the closest API-shaped ancestor of the already-adopted challenge-and-redeem seal; (2) break-glass access with written reason (#12) for the rare case a tool write must bypass the normal challenge flow during an incident.

## 3. What to fight

- **Mandatory comment on every four-eyes approval (#20).** Forcing a text field on every single second-approval turns into "type something to make the button work," which is theatre the moment approvers run out of real things to say — better as optional/logged than compulsory.
- **QLDB-style standalone ledger database (#15).** The product is retired; building new infrastructure around a discontinued cryptographic-ledger service would be pure architecture cosplay. Use hash-chained digests (#14) on the store already in use instead.
- **Bank-grade 24-hour blanket delay on all new payees (#9's strongest form).** Mudavym's vendors are usually known restaurant suppliers the operator already has a relationship with — a blanket day-long hold on every new payee, regardless of amount, punishes the common case (a known distributor) to guard against the rare case (a spoofed one). Reserve the heavy version for bank-*detail changes* (#24), not every new vendor add.
- **Full Azure-PIM-style approval-gated JIT activation (#21) for routine staff actions.** Time-boxed elevated sessions are built for admins touching cloud infrastructure a few times a week; wiring the same request→approve→expire ceremony around, say, a shift-lead's daily tasks would be friction with no matching risk — it's a fit for the assistant's "apply mode" and break-glass, not for staff-tier acts.
- **Per-transaction out-of-band SMS/call confirmation (#24) applied broadly.** As a one-off for bank-detail changes it's proportionate; applied to every payment release it would mean a phone call or text round-trip before every vendor gets paid, which is friction the two-person rule + dynamic linking already cover without a third channel.

## 4. Top 8 (ranked)

1. **Dynamic linking (#6)** — binds the existing seal to the exact amount+payee cryptographically; directly upgrades what Mudavym already has rather than adding new ceremony.
2. **Passkey/WebAuthn user verification as the seal's backing (#4/#23)** — turns "someone held the gesture" into "this specific enrolled person held it," on hardware most staff already carry or that a shared tablet can support.
3. **Tamper-evident hash-chained audit trail (#14)** — makes "the seal is verifiable after the fact" literally true instead of aspirational; low ongoing cost, background-only.
4. **Out-of-band confirmation for vendor bank-detail changes (#24)** — the single highest-fraud act in the whole list (BEC/vendor-impersonation), worth a real ceremony precisely because it's rare.
5. **Velocity/anomaly holds (#18)** — adds protection with zero friction on the common case, which matches "ceremony is rationed" better than almost anything else here.
6. **Per-role/per-day/per-payee limits (#11)** — bounds the blast radius of any single compromised approval, cheap to configure once, invisible day to day.
7. **Device trust / kiosk lock on the shared receiving tablet (#16)** — the precondition that makes the already-adopted manager passcode mean anything on a device anyone can pick up.
8. **Recall/undo window (#13)** — the deliberately *low*-ceremony half of the set: cheap reversibility for correctable mistakes (a receiving miscount, a just-published week), keeping the seal reserved for things that truly can't be undone.
