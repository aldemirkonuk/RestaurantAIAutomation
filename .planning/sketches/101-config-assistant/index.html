101 · The assistant configures the house, and the seal applies it.

The founder, 2026-09-03: “keep as defaults, but while onboarding they have the option to do that. + it will be game changer let AI assistant talk with you and handle all the configs then approval button, research this and understand how should we approach this.”

One rule holds the whole thing up: the assistant may never write a value the owner did not see — and a value that arrives this way is a third kind of value, not the same as one somebody typed.

This house already refuses to read a column default as an answer: lead_time_days DEFAULT 7 means a row reading 7 is exactly as likely to mean “nobody was ever asked” as “the vendor said a week” (vendor-terms.service.ts:47–52). An assistant that fills fourteen registers in one sitting would turn every “nobody gave” into “somebody gave” and destroy that distinction on the house’s first day. So it does not. It writes a third state.

02

Why a diff, and not an interview or a filled-in page

three shapes were weighed; two were rejected on measured facts
ShapeWhat it isWhy it wins or loses
A — one talk, one diff, one seal
chosen		 The owner talks. The assistant returns one document listing every value it would set, grouped by register, each row prunable. One seal applies what remains. Wins, but only amended four times. The field’s settled shape for consequential change — Terraform’s plan, CloudFormation’s change set, Copilot Workspace’s editable plan. It survived four attempts to kill it (see below) and none of the four left it unchanged.
B — a guided interview
rejected		 One register at a time, each sealed. Toast’s onboarding checklist shape. Fourteen seals in a sitting turns the seal into a Next button. And it forfeits the only thing a conversation buys: one sentence — “small meyhane, closed Mondays, three vendors, I sign anything over ₺5,000” — moves eight registers at once. An interview re-asks per register, which is what /settings already is with a wizard on top.
C — fill the page, then review
rejected		 The assistant drafts /settings as pending values the owner walks through. Shopify Sidekick’s shape. Rejected on measured facts, not taste. Three of fourteen registers cannot hold a pending value: measurement is kind: 'browser' (st-format.ts:123) with no server row to stage; features writes to a table with no changed-at column at all (st-format.ts:54–55), so pending→applied cannot be dated; ledger is read-only. C needs a shadow table across eight services — more machinery than the batch — for a worse outcome, because a page of grey pending values is indistinguishable at a glance from a page of real ones.
03

Four attempts to kill shape A

three of the four succeeded partially — every amendment they forced is load-bearing
#The attemptWhat survived, and what changed
1 The seal is a per-commitment ceremony; a forty-field batch devalues it. The house’s own rule rations hold-to-approve — bulk actions get the die pressed dry, no wax. One seal over fourteen registers is the EULA gesture. Partly fatal. Amendment: a register that already holds a stated value never enters the batch. It is contested in a separate section with its own single seal. The batch is only ever a batch of answers nobody gave, so the seal covers filling silence, never overwriting a person.
2 Notion — the closest product in the field — forbids exactly this. Its agent restructures a whole workspace and may not “manage any workspace level settings, like member roles, billing, security features, and more”. Not fatal; it moves the line. Notion’s line is drawn by blast radius, not by the word “settings”. The same test applied here excludes Team, Locations, Features, Services, the ledger and anything touching payment — and does not exclude the registers that encode the house’s judgment about its own trade.
3 The batch cannot be transactional. Fourteen registers are written by eight services with no shared transaction. A seal that completes while three registers silently failed is this repo’s cross-cutting fault in its purest form. Fatal as proposed. Amendment: the batch never reports a single “Done”. Every item carries its own outcome and reason — written · refused · not attempted. Terraform publishes the same limit about itself on the same page as the apply command; so does CloudFormation.
4 It destroys the honesty machinery it is built inside. Fill fourteen registers in one sitting and every one reads as stated; the product can no longer tell “nobody was asked” from “the owner chose this”. Fatal as proposed, and the deepest. Amendment: a sealed proposal is its own provenance class. Not stated — proposed_sealed, recorded with the utterance that produced it. Three states, not two. Costs no migration.

06

Five questions only the founder can answer

the parent asks these; nothing here assumes an answer
1. “Talk with you” — literally talk?

Voice-first setup is plausible on the phone (apps/mobile) and a novelty on desktop. These drawings assume typing. Say if that is wrong.

2. Does a sealed batch belong to the house, or to the person who sealed it?

If a manager seals a batch and leaves, the values stay. Should the batch stay revocable as a unit by the owner, or dissolve into ordinary settings the moment it applies?

3. Is features on the right side of the line?

It is excluded because those switches “change what the system does on its own” (st-format.ts:127). Should the assistant be able to propose turning autonomy on — with the seal — as the natural end of a setup conversation?

4. The market drop threshold is per-deployment today.

MARKET_SIGNAL_DROP_PCT, one number for every house (market-price.producer.ts:95–97). Worth a column and a migration, or correct as it is for now?

5. How much may the assistant read to make a good proposal?

A genuinely useful batch wants the POS history, the vendor threads and the order book. All three are already exposed read tools — but “the assistant read your vendor mail to set your thresholds” is a sentence worth approving before it is true.
