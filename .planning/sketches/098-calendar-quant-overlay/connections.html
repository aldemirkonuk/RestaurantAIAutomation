The four directions, and the order they should be built in

Direction 1

Push — the house’s day-book appears on their phone

Every Mudavym entry is written into a Mudavym-owned secondary calendar on the connected account. Nothing external is ever read, and nothing external is ever touched: the connector owns one calendar and only that one.

Scope
calendar.app.created — Google’s narrowest write scope. It can create a secondary calendar and manage events on it, and can see nothing else.
Cost
One connector, one mapping table (mudavym entry id → provider event id), one write on each create/update/delete. No sync token, no webhook.
Risk
Duplicates, if the mapping is lost and a re-push runs. Closed by an idempotency key on (restaurant, entry, provider account) and by using the provider’s own event id as the update target, never a search.
Deleted on one side
Only one side can delete: ours. A person deleting the pushed copy in Google gets it back on the next push, and the row says so before they connect.
First slice
One vendor delivery pushed to one connected Google account, and the row showing the provider event id it wrote.

Direction 2

Pull — their meetings appear in the house’s book

External events are read into a read-only lane of the day. They are drawn in the book but never editable there, and they never enter the ledger: a pulled event is context for the day, not a house record.

Scope
calendar.events.readonly, plus calendar.readonly to list which calendars exist so the operator can choose.
Cost
A sync token per calendar, a 5-minute poll or a watch channel, and a table of external events keyed by (connection, provider event id, etag).
Risk
A pulled event that looks like a house entry. Closed by drawing it in a separate lane with the account it came from on the line — never a ribbon in the delivery spine.
Deleted on one side
Google’s incremental sync returns deletions explicitly, so a removed external event disappears on the next tick. A 410 means the token expired: discard and full-sync.
First slice
One calendar, read-only, drawn in the day ledger under “From Google” with the account name.

Direction 3

Two-way — one day, two writers

The hard one, and the only one that can lose data. Both sides may create, move and delete, and the house has to decide who wins when both moved the same entry since the last tick.

Scope
calendar.events — full read and write on the calendars the operator picks.
Cost
Everything pull needs, plus a per-entry version pair (our updated_at, their etag), a conflict table, and a UI for the conflicts that cannot be decided.
Conflict rule
Last writer wins per field, and a delete never wins silently. Both changed the time → the later updated_at wins and the loser is kept as a note on the entry. One side deleted, the other edited → the delete is refused, the entry is marked disputed and it goes to the day’s conflict line for a person. Nothing is ever resolved by discarding a row nobody saw.
Risk
The echo: our write triggers their webhook, which triggers our write. Closed by stamping every outbound write with our own request id and ignoring an inbound change whose etag we produced.
First slice
Two-way on one calendar with the conflict line rendered and a delete refusal actually exercised in a test.

Direction 4

Expose — the house’s calendar as MCP tools

Not a calendar connection at all, and that is why it is fourth and not last in value. It offers the day-book to whatever assistant the house already uses, under the same rule the whole product runs on.

Scope
A per-tenant token the house mints, and three read tools plus one propose tool. No send verb exists to call.
Cost
A server package that does not exist yet, a transport, and a token store. The endpoint guard and the handshake are already built on the client side (mcp-runtime), so the shapes are known.
Risk
An assistant that commits. Closed structurally: the tools that could bind the house are not implemented, so there is nothing to refuse at runtime.
Deleted on one side
Not applicable — nothing is mirrored.
First slice
read_day, list_deadlines, propose_entry. Three tools, one tenant, and the propose lands in the same proposal queue the palette uses.

What has to be true before any of it

PreconditionStateWhat it takes
A server-side Google OAuth clientabsent The web app has a Google Sign-In client id; the gateway’s GOOGLE_CLIENT_ID / GOOGLE_CLIENT_SECRET pair is unset, so the integration catalogue reports every Google connector unavailable. A calendar connector needs the secret and a registered redirect URI — a different credential shape from the sign-in client.
Token encryption configuredgate exists Already enforced: the catalogue refuses to offer a connector when the crypto service is unconfigured, rather than storing a refresh token in the clear.
An integration definition rowone table entry The connections table constrains provider to google or microsoft and leaves integration_id a free 64-character string, so adding google_calendar is an entry in the definitions map. No migration.
An HTTPS webhook the provider can reachneeded for push Google requires a valid certificate and calls notifications unreliable by design, so a watch channel is an optimisation over polling and never the only path. Channels do not auto-renew; a job has to re-watch before expiry.
App verificationfounder’s call Calendar scopes are consent-screen scopes on a published app. Whether this deployment stays in testing with a user cap or goes through verification is a product decision, not an engineering one.

The feed that already exists, and why nobody has ever subscribed to it

SuspectWhereThe fix
Served as a download, not a feed calendar.controller.ts:647 The response sets Content-Disposition: attachment, which tells a browser and most clients to save a file rather than subscribe to a changing resource. Drop the header.
Times parsed without a zone calendar.service.ts:1288 Each event is built with new Date(‘YYYY-MM-DDTHH:mm:00’), which resolves on the server’s clock. A house in Istanbul gets its evening service written at the container’s local time. The restaurant’s IANA zone is on the row already.
No refresh hintthe generated calendar No X-PUBLISHED-TTL or REFRESH-INTERVAL, so a client picks its own interval — often a day.
A relative URLcalendar.controller.ts:666 The token endpoint returns a path, not an absolute origin. A calendar client cannot subscribe to a path, and there is no webcal:// alternative offered.
