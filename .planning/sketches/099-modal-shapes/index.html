Mudavym

099 · Three shapes, one primitive.

The founder, 2026-09-03: “create sketches for each because all have diff purposes … three main shape one primitive is a good start.” This is what those three look like on the pages that will use them.

An object gets a sheet. A question gets a panel. A choice gets a popover.

The shape is chosen by what the reader must do next — never by how much content there is, never by which page it is on. That is what makes the shape itself carry information: something arriving from the right is one record and the list behind it still matters; something in the middle wants an answer before anything else; something hanging off a control belongs to that control and nothing else.

Today the product has four hand-rolled overlays and nine more in the legacy shell, each with its own scrim colour, its own keyframes and its own Esc handler. None traps focus, none returns focus to the opener, none locks body scroll. Providers and calendar agree on a right sheet by accident — sketch 010 chose a centred sheet and nobody enforced it.

The three

When a page reaches for each

The record
One thing
Sheet · tuck 300ms · 440px

An object

A vendor, a calendar entry, a member, a letter. You came from a list and you will go back to it, so the list stays lit on the left. Focus is trapped, the body stops scrolling, and the close control is the word Close.

Never: a question, a menu, a second object, or a page wearing a scrim.
Ask
One answer
Panel · settle 320ms · 620px

A question

⌘K, Ask the book, the shortcuts card, and the confirmations that carry the seal. It sits where the eye already is because the page behind it is not the subject. Focus trapped, scroll locked, Esc closes.

Never: a record, a menu, a ten-field form, or a notice with nothing to answer.
Popover · ink 160ms · anchored

A choice

The bell, the branch switcher, the user menu, the invite form. It does not dim the page and it does not trap focus — it is one control's own drawer, and tabbing past it should leave it.

Never: a record, a commitment (the seal never appears here), a long form, or anything without a visible trigger.
Honesty

The three hard cases, said out loud

a taxonomy is only worth adopting if it survives the cases that do not fit

  • The invite formIt is a form (a panel's job) attached to a button (a popover's job). It resolves as a popover because the answer is two short choices about the roster underneath, and covering that roster hides the reason you are inviting anyone. The tree already made this call — it is the one Radix dialog in the product that takes an anchor. Rule: a form belongs in the anchored shape when the thing it is about must stay visible while you fill it in.
  • Deleting one recordA question (panel) about an object (sheet). It stays in the object's sheet, below a double rule, as a hold-to-approve. Stacking a panel on a sheet to ask about the sheet is two overlays for one thought. Rule: a question about the object already open never leaves it.
  • The composerA letter is an object being written — a sheet — but 440px is too narrow for a body with inserted figures. The honest answer is that width is a parameter, not a shape: sketch 100 asks the primitive for one wide sheet at 640px and changes nothing else. Making it a panel instead would cover the conversation book the letter is a reply to.
The field

Where the three shapes come from

None of this is invented. Every product that has more than one overlay shape has separated them the same way, and each source below decides the split by the same question — is the page underneath still the subject?

  • LinearPeek preview exists so you can “view details of focused issues at a glance from any list or board view, similar to Quicklook in macOS”, and arrow up and down through adjacent issues with the preview updating. That is only possible because the list is not covered. A centred modal cannot do it at all.
  • NotionSide peek “opens the page in a side panel, splitting your screen in two… you can view both pages at once”, and it is the default for table, board, timeline and list — the layouts where the surrounding rows are the context. Calendar and gallery default to centre peek instead.
  • shadcn / RadixSheet “extends the Dialog component to display content that complements the main content of the screen” — the same distinction, stated as an API. Popover is a third thing: anchored to its trigger, modal false by default.
  • StripeThe Dashboard opens a payment as a detail view over the payments list; Stripe ships the same thing to platforms as an embedded component whose docs call it “the detail overlay of a given payment” — one record, over its list.
  • AppleHIG, Popovers: “a transient view that appears above other content onscreen when people click or tap a control”; its arrow must point at the element that revealed it and must not cover it; and people “can unintentionally dismiss a nonmodal popover”. That last sentence is why the seal never appears in this shape.
  • W3CAPG, Modal Dialog is the contract the primitive meets and the four hand-rolled overlays did not: Tab wraps to the first element from the last; Escape closes; focus moves inside on open; and “when a dialog closes, focus returns to the element that invoked the dialog”.
  • GOV.UKThe most conservative design system in the field still has no published modal component — the request has sat open in the backlog, unpublished, while services build their own. The lesson we take is not “never use one” but the reason it stays unpublished: a modal is a debt you take on the reader's behalf, so three named shapes with stated boundaries is the least you can ship responsibly.
The fork

What only the founder can decide

  • 1 · Three, or one?The strongest case against this sketch is one shape everywhere: one implementation, one motion, one contract, and nothing for anyone to learn. It loses because it deletes the page underneath — the sheet exists so the list stays readable, and an anchored menu with no anchor is a menu that has lost its meaning. But it is a real simplification and it is the founder's to refuse.
  • 2 · Does the composer get a wide sheet?640px instead of 440px for one named case (sketch 100). Either the primitive gains a size parameter, or the composer becomes a route and stops being an overlay at all.
  • 3 · Does the seal ever appear in a popover?This sketch says never, on the grounds that popovers are dismissed by accident. If the founder wants one-click approvals from the bell, that rule has to be written down as an exception rather than quietly broken.
