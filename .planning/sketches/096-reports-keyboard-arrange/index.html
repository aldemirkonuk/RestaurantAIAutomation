096 · Moving a cutting without a pointer.

“Keyboard drag and resize are not supported by the grid library … research web find a way to be able to do that, engineering part is important research and analyze — if found ways create me a sketch for it.”

A way was found, and it is not a new library. react-grid-layout still exposes no keyboard affordance — its own request for one (issue #936, 2019) went stale and was closed unimplemented — but its layout is a controlled prop, and this page already holds it. Measured in the installed package: the responsive grid re-derives its internal layout whenever the layouts prop stops deep-equalling the previous one, and the library's own pointer path is exactly two exported functions, moveElement then compact. The keyboard runs the same two. A keyboard move and a dragged move to the same square produce a bit-identical layout, because they are the same function.

Grafana's dashboard is built on this same library and is recorded as unable to move a panel from the keyboard (grafana#79627). The interaction model below is dnd-kit's KeyboardSensor (Space/Enter to start and end, Escape to cancel) and react-aria's “drag affordance”; the button path exists because WCAG 2.2 SC 2.5.7 asks for a single-POINTER alternative and is evaluated independently of keyboard access.

Direction A · built

The grip and the placing bar

A named Move grip on every cutting while arranging. Space picks it up, arrows move one grid unit, Shift and an arrow resize, Enter places, Escape puts it back. A bar of ordinary buttons does the same ten things for a pointer that cannot drag. Shows the focus ring, the ghost outline and the announcement.

Ships behind mudavym_design_reports · no new dependency

 Direction B · not built

The compass card

The same handlers behind a floating three-by-three pad anchored to the held cutting, with four named outcomes underneath. Calmer inside a small cutting; costs a floating layer that must chase a cutting which moves on every keystroke.

A swap, not a rewrite — same arrange engine

 Direction C · not built, and why

The move-to menu

The pattern the strongest counter-argument recommends: no arrow keys at all, a menu of named outcomes per cutting. Right for a board with nameable destinations; on a free twelve-column canvas the outcomes are coordinates, and the menu can only ever offer less than the pointer can.
