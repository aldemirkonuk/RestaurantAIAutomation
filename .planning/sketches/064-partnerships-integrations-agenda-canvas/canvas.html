The finding that reframes the seed

Square and Clover are not half-built adapters. Both normalizers are written and registered (pos-adapters.ts:72, :116, :198-202); the registry says what is missing in its own words — "needs merchant OAuth token", "needs merchant API token".

But the door they would knock on verifies the wrong thing. verifyWebhookSignature(rawBody, signature) takes no provider argument and keys off one global POS_HUB_WEBHOOK_SECRET for all 27 providers and all restaurants — so a signature valid for restaurant A is valid for restaurant B's URL, and no real vendor's signature scheme is implemented at all. Filed as OD-B on 2026-08-24. Never registered. Never carried into this department's charter, which still calls that route correct.

So: the second POS provider is blocked on neither engineering effort nor a partner signature. It is blocked on one unregistered fork about where a per-connection secret lives.
