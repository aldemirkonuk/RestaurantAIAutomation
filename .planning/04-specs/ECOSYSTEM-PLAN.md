## 1. The one sentence

The **sell-side sensing loop is real and closed** — a guest's order flows autonomously from POS check → inventory depletion → low-stock detection → analytics learning — but the **buy-side acting loop breaks at the sense→act seam** (and, measured 2026-09-01, *one ungated path across that seam already exists and E1's own POS unification would switch it on*), the **intelligence layer promises far more than it computes**, the **demand-origin (the guest) is unbuilt and held**, and three **cross-cutting faults** (a two-runtime split, auth-by-omission, and zero real-merchant data) sit under all of it. This plan closes the loop, in an order the founder chooses.

## 3. The four segments — verdict and the load-bearing gaps

Full evidence in `eco-research/01-04`.

**POS → data spine** (`01`) — *the hard half is built and runtime-proven on synthetic data, but has never carried one real restaurant's check, and the one provider it's configured for (Toast) bypasses the spine.* Gaps: zero merchant-backed providers; Toast never writes `pos_checks` and still carries the `?? "bottle"` 5× over-depletion on its own path — **the default is at `toast.service.ts:524`, and three documents cite `:502`/`:520`, all stale**; the Toast door also POSTs to a route that does not exist (`:697` → orchestrator has only `/api/v1/pos`) and **swallows the 404** at `:708-715`, and never selects `sale_volume_ml` (`:472`) so the remediation UI cannot repair the over-depletion; cross-tenant webhook forgeability (**half-fixed — see hop 1**); push-only, no `pos_connections` model, no pull path for 13 webhook-less providers, `csv_import` doesn't parse CSV; real-venue onboarding unbuilt (catalog pull is SimPOS-only).

**Restaurant ops loop** (`02`) — *both ends SOTA (lots-as-truth depletion; receiving→four-way-match→credit→landed-cost), the middle doesn't auto-close, and the automation that exists is wired to the wrong POS pipeline.* Gaps: deplete→reorder unwired; **two divergent POS pipelines** — the dead wiring is confirmed and holds by **four independent breaks**, any one sufficient: `pos.sale.completed` has one producer in the whole repo (`pos_integration_agent.py:837`, zero in `apps/`); the Toast door 404s (hop 1); the pos-hub spine has no orchestrator wiring at all; and — previously unnamed — the **envelope shapes disagree** (NestJS publishes flat at `orchestrator.service.ts:78-88`, Python wraps as `{event_type, payload}` at `message_bus.py:693-701`, and `buffer_manager.py:231` reads `message["payload"]` then bails at `:242`). **One correction that shrinks the fix:** the Python read side is *already on the live path* — `buffer_manager` evaluates `restaurant_inventory` (`core/database.py:814`), the lots projection NestJS writes — so **only the trigger is disconnected, not the data**; Toast fail-closed for all 10 restaurants (`TOAST_WEBHOOK_SECRET` unset, OD-64); reconcile hinges on a manual `verifyReceipt`; `recurring_order_agent` auto-approve had no per-order gate **(closed this session by the A3 fix, PR #152)**.

**Sales / analytics intelligence** (`03`) — *healthy tested core, hollow edges — a strong deterministic engine wrapped in claims and menus that outrun what computes.* Gaps (**numbers corrected 2026-09-01**): the honest reconciliation is **enumerated 573 vs implemented ≤24, gap ~549** — not 573/375/19. 573 is real (`insight-catalog.ts:547`, settled by OD-33); **375 was never a true state on main**; ~19 undercounted (16 `record()` sites plus a helper called 3× emitting 12 more keys = **24**), and *fewer than 24 actually fire* because two families are dead on a missing `provider_name` column and an `undefined` `wineId` join key. **The shipped "computable now" meter overstated by ~24× — it showed 573 of 573, its ceiling being the whole catalogue, against ≤24 real. Live to users and a violation of locked ADR 0020; fix in flight (PR #199) takes it to 24.** Feedback loop half-wired (`recommendation_impressions` logged never read; `insight_acceptance_rate` computable never computed); ~~Ask AI is not on main~~ — **Ask AI IS on main and in production** (`ask-ai.service.ts:913-926`), and it is the propose→confirm→execute spine the hop-4 bridge should build on; consultant grounding has a failed-fetch blind spot **(scheduled as analytics-bi C1)**; analytics reads `stock_live`+`wine_consumption_log` not the lots ledger (latent dual-bookkeeping) and consumes **zero guest data** — no seam to the customer segment.

**Customer / guest** (`04`) — *the demand-side flywheel input; almost entirely potential, not built, and held.* The NF store ships with the guest slot open but **zero emitters, zero rows**; the 564-line consent slice has **zero callers**; guest keys are HMAC-*derived* from one master (can't be crypto-shredded — needs *stored* per-guest keys, ADR 0037 addendum); `erasure_receipt_id` dangles; the only POS↔guest seam is `guest_check_links.pos_check_id`, unwired. Activation prereqs (all founder-gated): OD-05/OD-07, the erasure model, A15 dish-identity vs wine-only taste, the k=20 anonymity gate as code.

## 4. Cross-cutting faults no single segment owns

1. **The sense→act seam (hop 4).** The buy-side has no autonomous trigger; the core "autonomous operations" promise breaks exactly here. Owner: nobody today.
2. **The two-runtime split.** Live path is NestJS; the agent fleet is Python; they meet over RabbitMQ. Buy-side *send* is RabbitMQ-only into a Python orchestrator CI can't prove is alive — a silent orchestrator means approvals that never reach the vendor. This split also explains why the automation is wired to the dormant Python POS pipeline. It ties directly to **OD-03** (the harness choice, still open).
3. **Auth-by-omission — ~~~94 endpoints~~ measured 2026-09-01: ZERO by omission.** 468 route handlers, 444 authenticated, 23 deliberately public with evidence, **0 by omission**, 1 unclear. The six prior numbers were six different questions on three different trees, not a conflict; the reproducible series is 131 → 71 → 6 → 7. **The defect count is zero and the defect *generator* is intact:** `JwtAuthGuard` is per-controller, not `APP_GUARD` (`app.module.ts:130-137`), so a controller that declares nothing is fully unauthenticated by default — endpoint 469 arrives unguarded. `TenantGuard` fails open and *can never do otherwise* (global, runs before passport sets `request.user`, comparison at `tenant.guard.ts:37-46` has never executed) — but `assertTenantMatch` now lives in `JwtAuthGuard:60`, so tenant isolation fails **closed** on any guarded route; state both halves or the claim misleads. Still open: WebSocket auth fails open outside production (`websocket.gateway.ts:672-678`, and dev/staging share prod's Supabase per OD-35) and Swagger is unauthenticated at `/api/docs`. Full census + the four counting traps: [ECOSYSTEM-E0-MEASUREMENTS.md](ECOSYSTEM-E0-MEASUREMENTS.md) §2.
4. **Zero real-merchant data.** The entire analytics stack is downstream of a pipe proven only on a 47-row simulator window + 66 P3PROOF fixtures. L0 data is the named blocker (README §1).
5. **Doc-vs-reality skew — ~~this fault's own citation was false when written~~.** `STATE.md:8` and `PROJECT.md:31` both read **"P3 — Grade, then scale"**, and had since 2026-08-26/27 — a day *before* this sentence was written. P1 was not the frontier: P1 closed 2026-08-24/25, P2 on 2026-08-26, and P3.0's gate shipped 2026-08-27. The symptom is real but the live skew is narrower and different in kind: `ROADMAP.md:35` still shows P3.0 open; `STATE.md:92` calls P3.A mobile parity "not started" when it merged 8.9%→20.3%; `STATE.md` names no section for the ~32-commit Mudavym brand track; `v3.0-TECH-DEBT.md:36` still says P2. Those four are E0's actual doc work. See [measurements](ECOSYSTEM-E0-MEASUREMENTS.md) §1 and §9.

6. **Silent cross-runtime failure (new, 2026-09-01).** Five instances across three runtimes, **none visible to CI**, all the same shape — a swallowed error making a permanently-dead path look like a merely-empty one: the Toast door's 404 (`toast.service.ts:697`→`:708-715`), the NestJS↔Python envelope mismatch, the `conversations.*` path returning `messageSent: true` over a nonexistent route, a load-bearing bare `except` at `provider_conversation_agent.py:2677`, and the insight generator selecting a column that does not exist. A platform posture, not five bugs. Owner: unassigned. See [measurements](ECOSYSTEM-E0-MEASUREMENTS.md) §7.

## 6. The phases (content fixed; order is §7's fork)

- **E0 — Foundational integrity.** Land the four fixes; finish the auth-by-omission classification to one reproducible census + a global-guard decision; true up STATE/PROJECT to the real frontier. *Rationale: nothing above is trustworthy while the door is open, the pipe is unaudited, and the map is stale.*
- **E1 — Close the buy-side loop.** **E1.0 (blocking, founder-locked 2026-09-01): gate `procurement_agent` to proposals-only before anything else lands.** It is an ungated path to a vendor that E1's own POS unification would switch on; nothing else in E1 ships until a par crossing cannot reach a vendor without a human. Then: build the sense→act bridge — the *output* half already exists in production (`ai_proposed_actions` + `AskAiService.confirm`), so this is a **proposer**, not a table or a gate; unify the POS pipeline so automation feeds the **live** path (cheaper than it looked — `buffer_manager` already reads `restaurant_inventory`, the live lots projection, so **only the trigger is disconnected, not the data**); and make cross-runtime send reliable — noting the seam is `approveOrder`'s queue-only publish, *not* the send itself, and that a **stuck approval is currently invisible**. *This is the flagship "autonomous operations" promise, and it is one seam wide.*
- **E2 — Make the intelligence honest and actionable.** Reconcile 573/375/19 to one truthful number the engine actually produces; wire the feedback loop (`recommendation_impressions` read, `insight_acceptance_rate` computed); give the cost/verdict views their readers; merge Ask AI as the insight→action bridge; close the grounding failed-fetch blind spot.
- **E3 — Turn on the demand side (staged, gated).** Only behind its founder forks: the erasure model (stored keys), consent enforcement as code, the k-threshold guard, OD-05/OD-07. Wire the guest→check seam and, if activated, guest-taste → recommendation. *NF-B stays HELD until the founder says otherwise.*
- **E4 — Real-merchant activation & the closed loop.** Onboard the first real venue (Toast onto the spine, catalog pull, "create inventory from POS item"), then close hop 10 (recommendation writes back to par/menu, human-gated), then begin the wine→beverages vertical expansion.

## 7. The forks — the founder's to decide (§0.1)

These are put to the founder before this becomes a locked ADR. They are in the companion question set; recorded here so the doc names them.

1. **Sequencing. ✅ Locked by the founder 2026-08-28: E1 leads after E0.** Close the buy-side autonomous-ops flagship on the sell-side data we already have — the sense→act bridge (hop 4) is one seam wide and the highest-visibility promise. E2/E4 run behind it; E3 stays gated. *(Considered and not chosen: E2-intelligence-first, E4-real-merchant-first — recorded so the order is not silently revisited.)*
2. **The two-runtime question (ties to OD-03). ✅ Locked by the founder 2026-08-28: decide it via the A1 bake-off (PR #150), not by a guess now.** "NestJS-native fleet vs keep-Python-and-harden-the-bridge" enters the bake-off as a scored axis; the plan sequences the runtime commitment as a *bake-off output*. Until it reports, E1 hardens the existing NestJS↔Python send seam (an HTTP fallback / outbox for `conversation.approved`) rather than migrating either way — that hardening is useful under both outcomes.
3. **Autonomy posture for the sense→act bridge. 🟡 Answered 2026-09-01, not yet closed: the founder asked for "everything in detail, proof planned, and designed carefully to mimic real world exactly as is" rather than picking a posture.** So the posture is deferred to shadow data and the bridge must be built with cap and ranking as *parameters*, not baked-in assumptions. Standing recommendation is **(c) every crossing proposes into a capped, ranked, batched queue** — because the fork as posed is a false binary between "all" and "filtered" when the real variable is *how many reach a human per day*, and a cap is a filter nobody has to author. Measured grounding: production logged **3,242 new crossings in 20 days across 64 SKUs**, so posture (a) would have emitted 3,242 draft POs; posture (b) depends on a config surface being filled, and this repo's precedent is against that (`restaurant_feature_flags` holds exactly **one** row in production). Posture (b) stays reachable later as a *suppression layer* over (c), which is the ordering that makes rules authorable rather than speculative. **This fork still has no OD row** despite being named here since 2026-08-28.
4. **The POS `pos_connections` fork (OD-A/OD-B, unfiled).** Per-connection webhook secret + per-vendor signature schemes: a new `pos_connections` table vs a column on `restaurants`. The env-scoped half is in flight; this half needs an ADR.
5. **Guest activation trigger (OD-05/OD-07).** Unchanged — when does the demand side turn on. Named for completeness; E3 is gated on it and nothing here moves it.
